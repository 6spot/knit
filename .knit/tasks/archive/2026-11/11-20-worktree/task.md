## 目标与范围

现在执行者只在主检出里跑，整个项目同一时间只能有一个（`docs/design/DESIGN.md` 第 7 节）。两个后果：

- 任务不能并行。用户在瘦身重构时就定了「Worktree 必须有：多个任务并行时各用一个 Worktree，互不影响」；旧实现随旧代码删掉了，要在现在的代码上重新做。用户 2026-11-20 决定提上日程。
- 执行期间主检出里别人改的文件会算到执行者头上。2026-11-19 的执行 `r-5f861db2a268` 因为用户手动改了 `.knit/workflow.yaml` 被记成「执行者改了受保护的文件」；改动是靠派发前后对比出来的，不区分是谁改的。用户 2026-11-20 决定：这个问题不单独处理，以后靠 Worktree 隔离解决，不做依赖某个客户端的归属判断。

做完之后：派发的任务在自己的 Worktree 和分支里执行，几个任务可以同时跑，互不影响；主检出里的改动碰不到执行者。

第一版的范围（用户 2026-11-20 定）：

- 做：派发的任务各有一个 Worktree 和一个分支，执行、审查和提交都在里面；不同任务可以同时跑。小任务由主会话直接做，不派发，没有 Worktree。
- 做：新建 Worktree 之后运行配置里的准备命令（例如装依赖）。
- 做：合并和清理的开关。配置了，交付之后自动合并进主检出的当前分支并删掉 Worktree 和分支；没配置时由用户或主会话用 Git 做，Knit 只告诉分支名和位置。合并失败时不硬来，由主会话问用户。
- 做：取消任务时删掉它的 Worktree 和分支。
- 做：Worktree 这部分新加的代码在 Windows 上也要成立（位置、路径、准备命令）。让整个 Knit 在 Windows 上跑起来不在这个任务里：现在的进程管理只适用于 macOS 和 Linux。
- 不做：解决合并冲突、任务之间的调度、把没入库的文件复制进 Worktree 的白名单。旧方案里的这些规则（`docs/research/WORKTREE.md`）不照搬。

这是主任务：方向、设计和子任务清单在这里，不产出代码，改动都在子任务里。设计在 `design.md`，子任务清单在 `plan.md`。设计里的方案用户 2026-11-20 都定了，决定记在 `design.md` 第 8 节。
