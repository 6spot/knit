# Worktree 设计

方案已定（用户 2026-11-20，决定在第 8 节）。都还没有实现。第 5 节末尾列出的 Git 行为在临时仓库里试过；其余做法没有试过，依据是现在的代码、Git 和 Pi 1.5.2 的文档。

## 1. 什么时候用 Worktree

- 派发执行者的任务一律在自己的 Worktree 里执行，不再有在主检出里派发执行的方式。
- 小任务由主会话直接做，不派发，也就没有 Worktree：和现在一样在主检出里改、`task close`、交付。

## 2. 一个任务一个 Worktree

```
~/IdeaProjects/knit/               主检出：主会话在这里，任务资料和运行资料都在这里
  .knit/tasks/11-20-foo/           task.md、record.json（只有这一份）
  .knit/.runtime/runs/<id>/        交接内容、日志、报告、会话记录

~/.knit/worktrees/
  knit-3f9a1c2e/                   一个项目一个目录
    11-20-foo/                     任务 11-20-foo 的 Worktree，分支 knit/11-20-foo
```

- 位置是 `<Knit 的用户目录>/worktrees/<项目目录名>-<摘要>/<任务目录名>/`，分支是 `knit/<任务目录名>`。都从主检出的路径和任务目录名算出来，不另存绑定关系。
- Knit 的用户目录缺省是用户主目录下的 `.knit`（macOS 和 Linux 是 `~/.knit`，Windows 是 `C:\Users\<用户名>\.knit`），可以用环境变量 `KNIT_HOME` 换掉；测试靠它不碰真的用户目录。
- 摘要是主检出真实路径（解析符号链接之后）的 SHA-256 前 8 位。带它是因为两个项目的目录名可以相同（同一个仓库克隆了两份）。
- 不放在项目里，也不放在项目旁边。Pi 会加载工作目录和它所有上级目录里的 `AGENTS.md`（Pi 1.5.2 `docs/configuration.md`「Context files」）：放在项目里面时执行者会同时读到 Worktree 和主检出里的两份。
- 第一次派发时建：从主检出当时的 `HEAD` 开分支。主检出里没提交的改动不会带过去。仓库还没有提交时拒绝派发，提示先提交一次。
- 再次派发（返工、审查）用同一个 Worktree。目录不在了而分支还在时，按分支重新检出（Git 还登记着那个不在了的目录，要先 `git worktree prune`）。
- 新 Worktree 里只有入库的文件，没有 `node_modules` 这类被忽略的目录。`config.json` 的 `worktree.setup` 写建好之后要运行的命令（第 6 节），按顺序在 Worktree 里跑，只在新建时跑。有一条失败：把刚建的 Worktree 和分支删掉，拒绝派发，原样给出错误；下次派发重新建。

## 3. 执行

- 执行者的工作目录是 Worktree。派发前后的工作区记录在 Worktree 里拍，改动文件是 Worktree 里的相对路径。
- 那份检出里只有执行者在写，对比出来的改动就是它的。受保护文件的检查照旧，但只看 Worktree 里的那一份：用户在主检出里改 `.knit/workflow.yaml` 不再影响执行。这一条不依赖客户端。
- 执行者不能提交：结束时 Worktree 的 `HEAD` 变了，这次执行记为失败。审查通过之后任务回到主会话，主会话核对之后用 `knit deliver` 提交（第 5 节）。
- Knit 自己读的流程、规范、配置和角色文件用主检出里的；Worktree 里的那几份只是分支上的文件。
- 任务资料只在主检出里有一份。任务目录交付之前没有入库，Worktree 里没有它。运行资料（`.knit/.runtime/`）也留在主检出。
- 交接内容里：`.knit/tasks/` 下的资料（本任务的和别的任务的，例如主任务的设计）和以前各次的报告从主检出读，路径写成主检出里的绝对路径，并说明任务目录只读；仓库里的资料从 Worktree 读，路径照旧是相对路径，执行者按路径读到的就是附上的那一份。
- 主会话看任务状态的地方多一行 Worktree 的位置和分支：主会话要去那里核对。

## 4. 并行

- 「项目里只能有一个执行者」改成「一个任务同一时间只有一个执行者」。不同任务可以同时派发，各自结束时各发一条通知。
- 各任务写的是自己的 `task.md` 和 `record.json`，互不相干；写文件时核对版本的做法不变。
- 依赖的规则收紧：依赖的任务要是 `delivered`，并且在主检出里看得到。现在 `done` 就算数，但 `done` 的任务代码还没提交，新开的 Worktree 里拿不到。依赖的任务已经交付但还没合并时，拒绝的提示要写明「可能还没有合并」，不能只说任务不存在。

## 5. 交付、合并和清理

代码和任务记录一起，在任务分支上提交一次。授权的规则不变：`knit deliver` 要有用户的授权，可以在任务开始时就给。自动合并开着时，这一次授权同时覆盖合并。

1. 预览：列出 Worktree、分支、要提交的文件、「结果」和提交文案；自动合并开着时写明会合并到哪个分支。
2. 状态改成 `delivered`，记下授权，把任务目录从主检出移到 Worktree 里的 `.knit/tasks/archive/<YYYY-MM>/`。
3. 在 Worktree 里只暂存这些文件，在任务分支上提交一次，末尾加 `Knit-Task: <id>`。
4. 核对提交内容。Git 拒绝提交时撤回：任务目录移回主检出，状态改回 `done`。
5. 自动合并关着（缺省）：输出分支名、提交号和 Worktree 的位置，合并和清理由主会话接着用 Git 做，不用再问用户：交付的授权同时覆盖合并和清理。
6. 自动合并开着（`worktree.autoMerge`）：在主检出里把任务分支合并进当前分支，然后删掉 Worktree 和分支。

自动合并的规则：

- 用普通的 `git merge`：能快进就快进，不能时生成一个合并提交。合并的结果都落成提交，主检出里不留没提交的合并结果（不用 `--squash`、`--no-commit`）。不要求快进，因为几个任务并行时主分支在前一个任务合并之后已经往前走了，后面的任务都快进不了。
- 合并失败（有冲突，或主检出里没提交的改动挡住了）：有冲突时放弃这次合并（`git merge --abort`），Worktree 和分支都留着，原样输出 Git 的错误。任务仍然是 `delivered`，提交留在任务分支上。
- 合并失败之后由主会话问用户怎么处理。交付规范里写明：主会话这时把 Git 的错误给用户看并问他，不自己解决冲突，不强行合并。
- 合并成功之后的清理不强制：Worktree 里还有没入库的新文件时 Git 拒绝删除，留着并报告。

取消任务（`knit task cancel`）：不合并，把它的 Worktree 和分支都删掉，用强制删除，里面没提交的改动随之丢掉。取消的任务不会接着做，要做就重新开任务。输出里写明删了什么；删不掉时任务照样取消，报告位置。

在临时仓库里试过的 Git 行为（2.54.0，macOS）：

- Worktree 里有没入库的新文件时 `git worktree remove` 拒绝，退出码 128；只剩被忽略的目录（`node_modules`）时成功，连同它一起删掉；加 `--force` 时有没提交的改动也删。
- 分支还被 Worktree 占着时 `git branch -d` 拒绝；合并并删掉 Worktree 之后成功。
- 目录被直接删掉而分支还在时，`git worktree add -b <分支>` 被拒绝（分支已经存在）；不带 `-b` 检出那个分支也被拒绝（目录还登记着），先 `git worktree prune` 之后成功。
- 还没有提交的仓库里 `git worktree add -b` 退出码是 0，建出来的目录是空的。
- 主检出里同一个文件有没提交的改动时，`git merge` 退出码 1，不进入合并状态，文件没被动过。
- 两边改了同一行时，`git merge` 退出码 1 并进入合并状态；`git merge --abort` 之后工作区恢复原样。

别的后果：

- 自动合并关着时，交付之后、合并之前主检出里看不到这个任务；合并之后它出现在主分支的归档里。
- 主会话直接做的任务交付方式不变：在主检出的当前分支上归档并提交。
- 任务目录在交付之前就被提交过的情况（分支上也有一份），留给交付的子任务处理。

## 6. 配置

`.knit/config.json` 加一组字段，都可以不写：

```json
{
  "worktree": {
    "setup": ["npm ci"],
    "autoMerge": true
  }
}
```

| 字段 | 缺省 | 含义 |
| --- | --- | --- |
| `worktree.setup` | 没有 | 新建 Worktree 之后按顺序运行的命令 |
| `worktree.autoMerge` | `false` | 交付之后自动合并进主检出的当前分支，并删掉 Worktree 和分支 |

不做复制文件的白名单：要复制的东西还没有遇到，遇到了再加。

## 7. Windows

Worktree 这部分新加的代码在 Windows 上也要成立：

- 用户主目录用 Node 的 `os.homedir()` 取，文件路径用 `node:path` 拼，不手写 `/`。Git 给出的仓库内相对路径仍然是 `/` 分隔。
- Git 命令照现在的做法用参数数组调用，不经 shell。
- 准备命令经系统的 shell 运行（Windows 上是 `cmd.exe`）：那里的 `npm` 是 `npm.cmd`，不经 shell 启动不了。命令本身能不能跨平台由项目自己写对。
- Worktree 的路径尽量短，不再往下加层级：Windows 的路径长度缺省上限是 260 个字符。

范围的边界：Knit 现在整体没有在 Windows 上跑过，`src/` 里没有按平台分支的代码，管理执行者进程用的是 `ps` 和进程组信号，这些在 Windows 上不成立。让整个 Knit 在 Windows 上跑起来不在这个任务里。上面几条也都没有在 Windows 上试过。

## 8. 用户的决定

2026-11-20：

- 派发才用 Worktree；小任务由主会话直接做，没有 Worktree。
- Worktree 放在 `~/.knit` 下面，不放在项目的同级目录；Windows 上也要成立。让整个 Knit 支持 Windows 先不考虑，不建任务。
- `~/.knit` 里旧 Knit 留下的 `keys` 和 `locks` 不保留（当天已删）。
- 交付时代码和任务记录在任务分支上提交一次。
- 加准备命令，尽量少出问题。
- 加自动合并和清理的开关，配置了才做。一次交付授权同时覆盖合并；用普通合并，不要求快进。
- 合并失败时不硬来，由主会话问用户。
- 自动合并关着时，主会话手工合并和清理不用再问用户。
- 模型：主会话在主检出里直接做的用主会话当前的模型，不切换；派发到 Worktree 分支里做的用 openai；模拟演练用 deepseek。
- 取消的任务也清理 Worktree 和分支。
- 执行者不能提交；审查之后交给主会话，主会话判断之后提交。
- 受保护文件分不清是谁改的，不单独处理，靠 Worktree 隔离解决；不做依赖某个客户端的归属判断。
- 合并的时候一定要提交：没有提交的东西，之后建出来的 Worktree 里没有，就会出现主检出里有、Worktree 里没有的情况。
- 派发被拒绝时不留下这次新建的 Worktree 和分支；点名的资料没提交时在提示里说明。
- W5 到 W9 先都写好正文，一次看完之后按顺序逐个执行。
