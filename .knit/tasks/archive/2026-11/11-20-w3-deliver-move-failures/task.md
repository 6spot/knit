## 目标与范围

上一个子任务（W2，提交 `93472d2`）之后，派发过的任务交付时，`knit deliver` 把任务目录从主检出移到任务的 Worktree 里归档，在任务分支上提交。主会话核对时试出两个缺陷，审查没有发现，都能复现（见「相关资料」）：

1. 跨文件系统时交付失败，并且卡住。移动目录用的是重命名，源和目标不在同一个文件系统时报 `EXDEV`。这时任务状态已经改成 `delivered`、授权已经记下，目录还在主检出，没有提交；再交付一次被拒绝（「已经结束」）。Worktree 在用户目录下，项目在别的盘上就会遇到；系统临时目录在另一个文件系统（Linux 上常见）并且任务目录入过库时也会遇到。
2. 任务目录被 Git 忽略的项目会丢任务记录。任务目录移进 Worktree 之后提交里没有它，合并之后主检出里也没有；`git worktree remove` 成功之后任务记录就不在任何地方了。

本任务修这两个缺陷。做完之后：

- 派发过的任务在项目和 Worktree 不在同一个文件系统时也能交付，结果和在同一个文件系统时一样。
- 交付过程里任何一步移动失败（不只是 `EXDEV`），都撤回到运行之前的样子：任务目录在主检出原来的位置，状态是 `done`，没有记下授权，Worktree 里没有暂存的改动和新建的归档目录，任务分支上原来带着的旧任务目录还在；原样报告错误。现在只有 Git 拒绝提交时才撤回。
- 任务目录被 Git 忽略时，归档留在主检出里（和没有派发过的任务一样），不移进 Worktree；任务分支上的提交只有代码。预览和输出里的归档位置跟着写对。

思路上已经定的：

- 任务目录被 Git 忽略时归档留在主检出（用户 2026-11-20 定）：不走「移进 Worktree、清理之前再搬回来」，步骤少的那种出错的机会少。
- 临时存放任务分支上那份旧任务目录的位置不要用系统临时目录：它和 Worktree 可能不在同一个文件系统。旧的那一份在 Git 里，可以不存放、失败时从 Git 恢复，也可以放在 Worktree 所在的文件系统里；用哪种由执行者定。
- 跨文件系统的移动怎么实现由执行者定（例如重命名失败时改成复制再删除）。要保证的是：中途失败时源还在，不留下只复制了一半的目标。

不能变的行为（都有测试）：

- W2 的三个场景：提交落在任务分支上；Git 拒绝提交时撤回；任务目录入过库的任务交付之后合并得进去。
- 没有派发过的任务、不在 Git 仓库里的项目，交付的结果和输出不变。

不能动的：

- `.knit/standards/`、`.knit/workflow.yaml`、`.knit/config.json`、`.knit/agents/` 是受保护的，改了这次执行会记为失败。`.pi/extensions/knit.ts` 是生成的副本，也不改。
- 执行相关的代码（`src/application/run-*.ts`、`src/application/worktree.ts`）：本任务只用它，不改它的行为。
- 交接内容、配置字段、自动合并、清理、取消任务时的清理、并行：都是后面的子任务。
- `validation/`、`docs/history/`、`docs/research/` 是历史记录，不改。不加依赖。

`docs/design/DESIGN.md` 第 8 节跟着改：撤回的条件（现在只写了 Git 拒绝提交）、任务目录被忽略时归档在哪、「没有可恢复的中间状态」那一段现在的说法还对不对。

环境（这个任务在一个新建的 Worktree 里执行）：

- Worktree 里没有 `node_modules`：开始之前先在 Worktree 里运行 `npm ci`。装不上时停下来报告。
- Worktree 里没有 `.knit/tasks/` 下这个任务和主任务的目录，它们只在主检出里，内容已经附在交接里。主检出只读，不要在里面改任何东西。
- 测试不在真实的用户目录下建东西：测试辅助已经把 `KNIT_HOME` 指到临时目录。

验证：

- 新的场景先写测试，看到它失败再改代码。
- 跨文件系统的场景在测试里不好造（要另一个文件系统）。自动测试至少覆盖「移动失败时撤回」；真的跨文件系统的情况在 macOS 上用内存盘验证一次（做法在「相关资料」里），用完卸载，报告里写实际看到的结果。要不要把它做成自动测试由执行者定；做的话，造不出另一个文件系统的机器上要跳过而不是失败。
- `npm test` 全部通过，测试个数不比改之前少（改之前先运行一次记下个数；改之前就有失败时停下来报告）；`npm run typecheck` 退出码 0。
- 运行前后各看一次 `git worktree list`，应当只有主检出和这个任务自己的 Worktree；`/Volumes` 下不留内存盘。

交回：不提交。做完之后改动留在 Worktree 里，由主会话核对，用 `knit deliver` 在任务分支上提交。

## 完成条件

### Requirement: 交付时移动任务目录失败不卡住，被忽略的任务目录不丢

#### Scenario: 项目和 Worktree 不在同一个文件系统时交付成功

- GIVEN 一个派发过的任务已经完成，它的 Worktree 和主检出不在同一个文件系统
- WHEN 带授权和提交文案运行 `knit deliver`
- THEN 命令成功，任务分支上多了一个提交，里面有代码和归档位置下的任务目录
- AND 主检出里原来的任务目录不在了

#### Scenario: 移动失败时撤回

- GIVEN 一个派发过的任务已经完成，任务目录没法移进它的 Worktree（例如归档的上级目录不可写）
- WHEN 带授权和提交文案运行 `knit deliver`
- THEN 命令失败，输出里有原来的错误
- AND 任务目录在主检出原来的位置，状态是 `done`，`record.json` 里没有记下授权
- AND 任务分支的 `HEAD` 没有变，Worktree 里没有暂存的改动；再运行一次 `knit deliver` 不会因为「已经结束」被拒绝

#### Scenario: 任务目录被 Git 忽略时归档留在主检出

- GIVEN 一个项目的 `.gitignore` 忽略了 `.knit/tasks/`，里面一个派发过的任务已经完成
- WHEN 运行 `knit deliver`，在主检出里合并任务分支，再 `git worktree remove` 它的 Worktree
- THEN 任务分支上的提交里只有代码
- AND 主检出的归档位置下有这个任务的 `task.md`，状态是 `delivered`；`knit task show` 读得出它

## 结果

W2 留下的两个交付缺陷修好了。

1. 项目和 Worktree 不在同一个文件系统时也能交付：重命名报 `EXDEV` 时改成先完整复制、再删除源。交付过程里移动目录失败（不只是 `EXDEV`）和 Git 拒绝提交现在走同一套撤回：任务目录回到主检出原位置，状态回 `done`，授权撤掉，Worktree 里没有暂存的改动、新建的空归档目录和临时副本，任务分支上原来带着的旧任务目录还在。
2. 任务目录被 Git 忽略时，归档留在主检出，任务分支上的提交只有代码；预览和输出里的归档位置写的是主检出。合并并删掉 Worktree 之后任务记录还在。

任务分支上旧任务目录的临时存放位置从系统临时目录改到了 Worktree 里（同一个文件系统）。

改了 5 个文件：`src/cli/deliver.ts`、`src/application/delivery.ts`、新增 `src/infrastructure/directory.ts`、`test/deliver-worktree.test.mjs`、`docs/design/DESIGN.md` 第 8 节。

实现由 `r-e7b9386ea6c9` 做，独立审查 `r-29d66a7820b3` 结论 pass（都用 magpie/group/openai，都在任务的 Worktree 里执行）。审查自己修了一个问题：任务分支上的旧任务目录里有只读子目录时，提交成功了但删临时副本失败，命令报错并留下副本；加了回归测试。
