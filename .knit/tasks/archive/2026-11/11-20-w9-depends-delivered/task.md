## 目标与范围

任务的 Worktree 是从主检出当时的 `HEAD` 建出来的，没有提交、没有合并进主检出的东西，里面都没有。而派发时对依赖的检查现在是：依赖的任务 `done` 或 `delivered` 就放行。这两种情况下新任务都可能拿不到依赖的代码：

- `done`：依赖的任务做完了，但还没有提交，改动在它自己的 Worktree 里（或者是主检出里没提交的改动）。
- `delivered` 但没有合并：提交在依赖的任务分支上，主检出的分支上没有。

新任务就会在缺了依赖的代码上开始做。几个任务可以同时执行之后，这种情况更容易出现。

做完之后：派发时，依赖的任务要已经交付，并且它的提交已经在主检出的当前分支上，否则拒绝派发，提示里说明差在哪一步。

规则：

- 依赖的任务是 `done`（或者更早的状态）：拒绝，提示它还没有交付，交付并合并之后再派发。
- 依赖的任务在主检出里找不到：它可能已经在任务分支上交付、还没有合并（这时任务目录已经移进了它的 Worktree，主检出里看不到），也可能确实不存在。提示要把这两种可能都写出来，不能只说「不存在」；任务分支找得到时，写出分支名和合并的命令。
- 依赖的任务在主检出里是 `delivered`，但它的任务分支 `knit/<任务目录名>` 还在，并且没有合并进主检出的当前分支：拒绝，提示还没有合并。这是任务目录被 Git 忽略的项目会遇到的：归档留在主检出，代码还在分支上。
- 依赖的任务在主检出里是 `delivered`，任务分支不在了，或者已经合并进当前分支：放行。主会话直接做的任务（没有 Worktree 和分支）交付之后属于这一种。
- 依赖的任务被取消了：照现在的做法拒绝。
- 这些检查和别的派发条件一样，在建 Worktree 之前做；被拒绝时不建 Worktree，不留下执行记录。
- 只在派发时检查。主会话直接做的任务不经过派发，不检查。

跟着改的说明：`docs/design/DESIGN.md` 第 7 节里派发前的检查（「依赖的任务都已完成」）。

不能变的行为（都有测试）：

- 没有依赖的任务，派发的行为和现在逐字相同。
- 依赖的任务已经归档的也算在内（现在就是这样）。

不能动的：

- `.knit/standards/`、`.knit/workflow.yaml`、`.knit/config.json`、`.knit/agents/`、`.pi/extensions/knit.ts` 是受保护的或者是生成的副本，改了这次执行会记为失败。
- 交付的代码（`src/application/delivery.ts`、`src/cli/deliver.ts`、`src/infrastructure/directory.ts`）。
- `validation/`、`docs/history/`、`docs/research/` 是历史记录，不改。不加依赖。

## 完成条件

### Requirement: 依赖的任务要已经交付并合并

#### Scenario: 依赖的任务做完了但没有交付

- GIVEN 任务乙依赖任务甲，任务甲是 `done`
- WHEN 派发任务乙
- THEN 派发被拒绝，提示任务甲还没有交付
- AND 没有建任务乙的 Worktree，没有执行记录

#### Scenario: 依赖的任务在任务分支上交付了，还没有合并

- GIVEN 任务乙依赖任务甲，任务甲派发过，已经在它的任务分支上交付，还没有合并
- WHEN 派发任务乙
- THEN 派发被拒绝，提示里说明任务甲可能已经交付、还没有合并，并有任务甲的分支名
- AND 把任务甲的分支合并进主检出的分支之后再派发，派发成功，任务乙的 Worktree 里有任务甲的代码

#### Scenario: 任务目录被 Git 忽略时，依赖的任务交付了但没有合并

- GIVEN 项目的 `.gitignore` 忽略了任务目录；任务乙依赖任务甲，任务甲已经交付，归档在主检出，代码的提交还在任务分支上
- WHEN 派发任务乙
- THEN 派发被拒绝，提示任务甲还没有合并
- AND 合并之后再派发，派发成功

## 结果

做成了：派发前检查依赖的任务，必须已经交付、并且它的提交已经在主检出的当前分支上才放行。「已经合并」的判断是：任务分支不在了，或者它已经是主检出当前 `HEAD` 的祖先。检查在建 Worktree 之前，拒绝时不建 Worktree、不留执行记录。各种拒绝的提示：依赖是 `done` 或更早的状态时提示还没有交付，交付并合并之后再派发；被取消的依赖仍拒绝，提示沿用原文；依赖已交付但任务分支还没合并时给出分支名和 `git merge` 命令；主检出里找不到依赖时提示可能已经在任务分支上交付还没合并、也可能确实不存在，能在某个任务分支里按任务 ID 找到时给出那个分支名和合并命令。主会话直接交付、没有任务分支的依赖放行。任务目录被 Git 忽略、归档留在主检出而代码还在任务分支上的情况同样按分支判断。只改了 `src/application/run-prepare.ts` 一个源文件，`docs/design/DESIGN.md` 第 7 节同步。

三个完成条件都有测试并通过（用真实的派发准备、`task close` 和 `knit deliver` 构造）：依赖是 `done` 时拒绝，不建 Worktree；依赖在任务分支上交付但没合并时拒绝并给出分支和合并命令，合并之后派发成功，新 Worktree 里有依赖的代码；任务目录被忽略的项目同样先拒绝、合并后放行。
