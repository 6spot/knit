# 需求澄清协议：行为、记录与核对

状态：A–F 已确认（2026-11-06），未实施。实现前复核；行为变化按任务输入更新规则处理。

## 1. 适用范围

- 适用：新正式需求、正式任务的需求讨论、既有任务的范围变化、复杂需求拆分。
- 不适用：普通问答、只读调查、非正式小修改。后者仍按现状直接完成，不因本协议增加盘问。

## 2. 协议步骤（主会话行为）

1. **任务选择**：按现行规则先确认是否建任务（D 已确认不变）。澄清不要求先建任务；未建任务时的讨论同样执行本协议。
2. **取证**：先查而不是先问。可查来源：AGENTS／项目规则、`.knit/standards`、`docs/design`、活跃任务、归档任务与 `knit task search` 命中、代码／测试／配置、必要的 Git 历史。
   - 引用具体位置（`path:line`、任务 ID、`commit:<sha>`、`run:<id>`），不写「我记得项目里…」。
   - 归档或旧记录若已被后续决定取代，说明取代关系；相关只证明时间／内容相关，不作为因果结论。
   - 查不到才问；能把问题查清的，不问用户。
3. **缺口扫描**（逐项判断，缺项不必强行制造问题）：
   - 目标与成功判据：解决谁的什么问题、怎样算解决。
   - 范围与非目标：明确不做什么。
   - 验收与证据：可观察结果、靠什么验证。
   - 约束与依赖：必须沿用的既有结构、数据、平台与前置任务。
   - 冲突与合规：与既有规范、设计决定、授权边界、数据保护规则的矛盾。
   - 数据与副作用：写入范围、保护路径、不可逆操作、对外提交。
   - 失败与回滚：出错时的处置与恢复口径。
   - 优先级与时序：与其它任务／分支的先后。
4. **提问**：一轮最多 3 个，一个问题只承载一个决定。每个问题给出：要定的决定、为什么重要、推荐项、选另一个的代价。
   - 推荐项不等于默认值：用户没有答复时不得假装已选择；要按推荐推进就必须落成 `[assumed]` 并标注「（Agent 建议，待确认）」。
   - 用户已明确决定的不再重复建议；证据已解决的问题不再问。
   - 不把「完整方案／实现计划＋是否正确」当作唯一确认；最终摘要只能在全过程最后一轮出现。
5. **回写**：每轮答复后更新 task.md（结论写进目标／完成条件／输入引用），重算未决项；结论取代旧方案时替换而不是并列保留（讨论经过留在会话）。
6. **收敛**：`blocking` 项清零后给最终摘要（目标、范围内外、验收、关键决定、风险与延期、资料状态），等用户明确批准；批准后 `task ready` 冻结输入。

## 3. task.md「待澄清」区段

位置：输入区，建议放在「完成条件」之后、「输入引用」之前。固定标题 `## 待澄清`。

```markdown
## 待澄清

- [blocking] 归档后旧索引是否保留？选项 A 保留（推荐，兼容旧链接）／B 删除（更干净）；差异影响回滚路径。
- [assumed] 批量交付暂不支持逐任务文案（Agent 建议，待确认）。
```

规则：

- 行前缀固定 `- [blocking] ` 与 `- [assumed] `；同一行内写清待决决定与选项，不嵌套列表。
- 已解决项：结论写进目标／完成条件后删除该行，不保留空壳、不写已答问题。
- `assumed` 项在用户确认后同样折入正文并删除；未确认前保留。
- 全部解决时可以整个区段删除；无区段视为没有未决项（兼容现有任务）。
- 中文标题固定，不提供英文别名；解析大小写敏感。

## 4. 核心核对与展示

- `task ready`（`src/application/task-service.ts` 的 `assertReadyStructural`）：解析输入区 `## 待澄清`，存在以 `- [blocking] ` 开头的行时抛 `TaskGuardError("clarify_blocking", ...)`，消息含数量与前 3 条（单条截断到 120 字符）。
- 无区段、只有 `assumed`、或区段为空：放行；不改变现有完成资格与授权规则。
- `knit status` 的 data 增加 `clarify: { blocking, assumed }`（由同一解析函数得出）。桥接在 `blocking > 0` 时注入一行「待澄清: N 项」；`assumed > 0` 时注入「假设待确认: n 项」；都为 0 不显示。
- 不新增 CLI 子命令：主会话照现状直接编辑 task.md 正文。

## 5. 提示词与文档改动

同一套措辞落四处，避免多口径：

- `src/application/templates.ts` 的 `agentsManagedBlock`：把现有「需求澄清门」一行扩为：取证优先（含任务历史与归档）、缺口维度概览、每问四要素与一轮上限、冲突须给替代方案、假设落盘、禁止一次性总确认。
- `assets/templates/pi/extensions/knit.ts` 与 `.pi/extensions/knit.ts`：`SESSION_BEHAVIOR_GUIDANCE` 与无任务分支同步同样要点；桥接新增未决项展示行。
- `docs/design/ROLE-CONTRACT.md`：`start` 行补「先取证再提问、每问带推荐与代价、阻塞项未清不 ready」；第 3 节补「需求澄清属于查明事实，不是用户意图推定」。
- `docs/design/DESIGN.md`：4.2 讨论段改写「需求明确」的判定为「取证后缺口清单为空或用户已裁决」；历史检索段落补「澄清取证可主动检索并须引用，普通对话仍按用户意愿」。
- `docs/design/OPERATIONS.md`：ready 前置补 `clarify_blocking` 的错误语义与放行条件。

## 6. 边界与不纳入

- 不新增 status／stage／独立需求状态机；`blocking` 是 task.md 内的标记，不是任务状态。
- 不统计提问轮数、不强制最小轮数；协议约束的是「先取证、逐项判断、按决定提问」，不是次数。
- 不做自动冲突检测（Knit 不调用模型）；冲突识别属主会话职责，核心只核对 `blocking` 标记。
- 不改变授权、完成验证、提交与归档规则。
- 不清洗旧任务的 discussion 内容；旧任务无区段照常 ready。

## 7. 测试与验收

机械验证：

- `ready`：`blocking` 存在时拒绝且错误码／消息正确；仅 `assumed`、空区段、无区段均放行；行前缀大小写与缩进变体判为忽略。
- `status`：`clarify` 计数正确；无区段时为 0。
- 注入：受管块、两个桥接文件与模板输出逐字一致；无未决项时不出现展示行。
- 既有测试回归：init 模板安装、受管块一致性、bridge 注入断言。

行为验收（另记，不冒充已验证）：真实会话中新需求首轮是否先取证、是否按轮次提问、是否在冲突时给替代方案、是否避免一次性总确认。用户已把真实宿主验收延期，本任务不宣称行为已改善。

## 8. 风险

- 提问变多会拉长讨论；用「证据已答不问、一轮最多 3 个、assumed 可推进」控制成本。
- `blocking` 可能被滥用为拖延；约定它只表示「需用户取舍且影响实施」，其余写进风险或假设。
- task.md 区段与输入摘要绑定：ready 后修改会按 clarify/change 规则使检查 stale，这是预期语义，不额外放宽。
