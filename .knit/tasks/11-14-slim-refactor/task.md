# 重构：收敛为轻量的需求规范与任务管理（主任务）

## 目标与范围

需求未全部确认，不含实施授权。

Knit 要做的是两件事的轻量合并：OpenSpec 式的需求与场景管理和传递，加一个简化的任务管理。现状比这个目标重得多，近期任务反复卡在收口上。

本任务是主任务，只持有三样东西：方向、范围设计（`design.md`）和子任务清单（`plan.md`）。所有改动由子任务完成。

不在本任务内：推送、发布、NPM 发布；新客户端适配（Codex、Claude Code）。

## 用户已定（2026-11-14 至 11-15）

规范：

- 开发规范、交付规范写进仓库并真正落地；频繁重复的错误要有避坑清单。
- `AGENTS.md` 是项目自己的文件，Knit 不靠它承载规范，也不在里面写指向。规范正文放 `.knit/standards/`，由程序在对应环节注入给智能体。
- 项目自己的规范（开发规范、避坑清单）由用户按项目情况总结沉淀，内容参考 opencode 的 AGENTS.md，只取适用条目。
- 通用的规范（任务编写、任务拆分、交付）由 Knit 自带：放进模板，`knit init` 时生成；初始化之后生成一个引导任务，带用户把规范补齐。这件事排在重构切换之后做（子任务 I1）。
- 每份规范自己声明适用的环节，任务可以再点名追加。
- 角色文件是 Knit 的固定模板，写这个角色在 Knit 里怎么工作，和项目规范没有关系。
- 角色文件只放 `.knit/agents/` 一份，不生成到 `.pi/agents/` 或其它客户端的目录；以后接入别的客户端时共用这一份。

任务与交接：

- 任务拆细拆小。已写成规范：`.knit/standards/task-splitting.md`。
- 任务不按谁来做、在哪里做区分写法，都写到执行者只拿到仓库和 `task.md` 就能做完的程度。已写成规范：`.knit/standards/task-writing.md`。
- `task.md` 人和程序都读，内容要方便人读：写需求和完成条件，完成时在末尾写「结果」。只给程序用的内容（编号、摘要、标记、运行引用）放别的文件。
- 「结果」只写总结，不放明细；改动文件清单只记在 `record.json`。
- 同一内容不存两份，能不重复存的就不重复存。
- 不同环节只传各自需要的内容，不全量传。
- 执行者像普通智能体一样读取 `AGENTS.md`。

流程与执行：

- 流程保持可配置，不固定。
- 现在的 `check` 环节改名为 `review`（审查）。
- 审查者可以直接修改：发现问题直接修，减少来回交接。
- 审查不通过的返工上限是 5 轮，并且要给执行者合适的引导，尽量避免走到上限。引导的做法（`design.md` 第 7.1 节）：再次进入一个环节时带上它自己上一次的报告；报告怎么写、返工怎么回应写在角色文件里，程序不校验、不给问题编号、不跨轮比对；到上限时只停下并列出各轮报告的路径和四条可走的路，不生成汇总。
- 执行者的模型和返工上限写在 `workflow.yaml` 里：顶层的 `model` 是缺省，环节可以写自己的；`config.json` 只留交接的字节上限。
- 执行者的过程：第一版只留日志和状态查询，Rex 窗格在核心可用后作为单独子任务加回。
- Worktree 必须有：多个任务并行时各用一个 Worktree，互不影响。切换到小核心时旧实现可以删，之后加回。

交付：

- 一个任务一次提交，只保留“授权后才提交”和提交范围核对。
- 任务完成之后，交付不因为“不规范”被拒绝。

工具与重构方式：

- 桥接工具只保留需要的。
- 重构后要能用 Knit 开发 Knit 自身。
- 重构方式：重写小核心，搬用已验证的代码。
- `design.md` 的范围按 Agent 的建议，包括：去掉规范的候选与审阅回执；去掉 `AGENTS.md` 受管块；审查结论不再防篡改；流程配置出错时拒绝派发而不是降级。

子任务：

- `plan.md` 的清单已确认，分批登记：做到哪一批登记哪一批。
- A 批由主会话在本机直接做。进度见 `plan.md`。
