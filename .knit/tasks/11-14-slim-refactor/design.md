# 小核心范围

本文回答一个问题：Knit 收敛之后保留什么、不做什么、长什么样。用户已于 2026-11-14 确认范围按本文推进；仍是假定的内容见第 15 节。子任务清单见 `plan.md`。本文不含实施授权。调查依据见 `research/findings.md`，用户已定的事项见 `task.md`。

## 1. 要做的事

Knit 管一个项目的开发周期，只做五件事：

1. **任务**：把一件事写成需求和可验证的完成条件，记录做到哪一步、结果如何。
2. **规范**：保存项目的开发规范，按环节交给智能体。
3. **交接**：派执行者做某个环节时，只给它这个环节需要的内容。
4. **交付**：用户授权后，把一个任务的改动提交成一次提交。
5. **接入 Pi**：在主会话里提供少量工具和一小段每轮状态。

四条原则：

- 每个拒绝都给出一条能继续的做法。（来源：`--retry` 与 `--recover-policy` 互相拒绝的死锁）
- 一个事实只存一处。任务的事实在任务目录里，随仓库走，不另存本机数据库。
- 管理本仓库的 Knit 和正在被修改的 Knit 是两份。
- 任务状态没变时，每轮注入的内容逐字不变。

## 2. 目录布局

```
项目根/
  AGENTS.md                 项目自己的文件，Knit 不写入
  .pi/extensions/knit.ts    桥接，knit init 生成
  .knit/
    config.json             执行者模型、返工上限、交接字节上限
    workflow.yaml           流程：有哪些环节、顺序、各环节的工具和角色文件
    standards/              项目规范，一份一个文件，由项目自己写
    agents/                 角色文件，Knit 的模板：implement.md、review.md
    tasks/
      <MM-DD-名称>/
        task.md             需求、状态和结果，人和程序都读它
        record.json         人不需要读的运行记录
        plan.md、design.md  可选
      archive/<YYYY-MM>/    已交付或已取消的任务
    .runtime/               本机运行资料，不入库
      runs/<run-id>/        一次执行的日志和报告原文
```

没有 SQLite 数据库、锁目录和密钥目录。

## 3. 任务资料

每个事实只存一处，两个文件的内容不重复：

- `task.md` 是需求、状态和结果唯一的存放处。人读它，程序也读它（解析状态和完成条件，把需求部分交给执行者）。它的写法要方便人读，所以里面不放编号、摘要、标记这类内容。
- `record.json` 只放人不需要读、程序需要的运行记录。

### 3.1 task.md

```markdown
---
id: k-19c962be9fb8
title: 交接只传需求部分
status: draft
stage: null
verification: self
parent: null
dependsOn: []
priority: P2
createdAt: 2026-11-14T13:36:56Z
---

## 目标与范围

## 完成条件

### Requirement: 名称
#### Scenario: 名称
- WHEN …
- THEN …

## 待澄清

## 相关资料

- `src/application/stage.ts` — 现在拼交接内容的地方
- `.knit/tasks/11-14-slim-refactor/design.md#5-交接` — 本任务依据的设计

## 结果

交接改为只传需求部分，完成条件都已满足，测试全绿。

未验证：超出字节上限时的提示还没在真实模型上看过。
```

- 「结果」之前的正文是**需求部分**，交接只传这一段。
- 「完成条件」沿用现有的 Requirement／Scenario 写法；`independent` 任务必须写场景。
- 「待澄清」沿用 `[blocking]`／`[assumed]`；有 `[blocking]` 时不能确认需求。
- 「相关资料」一行一个路径加理由，可以用 `#标题` 指到文件里的一节。路径一律相对项目根，本任务目录里的文件也写全路径。
- 「结果」在任务完成时写，是一段总结：做成了什么、完成条件是否都满足、怎么验证的；没满足或没验证的条件逐条点名。
- 「结果」里不放明细。改动文件清单记在 `record.json` 里，`knit task show` 和交付预览会列出来，提交之后以 Git 为准。提交号也不写进文件，`knit task show` 从 Git 记录里查。

### 3.2 状态

`status` 和 `stage` 两个字段，代替现在的 `status`、`stage`、`outcome` 三个：

| `status` | 含义 | 怎样进入 |
| --- | --- | --- |
| `draft` | 需求在讨论 | 创建任务 |
| `ready` | 需求已确认，等待开始 | 用户确认后 `task ready` |
| `active` | 正在某个环节，`stage` 写这个环节的 id | 派发第一个环节，或主会话开始做 |
| `done` | 已完成、待交付，「结果」已写 | 见第 8 节「完成」 |
| `delivered` | 已提交并归档 | `deliver` |
| `cancelled` | 已取消 | `task cancel` |

需求确认之后又改了需求部分，任务回到 `draft`，要重新确认。

### 3.3 record.json

入库，不进任何上下文，不重复 `task.md` 里的内容。字段：

| 字段 | 内容 |
| --- | --- |
| `runs` | 每次执行的编号、环节、起止时间、结论、当时需求部分的摘要、改动文件、会话文件位置 |
| `confirmedDigest` | 需求确认时需求部分的摘要；与当前不一致就视为回到 `draft` |
| `changedPaths` | 主会话直接做时登记的改动文件 |
| `authorization` | 交付时用户授权的引用 |

- 每个环节进入过几次从 `runs` 里数，不另存。
- 一次执行结束后，它的事实只记在 `runs` 里；`.runtime/runs/` 下只留日志和报告原文，`runs` 里记的是它的位置。
- 审查结论随仓库走，换机器不需要重建。

## 4. 规范

- 规范分两类。项目自己的规范（开发规范、避坑清单）由项目总结，写的是这个项目怎么开发。通用的规范（任务编写、任务拆分、交付）写的是怎么用 Knit 管任务，由 Knit 自带。两类都和角色文件无关（角色文件见 6.2 节）。
- 第一版的 `knit init` 不预置规范内容。切换之后再把通用规范放进模板，并在初始化后生成一个引导任务带用户补齐规范（子任务 I1，见第 11 节「延后」）。
- 规范是 `.knit/standards/` 下的 Markdown，一份一个文件，主会话用普通的写文件工具直接写。
- 每份规范在开头声明适用的环节：

  ```markdown
  ---
  title: 开发规范
  stages: [implement, review]
  ---
  ```

- 规范文件会原样进入智能体的上下文，所以只写智能体做事时要用到的内容。来源、日期、编号、制定经过不写进文件，写在提交说明里。开头声明了 `title`，正文不再加一行重复的标题。
- 环节名用 `workflow.yaml` 里的 id，另有两个固定的：`discuss`（主会话讨论需求）和 `deliver`（主会话收尾）。
- 没有声明环节的规范不注入；声明了流程里没有的环节，`knit standards list` 会标出来。
- 任务可以在「相关资料」里点名追加某份规范。
- 同一条规则只写一处：项目通用说明留在 `AGENTS.md`，需要按环节给的规范写在 `.knit/standards/`。
- 不确定是否该成为长期规则的，当场问用户；不设候选文件和审阅回执。

## 5. 交接

### 5.1 给谁什么

| 接收方 | 收到的内容 |
| --- | --- |
| 主会话，每轮 | 当前任务的标题、状态、下一步；适用当前环节的规范 |
| 环节执行者 | 需求部分；「相关资料」点名的文件或章节；`plan.md`（如有）；上一个环节的报告（改动文件、自述的验证）；适用本环节的规范；本环节的角色文件 |

- 不传：「结果」、`record.json`、其它任务、没有点名的 `design.md` 和研究资料。
- 分块的单位有两级：任务本身按拆分规范保持小；大文档用 `#标题` 只取一节。
- 字节上限的初始值：单个文件 16KB，一次交接合计 64KB。超出的只给路径和一句说明，由执行者自己读。受上限约束的是点名的资料、`plan.md` 和上一个环节的报告；角色文件、规范和需求部分任何时候都全文给，只计入合计。
- 执行者像普通智能体一样读取项目的 `AGENTS.md`（去掉现在的 `--no-context-files`），不加载项目扩展和技能（沿用现状）。
- 主会话直接做某个环节时，每轮收到的是适用该环节的规范。

### 5.2 放在哪里

- 执行者：角色文件和规范放在系统提示里；需求部分、点名的资料、`plan.md` 和上一环节的报告放在第一条消息里。
- 主会话：规范放在桥接维护的那一段系统提示里。环节不变时内容逐字不变，规范按路径排序。
- 规范不写进角色文件：角色文件是 Knit 的模板，升级时会重新生成。

放系统提示的理由：Pi 压缩会话时保留系统提示，把旧消息压成摘要。本机记录里一次执行中位 13 分钟、最长 141 分钟，规范放在消息里可能被压掉。

另外两个工具的做法（依据见 `research/findings.md` 第 9 节）：

| | 执行者 | 主会话 |
| --- | --- | --- |
| Trellis | 拼进派给子 Agent 的那条任务消息：角色说明、规范正文、需求、任务 | 在 Pi 上放进系统提示；在走 hook 的客户端上只给精简状态 |
| OpenSpec | 不区分执行者 | 智能体调用 `openspec instructions`，规则作为命令输出回到对话里 |

两者都不把规范写进角色文件。

## 6. 流程与角色文件

### 6.1 流程

流程可以配置，文件是 `.knit/workflow.yaml`，格式沿用现在的：

```yaml
version: 1
stages:
  - id: implement
    name: 实现
    prompt: .knit/agents/implement.md
    tools: [read, write, exec]
  - id: review
    name: 审查
    prompt: .knit/agents/review.md
    tools: [read, write, exec]
    report:
      verdict: [pass, changes_requested, blocked]
    onVerdict:
      changes_requested: implement
      blocked: review
```

- 两头固定：讨论（需求确认之前）和收尾（交付），都在主会话里。中间有哪些环节、什么顺序，由这个文件决定。默认是实现、审查两个。现在叫 `check` 的环节改名为 `review`。
- 每个环节可以写：`id`、`name`、`description`、`prompt`（角色文件）、`tools`（能力：`read`、`write`、`exec`、`external`、`network`）、`report`（额外的报告字段）、`onVerdict`（按结论跳到哪个环节）、`maxVisits`（最多进入几次）。
- 报告里带 `verdict` 的环节算审查环节。
- 文件手工改，`knit workflow validate` 校验并给出行号。不保留 `add`／`remove`／`move`／`set-*` 这些修改子命令和 `knit_workflow` 工具。
- 文件有错时，拒绝派发新的执行并指出哪一行；不再像现在这样降级成没有环节的流程。

### 6.2 角色文件

- 角色文件是 Knit 的模板，随 Knit 发布。默认两份：`implement.md`（实现）和 `review.md`（审查）。内容是这个角色在 Knit 里怎么工作：职责、做事的顺序、报告怎么写、返工时怎么回应上一轮的问题。
- 它和项目规范无关。项目自己的要求写在 `.knit/standards/`，不写进角色文件。Knit 升级后角色文件按模板重新生成，覆盖前备份。
- 项目在流程里加了自己的环节时，自己写那个环节的角色文件。
- 对所有环节都成立的硬规则由程序给，不写在角色文件里：不能提交、不能改受保护的路径、报告的格式。
- 位置：只有 `.knit/agents/` 这一份，由 `workflow.yaml` 的 `prompt` 指向。`knit init` 不往 `.pi/agents/` 或其它客户端的目录里生成：以后接入别的客户端时，各客户端共用这一份，由 Knit 拼进交接内容。
- Trellis 的做法相同：角色文件由初始化生成，规范目录初始化时只给待填写的骨架。

## 7. 执行

- 第一版只在主检出执行，同一时间只跑一个执行者。Worktree 并行之后加回，见第 11 节。
- 执行者是后台的 `pi --mode rpc` 进程。派发后工具立即返回，结束时桥接通知主会话。
- 执行者能用哪些工具，由环节的 `tools` 决定。
- 结束时：读取报告；对比开始前后的工作区得出改动文件，写入 `record.json`；推进任务状态。改动文件以对比结果为准，不依赖执行者自报。
- 执行者不能提交：结束时 HEAD 变了，本次执行记为失败。
- 执行者不能改 `.knit/standards/`、`.knit/workflow.yaml`、`.knit/config.json` 和流程用到的角色文件：改了，本次执行记为失败。
- 报告读不出来时，要求执行者补报一次；仍然读不出就记为失败，保留原文。
- 失败不自动重试。重新派发是一个新会话，带上一次的报告摘要。
- 第一版看执行过程靠日志文件和 `knit run status`。Rex 窗格在核心可用之后作为单独的子任务加回。

### 7.1 返工

审查者发现问题直接修，修完重新验证，不为小问题来回交接。结论有三种：

| 结论 | 含义 | 之后 |
| --- | --- | --- |
| `pass` | 修完之后完成条件都满足 | 任务完成 |
| `changes_requested` | 有不该由审查者修的问题：要改设计、超出任务范围，或改动量相当于重做 | 回到实现环节，算一轮返工 |
| `blocked` | 无法验证，例如缺环境 | 交回主会话，不算返工轮次 |

返工上限 5 轮，`config.json` 可改。

审查者改过的文件记在 `record.json` 里这次审查的名下，交付预览里单独标出。这些修改没有第二个人再看；Trellis 的审查者也是直接修。

让返工少发生、发生了能收敛（以下四条是 Agent 的草案，用户还没定，登记 E 批之前讨论）：

- 审查报告里每个问题写四项：位置、哪里不对、对应哪条完成条件、怎样算修好；已经修掉的另写改了什么。
- 返工时执行者收到的第一项内容是没修掉的问题，返工报告逐条回应。
- 再次审查时，审查者拿到上一轮的问题清单，先逐条判定是否修好，再看有没有新问题。
- 同一个问题第二次没修好时不停止，但换做法：下一轮返工要求先写出原因再动手，并附上前两次的改法。

到上限时停下，交给主会话一份汇总：每轮的问题和改法、仍未解决的问题，以及四条可以走的路：

1. 主会话直接修。
2. 拆成更小的任务。
3. 需求本身有问题就改需求。
4. 用户决定带理由接受，理由写进「结果」。

任务完成时如果返工过，主会话问用户要不要把原因记进避坑清单或规范。

## 8. 完成与交付

任务完成之后，交付不再评判它做得规不规范。质量的门在「完成」，交付只管提交。

### 8.1 完成

- `self`／`none` 任务：主会话 `task close` 并写「结果」。
- `independent` 任务：审查结论 `pass` 后完成。用户明确要求时可以带理由直接完成，理由写进「结果」。

### 8.2 交付

只有三种情况不提交：

| 情况 | 处理 |
| --- | --- |
| 任务还不是 `done` | 提示先完成任务 |
| 没有用户授权 | 提示需要授权（沿用现在的授权引用） |
| Git 自己拒绝提交，例如 hook 失败 | 撤回归档移动，原样报告 Git 的错误 |

其它情况只在预览里提示，不拦：

- 有未验证的完成条件。
- 提交里的文件和记录的改动不一致。
- 子任务还没结束。
- 工作区里有不属于本任务的改动（这些不会被提交）。

提交文案只要求非空，不做格式检查；格式写在交付规范里。提交在当前分支，不核对分支。

步骤：

1. 预览：列出要提交的文件（审查者改过的单独标出）、提交文案和上面的提示。文件是各次执行记录的改动、主会话登记的改动，加上任务目录。
2. 把任务目录移到 `archive/<YYYY-MM>/`。
3. 只暂存这些路径，提交一次；其它未提交的改动不动。提交说明带 `Knit-Task: <id>`。
4. 核对提交里的文件与预览一致；不一致就报告差异，提交保留。

没有可恢复的中间状态。主任务没有代码，交付只归档它的目录。

## 9. 命令与工具

命令行：

```
knit init
knit task new | use | ready | close | cancel | list | show | search
knit run start | status | cancel
knit deliver <任务> [--preview]
knit standards list
knit workflow show | validate
```

桥接工具从 9 个减到 3 个：

| 工具 | 动作 |
| --- | --- |
| `knit_task` | new、use、ready、close、list |
| `knit_run` | start（派发任务当前的环节）、status、cancel |
| `knit_deliver` | 预览、交付 |

- 工具的声明不随流程配置变化。
- `task.md` 正文、`plan.md`、`design.md`、规范文件和 `workflow.yaml` 都是普通文本，主会话用普通的读写工具直接改；格式在 `task ready`、`standards list` 和 `workflow validate` 时校验。检索用命令行。
- 每轮注入：任务标题、状态、下一步，加上第 5 节说的规范。没有选中任务时只有一行提示。当前任务的选择沿用现在的做法，写在 Pi 会话记录里。

## 10. 用 Knit 开发 Knit

1. 管理本仓库的是安装版（`npm run pack:install` 装到全局），桥接调用安装版。工作区的 `dist` 可以随意重建。
2. 升级安装版是显式的一步，在一个任务交付之后做。
3. 模板只有一份来源：`assets/templates/`。本仓库的 `.knit/agents/`、`.knit/workflow.yaml` 和 `.pi/extensions/knit.ts` 是安装版 `knit init` 生成的副本。执行者改模板，不改副本；升级安装版后重新生成。
4. 测试只在临时目录里建夹具，不读本仓库的 `.knit/`、`.pi/` 和 `AGENTS.md`。
5. 交付不依赖 `AGENTS.md` 或任何规范文件的摘要。
6. `knit init --force` 只重新生成桥接、`workflow.yaml` 和角色文件，覆盖前备份；`config.json`、`standards/` 和 `tasks/` 任何时候都不覆盖。

## 11. 不做与延后

延后，不在第一版，之后作为单独的子任务加回：

## 14. 重写怎么进行

- 在新目录（暂定 `next/`）里写小核心和它的测试，搬用第 12 节的代码。旧代码在此期间不动。
- 四份规范先写。旧 Knit 会把 `.knit/standards/` 下的文件全文交给执行者，所以它们从第一个代码任务起就对执行者生效；旧 Knit 不按环节挑选，每份都要短。
- `AGENTS.md` 在切换时清理。旧 Knit 拿它的内容算交付策略版本，切换前改它会让进行中的交付失效。
- 期间用安装版的旧 Knit 管理这些子任务。
- 小核心能完成一个任务的全过程（创建、确认、执行、审查、交付）之后切换：重新安装，重新生成桥接和模板，删除旧代码和旧测试。
- 切换时，没结束的任务手工转成新格式；已归档的 93 个任务保持旧格式不动。
- 已知代价：macOS 验收证据作废；现有 734 个测试大部分不搬；已经修过的问题（路径别名、进程清理时序等）可能重犯。
