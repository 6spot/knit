# 057 任务资料与业务产物分开提交及多任务逐项收尾

- 执行角色：Git 交付／任务归属 Agent。
- 来源：2026-11-03 用户要求参考 Trellis，Knit 任务文件与开发产生的文件分开提交；支持多个已完成任务最后一起处理，但每个任务保留自己的提交记录，不合成整批大提交。
- 实际依赖：054 固定来源研究、现有 scope／snapshot／Git 交付实现、056 的已完成未提交语义；Trellis 文件归属与提交行为可先独立调研。
- 唯一状态入口：[TASKS.md](../TASKS.md)。

## 用户已确认的行为

1. Knit 创建／维护的任务资料与实际开发产生的业务文件分开提交，不能因为同属一个任务就混进一次提交。研究报告等产物的归属按实际职责明确，不仅依据文件扩展名或是否位于任务目录猜测；有歧义时保留可审阅分类。
2. 支持单个任务收尾，也支持用户一次要求处理多个已完成未提交的任务。批量处理仍逐任务形成可追溯的提交记录，任务资料与业务产物继续分开，不用一次全仓提交替代。
3. 完成和提交互不冒充；建任务、执行、复核、标记完成均不自动授予提交授权。提交按用户明确授权的任务与范围进行，推送／发布仍需各自授权。

## Trellis 研究与设计要求

- 使用 054 的固定 Trellis 基线，实际核对任务 scope／changed files／记录脚本／提交入口和归档行为，输出固定链接及可复核证据。用户关于 Trellis 文件记录机制的描述是研究线索，不能未经核对宣称已有能力或隔离保证。
- 盘点 Knit 当前任务 scope、执行前后快照、结果接收、交付快照、Git pathspec／index 和收尾记录；区分“涉及过的文件”“获准成果”“当前 diff”“最终进入提交的内容”。
- 定义业务产物与任务资料的归属、提交顺序、完成后资料更新、归档移动及重试规则。检查 `.knit/` 的其它受管／共享资料，不能将整个目录都当成当前任务资料。
- 多任务同文件、同一段改动、任务开始前已有修改、完成后人工修改、部分暂存、重命名／删除、新文件及混合资料／产物必须可审阅。仅记录文件路径不能证明能按任务分离同文件 diff；不能分离时停止该项并说明具体冲突，不把其它任务改动归入当前提交。
- 保留已完成任务到提交内容的可核对来源；具体字段和快照策略以证据及最小业务需求确定，不强制引入额外持久化层。
- Git hooks、部分成功、提交回执丢失、批次中途停止与重试按现有恢复／锁规则核对，不能重复提交已完成项、覆盖用户 index 或丢失未提交改动。

## 实施与完成条件

- 同步 DESIGN、ARCHITECTURE、STATES、OPERATIONS、任务／交付 schema、CLI／桥接、角色提示词和升级规则；输出可审阅的单任务与多任务提交计划及明确授权来源。
- 在隔离 Git 仓库验证：单任务资料与业务产物分离；多个已完成任务逐项提交；无业务改动／仅资料变动；跨任务同文件与冲突；已有暂存内容保护；中途失败和重试。
- 核对每次提交的实际 diff 与记录来源一致，既不混任务也不漏记；共享改动无法可靠归属时给出明确处理入口，不自动压成一批提交。
- 未授权时只生成计划与只读预检结果；用户授权批量收尾后在授权范围内继续，不逐个任务重复索要相同授权。
- 现有基于完整分支和授权来源的交付约束须审视并与新行为一致，不能只在提示词中承诺“按任务提交”。
- 运行相称静态检查和隔离回归；真机／真实模型验收按用户要求暂缓。不在本任务测试中提交当前仓库或改写真实项目历史。
