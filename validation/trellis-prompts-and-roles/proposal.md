# 建议方案与文案草案（054）

本文件是**建议**，不是已生效规则。标注约定：

- **【已实现】**：当前 Knit 源码／模板已有行为。
- **【已确认规则】**：DESIGN／STATES／OPERATIONS 已定义的产品规则。
- **【建议】**：本任务提出、尚待实施和验证的改动。
- **【待决定】**：需要用户选择后才能改变的业务规则，见 [B006](../../BLOCKERS.md)、[B007](../../BLOCKERS.md)。

## 1. 分流原则

判定看**目标、副作用与是否作为正式成果跟踪**，不看读取了多少文件、调用了多少工具或是否使用子 Agent：

- 不修改项目、不产生需长期跟踪的成果、不需要正式复核 → 主会话直接完成。
- 只在当前会话改一处、自检即可 → 非正式小修改。
- 需要正式任务身份、阶段记录、独立检查或 Git 交付 → 正式任务。
- 只读调查即使临时委派子 Agent，也不因此自动变成正式任务；委派不是 Knit 阶段。

## 3. 角色职责表【建议】

| 职责 | 输入 | 允许的副作用 | 产出与证据 | 停止／交接 | 是否改变 Task phase |
| --- | --- | --- | --- | --- | --- |

| advisory（现有，任务内建议） | taskId + discuss／deliver 模式；只读上下文 | 只读；不修改项目；不推进业务 | 建议、备选、风险、`ready` 摘要 | 返回建议；不是完成证据 | 否 |
| 非正式 check（`run check --scope`） | 显式路径／范围、规范、实际文件 | 只读；不建 Task／binding；不提交 | verdict、coverage、findings、unverified | 返回结论；不赋交付资格 | 否 |

| check（正式） | 冻结需求、scope、实际文件、验证入口、上一实施报告 | 只读；不修改成果；不提交 | pass／changes_requested／blocked、coverage、findings、unverified | pass → deliver；changes_requested → implement；blocked 留 check | 由核心按结论转移 |
| deliver（确定性收尾） | 有效检查、任务范围、分支、用户授权 | 提交、封存、归档；不启动 worker | 工作提交、归档提交、操作记录、授权来源 | 完成或 needs_attention；不伪造回执 | closed／completed（或取消／替代） |

正式任务的完成判断不由实现者自报：implement 只交结果与验证，check 给 verdict 和 coverage，主会话在接收后按证据向用户汇报；deliver 的完成仍由核心核对检查资格与回执。

### 3.1 是否需要新增 research 角色

**建议不新增。** 理由：

1. Trellis 的 research 角色仍要求活动任务（Pi 角色）或至少把结果写回任务材料；它不是“无任务回答”的入口。
2. 新增 role 必须绑定 run／Session／phase／tool policy／context plan；为一次性调查增加整套状态不划算。
3. 正式研究报告需要写入、验证和交付，现有 implement＋check 已覆盖；只读调查由主会话覆盖。
4. `advisory` 已存在但只适合任务内第二意见；把它改造成研究闭环会改变“不推进业务”的定位。
5. 如果未来反复出现“任务内只读调查需要隔离上下文”，可在现有 advisory 上补 `.knit/agents/advisory.md`，而不是新增 phase。

**可选低风险改动**：补 `.knit/agents/advisory.md`，让现有 advisory 明确“只读、不推进、建议不是完成证据”。这不是新角色，只是补齐缺失的模板文件。

### 3.2 角色选择顺序

1. **无正式任务 + 只读调查**：主会话直接读取／检索／回答；宿主只读子 Agent 只是临时委派，不产生 Knit 角色或阶段。
2. **无正式任务 + 小修改**：主会话修改并自检；用户明确要求独立复核时用非正式 `run check --scope`，不建绑定。
3. **正式任务**：主会话选择／更新任务输入，然后 implement → check → deliver；advisory 只在 discuss／deliver 作为第二意见，不能替代实施或检查。
4. **已有正式任务 + 辅助调查**：主会话读取或临时只读委派；需要保留时写 `research/`；不派 implement／check，不推进 phase。
5. **正式研究报告**：implement 写项目内报告，check 核对来源／覆盖／结论；没有独立 research 角色，也不把任务 `research/` 当交付物。

任务创建授权不等于实施授权；用户确认实施后，正式工作流包含 implement 与 check。授权不自动扩展到 commit、push、发布或迁移；交付仍按 `knit_deliver` 的分支与授权来源核对。

## 6. 产品决定与选项

### B006：正式只读调研能否跳过 check／免 Git 完成

| 选项 | 做法 | 代价 | 评价 |
| --- | --- | --- | --- |
| **A（推荐）** | 不新增阶段／角色。一次性调查直接回答；正式研究报告仍走 implement → check → deliver；不想 check／commit 就不建正式任务。 | 只改提示词、注入与文档；正式报告仍需检查与授权提交。 | 保留独立性、状态机和授权边界；解决真实案例的入口问题。 |
| B1 | 允许“正式研究报告”在 implement 后跳过 check，但仍按 deliver 提交。 | 需要新增“报告类任务”判定／标记；削弱检查对报告的覆盖；要定义谁保证来源与结论质量。 | 只有在报告检查确实无价值且反复出现时再考虑。 |
| B2 | 允许正式调研在无 Git 提交下标记 completed／归档。 | 需要新的完成结果、归档路径、交付守卫和审计；与“正常完成须有效检查”冲突。 | 不建议首版采用；会把“业务完成”和“Git 收尾”关系复杂化。 |
| C | 新增 research phase／role，产出报告后直接 deliver／close。 | 新 phase、role、tool policy、context plan、acceptance、状态转移、模板升级和测试。 | 不建议；Trellis 的 research 仍依附任务，也未免检查。 |
| D | 用 advisory 作为研究闭环。 | advisory 需 taskId；报告只作为 run 结果，不写任务输入／业务资料，也不推进 phase。 | 不可行；会把“建议”误当“完成”。 |

**免 Git 的合法路径**（按现状）：

1. 不建正式任务，直接回答或写会话内草稿。
2. 需要正式报告文件时，建正式任务并走 check；交付是否提交由用户授权，未授权则停在 deliver，不能伪称完成。
3. 放弃正式跟踪时，按 `task close --outcome cancelled/superseded` 结束业务；这不等于完成，也不等于已归档。
4. `task close --outcome completed` 不是正式调研的跳过路径；它的守卫问题见 B007。

### B007：`task close --outcome completed` 的检查资格守卫

当前 `TaskService.close` 只核对 `runsSettled` 和领域状态，`onComplete` 也没有核对 `lastCheckRunId`；因此从 implement／check 直接 close completed 在代码上可行，但违反 STATES L47“正常完成须有效检查及主 Agent 完成判断”。

- **建议**：另立实现任务补守卫（仅允许有效检查后的 deliver 完成，或提供显式、可审计的 override），不要把该路径写进研究分流规则。
- **本任务不修**：不改变状态机，不把缺陷当产品能力。
- **若用户决定 B2**：也不能复用这个缺口，必须显式设计完成结果和归档语义。
