## 完成与汇报

- 收尾由主会话自己做，不派执行者。
- 接收执行者的结果后，先对照任务的完成条件核对实际成果，再汇报。
- 汇报写三样：实际改了什么，运行过哪些验证和结果，还没验证或没实现的。
- 没运行的验证不写成通过；数字照实际输出写。
- 例行的做法不写进汇报：工作区是干净的、没有动别的文件、本地和远端一致这一类。用户问到，或者它影响使用、验收、恢复时才写。
- 任务返工过（审查结论是 `changes_requested`，回到过实现环节）时，汇报返工原因，问用户要不要记录。写入避坑清单前，用 `knit standards pitfalls <环节>` 查经验适用的分区。已有同一经验就补充原条目，跨所有环节适用的经验归 `通用`。
- 任务完成不等于可以提交。完成、提交、归档是三件事，后两件各自要有授权。

## 授权

- 提交前要有用户的明确授权。已经有明确授权的不重复确认。
- 授权只对它说到的操作有效。同意提交不包含推送、发布和部署。
- 提交文案由主会话在交付时写好，直接提交，不用先给用户看。

## 提交范围

- 只提交本任务的文件，用明确的路径暂存，不用 `git add -A` 或 `git add .`。
- 工作区里不属于本任务的改动不动：不暂存，不还原。
- 提交后用 `git show --stat` 核对提交里的文件和预期一致，再汇报；以 Git 的实际结果为准，不以工具的返回为准。

## 派发过的任务

- 派发过的任务，主会话要补改动时在它的 Worktree 里改，不在主检出里改。
- 项目配置 `.knit/config.json` 的 `worktree.autoMerge` 为 `true` 时，`knit deliver` 交付成功后在主检出里合并进当前分支，再删除 Worktree 和任务分支；主会话看交付输出，不重复合并或清理。
- 开关关着（缺省 `false`）时，交付之后提交仍在任务分支上，还没有合并进主检出的分支。主会话接着在主检出里运行 `git merge --no-edit knit/<任务目录名>`；合并成功后运行 `git worktree remove <位置>`，再运行 `git branch -d knit/<任务目录名>` 清理。位置和分支以交付输出为准。
- 一次交付的授权同时覆盖合并和清理，不用再问用户；不包含推送、发布和部署。
- 合并失败时，任务仍然是 `delivered`，提交、Worktree 和分支都保留。开关开着时由 `knit deliver` 在进入合并状态后运行 `git merge --abort`；关着时由主会话做。主会话把 Git 的错误原样给用户看并问他怎么处理，不自己解决冲突，不强行合并，不用 `--force` 删 Worktree，不用 `git branch -D`。
- 自动合并失败或清理被拒绝时，`knit deliver` 的退出码仍是 0：已经交付，没做成的是后续步骤。主会话必须看输出里的合并和清理结果，不能只看退出码。
- 交付后的清理被 Git 拒绝时保留 Worktree 或分支，把错误和位置报告给用户，不强制删除。
- 取消派发过的任务（`knit task cancel`）会强制删除它的 Worktree 和任务分支，里面没提交的改动找不回来。取消由用户决定，主会话不自己取消。

## 提交文案

- 首行写这次改动的结果，不能只有任务编号。
- `Task: <任务 ID>` 一行必须有。
- 不写以 `Knit-` 开头的行，这类行由 Knit 自己加。

## 失败

- 同一操作因同一原因失败两次就停下，把命令和错误原样报告给用户，不再重试。
