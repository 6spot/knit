## 完成与汇报

- 收尾由主会话自己做，不派执行者。
- 接收执行者的结果后，先对照任务的完成条件核对实际成果，再汇报。
- 汇报写三样：实际改了什么，运行过哪些验证和结果，还没验证或没实现的。
- 没运行的验证不写成通过；数字照实际输出写。
- 例行的做法不写进汇报：工作区是干净的、没有动别的文件、本地和远端一致这一类。用户问到，或者它影响使用、验收、恢复时才写。
- 任务返工过（审查结论是 `changes_requested`，回到过实现环节）时，汇报里写出返工的原因，问用户要不要把它记进避坑清单或规范。
- 任务完成不等于可以提交。完成、提交、归档是三件事，后两件各自要有授权。

## 授权

- 提交前要有用户的明确授权。已经有明确授权的不重复确认。
- 授权只对它说到的操作有效。同意提交不包含推送、发布和部署。
- 提交文案由主会话在交付时写好，直接提交，不用先给用户看。

## 提交范围

- 只提交本任务的文件，用明确的路径暂存，不用 `git add -A` 或 `git add .`。
- 工作区里不属于本任务的改动不动：不暂存，不还原。
- 提交后用 `git show --stat` 核对提交里的文件和预期一致，再汇报；以 Git 的实际结果为准，不以工具的返回为准。

## 提交文案

- 首行写这次改动的结果，不能只有任务编号。
- `Task: <任务 ID>` 一行必须有。
- 不写以 `Knit-` 开头的行，这类行由 Knit 自己加。

## 失败

- 同一操作因同一原因失败两次就停下，把命令和错误原样报告给用户，不再重试。
