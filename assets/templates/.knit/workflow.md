# 四环节工作流

Knit 以讨论 → 实施 → 检查 → 交付四个环节推进任务。本文件是项目资料：可按项目实际调整职责描述，Knit 只补缺不覆盖。

## 主会话：识别请求与任务入口

主 Agent 按上下文把每轮请求归入一类处理，不按关键词机械建任务：

- **普通讨论与问答**：直接回答；涉及任务状态时用只读查询展示，不建任务。
- **非正式小修改**：当前会话澄清、修改、自检、汇报；不建任务、不提交。范围扩大或需长期跟踪时提议正式任务。
- **新正式需求**：先以简洁提议说明目标与拟建任务，征得用户同意后 `task new`；用户已明确要求或已有持续授权时直接创建。授权不覆盖提交／发布。
- **继续已有任务**：读取当前任务资料与记录接续；已完成授权事项不重复询问。
- **已有任务补充／范围变化**：用 `task update --kind clarify/change` 更新；活动运行期间保存为草案，待运行结束后应用。不默认另建新任务绕过旧任务状态。

## 讨论 discuss

明确目标、完成条件与范围。从任务资料和工程代码取事实，已有资料能回答的不重复询问；只就需用户取舍的事项提问，未决定不自行选择。结论写入 task.md 输入区；有待确认事项先澄清，不带着未决问题进入实施。

复杂任务（多模块、迁移、协议、跨会话接续）在讨论确认时创建任务目录内的 `plan.md`：写清步骤产出、真实依赖、受影响结构／接口、验证方式与风险处理，保留未完成步骤标记。有重要技术取舍时写 `design.md` 保留备选对比与理由；调查材料多时放 `research/` 并在 task.md 输入引用中留入口摘要。简单任务只在 task.md 说明即可，不堆空文件。

## 实施 implement

按任务目标与规范完成代码改动，复杂任务按当前 plan.md 的未完成步骤推进。开始前核对输入已冻结；实施在快照就绪后进行。遇到需用户决定的事项记录后暂停，不自行取舍。

实施中勾选计划步骤、追加证据是进度更新，不改变需求；要改动目标、条件或验收，必须走 `task update --kind clarify/change`，不能只改计划文件。

## 检查 check

独立检查实施结果：核对 task.md 完成条件与实际成果，运行验证、记录发现。检查按冻结时的需求与资料版本评价，不按计划勾选判定成功；检查不修改实施内容，发现问题回到实施环节修复。

## 交付 deliver

整理提交与归档。交付前核对：检查结论有效、无待应用输入、提交范围限定在本次改动。归档后任务目录移入 archive/。
