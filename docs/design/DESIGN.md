# Knit 设计

本文是 Knit 现行的设计：保留什么、不做什么、长什么样。改设计时直接改对应的章节。

## 1. 要做的事

Knit 管一个项目的开发周期，只做五件事：

1. **任务**：把一件事写成需求和可验证的完成条件，记录做到哪一步、结果如何。
2. **规范**：保存项目的开发规范，按环节交给智能体。
3. **交接**：派执行者做某个环节时，只给它这个环节需要的内容。
4. **交付**：用户授权后，把任务归档；项目在 Git 仓库里时，再把这个任务的改动提交成一次提交。Git 不是必须的。
5. 在 Pi、Antigravity 和 WorkBuddy 的**主会话**中提供项目上下文和 Knit 命令入口。

四条原则：

- 每个拒绝都给出一条能继续的做法。
- 一个事实只存一处。任务的事实在任务目录里，随仓库走，不另存本机数据库。
- 管理本仓库的 Knit 和正在被修改的 Knit 是两份。
- 任务状态没变时，每轮注入的内容逐字不变。

## 2. 目录布局

```
项目根/
  AGENTS.md                 项目自己的文件，Knit 不写入
  .pi/extensions/knit.ts    knit init --pi 生成的 Pi 桥接
  .workbuddy/               knit init --workbuddy 生成的桌面主会话桥接
    settings.json           项目级钩子声明
    knit-hook.sh            为钩子准备 PATH 并启动安装版 knit
  .agents/plugins/knit/     knit init --agy 生成的 Antigravity 主会话插件
    plugin.json             插件名 knit
    hooks.json              主会话钩子
    rules/AGENTS.md         主会话使用 Knit 命令的说明
  .knit/
    config.json             交接字节上限、Worktree 设置与运行目录保留天数
    workflow.yaml           流程：有哪些环节、顺序，各环节的模型、工具和角色文件，返工上限
    standards/              项目规范，一份一个文件，由项目自己写
    agents/                 角色文件，Knit 的模板：implement.md、review.md
    tasks/
      <MM-DD-名称>/
        task.md             需求、状态和结果，人和程序都读它
        record.json         人不需要读的运行记录
        plan.md、design.md  可选
      archive/<YYYY-MM>/    已交付或已取消的任务
    .runtime/               本机运行资料，不入库
      runs/<run-id>/        一次执行的交接内容、日志、报告原文和会话记录

Knit 用户目录/              缺省为用户主目录下的 .knit，可用 KNIT_HOME 替换
  worktrees/
    <项目目录名>-<摘要>/
      <任务目录名>/         执行者的 Git Worktree，分支 knit/<任务目录名>
```

Worktree 的项目目录名来自主检出的真实路径（解析符号链接之后），摘要是该路径的 SHA-256 前 8 位；任务目录名是 `.knit/tasks/` 下的目录名。位置和分支都按这两样计算，不写进任务记录。Worktree 放在项目之外，避免执行者同时加载主检出与 Worktree 的两份上级 `AGENTS.md`。用户主目录用 `os.homedir()` 取得，文件路径用 `node:path` 拼接。`KNIT_HOME` 是相对路径时，以主检出的真实路径为基准解析；Worktree 的位置始终使用绝对路径。

交付之前，任务资料和运行资料只有主检出里的一份；派发过的任务交付时，任务目录移到它的 Worktree 里归档，运行资料仍在主检出。主会话直接做的任务不建 Worktree。

任务状态保存在任务目录的 `task.md` 和 `record.json`。多个 Knit 进程同时写入项目避坑清单时，通过 `.knit/.runtime/locks/pitfalls.lock` 的 SQLite 文件锁依次写入。进程退出时锁会释放。

`config.json` 的字段都可以不写，不认识的字段报错：

```json
{
  "handoff": { "fileBytes": 16384, "totalBytes": 65536 },
  "runtime": { "retainDays": 14 },
  "worktree": { "setup": ["npm ci"], "autoMerge": true }
}
```

`runtime.retainDays` 指定交付成功后保留已归档运行目录的天数。字段缺省时保留 14 天，正整数按连续的 24 小时计算，`0` 或 `null` 关闭自动清理。负数、小数和其他类型会导致配置校验报错。清理范围见第 8.2 节。

`worktree.autoMerge` 是布尔值，缺省 `false`。开着时，派发过的任务交付成功后在主检出里合并进当前分支，并删除任务 Worktree 和分支；没有 Worktree 的任务和不在 Git 仓库里的项目不变。一次交付的授权同时覆盖合并和清理，规则见第 8 节。默认配置模板不带这个开关，由项目自己打开。

`worktree.setup` 是可选的命令数组，数组中的每条命令必须是非空、非纯空白的字符串；空数组等同于不运行。写错时指出 `.knit/config.json` 的字段问题。默认配置模板不带准备命令，项目自己决定要运行什么；派发时的运行规则见第 7 节。

执行者的模型和返工上限是流程的设置，写在 `workflow.yaml` 里（第 6.1 节），不在这个文件里。

## 3. 任务资料

每个事实只存一处，两个文件的内容不重复：

- `task.md` 是需求、状态和结果唯一的存放处。人读它，程序也读它（解析状态和完成条件，把需求部分交给执行者）。它的写法要方便人读，所以里面不放编号、摘要、标记这类内容。
- `record.json` 只放人不需要读、程序需要的运行记录。

### 3.1 task.md

```markdown
---
id: k-19c962be9fb8
title: 交接只传需求部分
status: draft
stage: null
verification: self
parent: null
dependsOn: []
priority: P2
createdAt: 2026-11-14T13:36:56Z
---

## 目标与范围

## 完成条件

### Requirement: 名称
#### Scenario: 名称
- WHEN …
- THEN …

## 待澄清

## 相关资料

- `src/application/handoff.ts` — 拼交接内容的地方
- `docs/design/DESIGN.md#5-交接` — 本任务依据的设计

## 结果

交接改为只传需求部分，完成条件都已满足，测试全绿。

未验证：超出字节上限时的提示还没在真实模型上看过。
```

- 「结果」之前的正文是**需求部分**，交接只传这一段。
- 「完成条件」用 Requirement／Scenario 写法；`independent` 任务必须写场景。
- 「待澄清」用 `[blocking]`／`[assumed]`；有 `[blocking]` 时不能确认需求。
- 「相关资料」一行一个路径加理由，可以用 `#标题` 指到文件里的一节。路径一律相对项目根，本任务目录里的文件也写全路径。
- 「结果」在任务完成时写，是一段总结：做成了什么、完成条件是否都满足、怎么验证的；没满足或没验证的条件逐条点名。
- 「结果」里不放明细。改动文件清单记在 `record.json` 里，`knit task show` 和交付预览会列出来，提交之后以 Git 为准。提交号也不写进文件，`knit task show` 从 Git 记录里查；项目不在 Git 仓库里时没有提交号。

### 3.2 状态

`status` 和 `stage` 两个字段：

| `status` | 含义 | 怎样进入 |
| --- | --- | --- |
| `draft` | 需求在讨论 | 创建任务 |
| `ready` | 需求已确认，等待开始 | 用户确认后 `task ready` |
| `active` | 正在某个环节，`stage` 写这个环节的 id | 派发一个环节 |
| `done` | 已完成、待交付，「结果」已写 | 见第 8 节「完成」 |
| `delivered` | 已归档；项目在 Git 仓库里时也已提交 | `deliver` |
| `cancelled` | 已取消 | `task cancel` |

主会话直接做的任务不经过 `active`：没有单独的开始命令，确认之后直接 `task close`，从 `ready` 到 `done`，改动文件在这时登记。

需求确认之后又改了需求部分，任务回到 `draft`，要重新确认。

### 3.3 record.json

入库，不进任何上下文，不重复 `task.md` 里的内容。字段：

| 字段 | 内容 |
| --- | --- |
| `runs` | 每次执行的编号、环节、起止时间、结论、失败原因、当时需求部分的摘要、改动文件、会话文件位置和原生恢复标识 `resumeId` |
| `confirmedDigest` | 需求确认时需求部分的摘要；与当前不一致就视为回到 `draft` |
| `changedPaths` | 主会话直接做时登记的改动文件 |
| `authorization` | 交付时用户授权的引用 |

- 每个环节进入过几次从 `runs` 里数，不另存。
- 结束时间为空的执行是正在跑的。任务有执行者在跑时不能 `task close`、`task cancel`。
- 需求改过并重新确认之后，以前的执行不再算数：从第一个环节重新开始，进入次数从头数，审查通过的记录要重新取得。
- 一次执行结束后，它的事实只记在 `runs` 里。`.runtime/runs/<run-id>/` 是本机的运行资料，不入库：里面留着交接内容、日志、报告原文、派发前后的工作区记录和会话记录，`runs` 中的 `sessionFile` 定位会话记录，`resumeId` 用于下次恢复。Pi 保存核验过的原生 JSONL 路径，Antigravity 保存原生 conversation ID。旧执行省略 `resumeId` 时按 `null` 读取。
- 审查结论随仓库走，换机器不需要重建。

## 4. 规范

- Knit 从安装包 `assets/standards/` 加载讨论、任务编写、任务拆分和交付规范，标识分别为 `knit:standards/discussion.md`、`knit:standards/task-writing.md`、`knit:standards/task-splitting.md` 和 `knit:standards/delivery.md`。升级安装包后下次读取即生效。
- 内置规范和角色模板随安装包进入每个项目，只写任务怎么讨论、拆分、编写和交付。代码怎么分层、测试怎么组织、哪些改动要独立审查或单独授权，由项目写在自己的 `.knit/standards/` 和 `AGENTS.md` 里，不写进内置规范和角色模板。项目不能用同名文件覆盖内置规范，内容有偏差时直接改内置文本。
- `knit init` 和 `knit standards list` 会列出旧版留在 `.knit/standards/` 顶层的四份同名副本并提示迁移。原文保留，任务点名旧路径会解析到对应的内置资源。项目可在另名文件中调整提问数量、提交文案语言等团队约定。任务状态、交付授权、受保护文件和报告字段仍由对应操作的代码核验。
- 项目自己的开发规范由一个初始化任务带着写。`knit init` 运行时项目里一个任务都没有（归档的也算）就建这个任务：标题「完善项目的开发规范」，目录名里的名称 `bootstrap-standards`，状态 `draft`，验证方式 `self`，优先级 `P1`，正文是模板 `assets/templates/tasks/bootstrap-standards.md`。它只做一件事：照代码现在的做法写出 `.knit/standards/development.md`，用户看过、同意后保存。这个任务不自动选中，不自动确认，不派给执行者，由主会话和用户一起做；`knit init` 的输出在最后一行给出它的标题、id 和路径。项目里已经有任务时不建，所以重复运行 `knit init` 不会多建，已经在用 Knit 的项目也不会收到；没有关掉它的选项。
- 项目规范保存在 `.knit/standards/` 下，支持嵌套目录。普通规范在 Markdown 开头声明适用的环节。

  ```markdown
  ---
  title: 开发规范
  stages: [implement, review]
  ---
  ```

- 规范文件会原样进入智能体的上下文，所以只写智能体做事时要用到的内容。来源、日期、编号、制定经过不写进文件，写在提交说明里。开头声明了 `title`，正文不再加一行重复的标题。
- 环节名用 `workflow.yaml` 里的 id，另有两个固定的：`discuss`（主会话讨论需求）和 `deliver`（主会话收尾）。
- 普通项目规范按 `stages` 自动选取。任务可以在「相关资料」里用资源标识或项目路径追加整份规范。`knit standards list` 标出缺失声明和流程里没有的环节。
- 项目避坑清单固定为 `.knit/standards/pitfalls.md`。二级标题 `## 通用` 适用于所有环节，`## discuss`、`## implement, review` 等标题用环节 id 指定适用范围。三级标题是条目名称。`knit standards pitfalls <环节>`、主会话上下文和执行者交接都只选通用区及包含该环节的非空分区，保持文件中的顺序。任务点名清单或其中某节时也按当前环节选取。
- 记录经验前查看适用分区，已有同一经验时沿用原标题。`knit standards record --section <分区> --title <标题> --body <正文>` 补充已有条目或创建新条目，首次记录会建立文件。
- 同一条规则只写一处：项目通用说明留在 `AGENTS.md`，需要按环节给的规范写在 `.knit/standards/`。
- 不确定是否该成为长期规则的，当场问用户；不设候选文件和审阅回执。

## 5. 交接

### 5.1 给谁什么

| 接收方 | 收到的内容 |
| --- | --- |
| 主会话 | `discuss` 的普通规范，通用及当前环节的避坑条目。选中任务时追加任务标题、状态、下一步和当前环节的补充规范。Pi 每轮完整替换；钩子宿主首轮完整注入，之后按块更新 |
| 使用全新会话的环节执行者 | 需求部分；「相关资料」点名的文件或章节；`plan.md`（如有）；主会话本轮修改指令（如有）；上一批每位执行者的报告或失败原因；本执行器上一次进入本环节的报告（如有）；适用本环节的规范；本环节的角色文件 |
| 恢复原会话的环节执行者 | 主会话本轮修改指令、上一批每位执行者的报告路径与结论或失败原因、本轮执行规则和报告格式。环节未授予 `read` 时，在交接字节上限内同时附上审查报告原文 |

- 不传：「结果」、`record.json`、其它任务、没有点名的 `design.md` 和研究资料。
- 分块的单位有两级：任务本身按拆分规范保持小；大文档用 `#标题` 只取一节。
- 字节上限的初始值：单个文件 16KB，一次交接合计 64KB。超出的只给路径和一句说明，由执行者自己读。受上限约束的是点名的资料、`plan.md`、上一批的报告和本执行器上一次的报告；完整交接中的角色文件、规范、需求部分和主会话修改指令全文给出，只计入合计。
- `tools` 省略、为 `all` 或含 `read` 时，普通点名资料只内联不超过 `min(4096, handoff.fileBytes)` 字节的 `.md` 文件或 `路径#标题` 章节，并受合计上限约束。其他文件给出路径，供执行者按需读取。没有 `read` 时，所有点名文件和章节都沿用配置的单文件和合计上限。本任务的 `plan.md` 和历史报告也沿用配置上限。
- 执行者像普通智能体一样读取项目的 `AGENTS.md`。环节的 `tools` 显式列出能力且没有 `external` 时，关闭扩展、技能和 MCP 的自动发现。
- 适用 `discuss` 的普通规范不依赖任务选择。读取主会话上下文不创建任务或执行记录。选中 `draft` 时，任务部分只提供任务信息；其他状态按环节补充规范：`ready`、`active` 是正在跑的那次执行的环节，没有在跑的就是下一步要做的环节，所以主会话直接做某个环节时也收到该环节的规范；环节都做完、等主会话核对和 `task close` 时，以及 `done`，补充 `deliver`（不再提供开发规范）；`delivered`、`cancelled` 不补充环节规范，讨论规范仍在。
- 普通规范按资源标识或项目路径去重。避坑清单只出现一次，按当前任务环节选区。无选中任务、草稿和已归档任务按 `discuss` 选区。

### 5.2 放在哪里

- 完整交接保存在执行目录的 `system.md` 和 `message.md`。选中原生续聊时，客户端接收 `resume-message.md` 的增量消息。
- 完整交接中，角色文件和规范放在系统提示里；需求部分、主会话裁决（`<main-instruction>`）、点名的资料、`plan.md`、上一批各成员的报告和本执行器上一次的报告放在第一条消息里。
- 声明 `report.verdict` 的环节在 `message.md` 和续聊的 `resume-message.md` 中都收到 `<worktree-changes>`。它列出准备命令完成后 Worktree 的 `git diff --stat HEAD` 和未忽略的未跟踪文件。补丁保留一行上下文，最多 8192 字节，同时受 `handoff.fileBytes` 限制。加上补丁后的完整交接（续聊时为本轮增量消息）在 `handoff.totalBytes` 内才附上正文。超限时保留摘要和 `git diff HEAD` 提示。工作区干净时省略整块。
- 仓库资料（不在 `.knit/tasks/` 下的点名资料）从任务的 Worktree 读，仍给项目内的相对路径；执行者按路径读到的就是附上的那一份。文件里的章节仍用 `路径#标题` 点名。
- `.knit/tasks/` 下的点名资料（本任务的，和别的任务的，例如主任务的设计）、`task.md` 的需求部分、`plan.md` 和各次报告从主检出读，块上的路径给主检出里的绝对路径，章节路径保留 `#标题`。超过字节上限时仍只给路径和说明，执行者可以按绝对路径读到当前资料，不会读到 Worktree 里的旧任务副本。
- 第一条消息由 Knit 生成一段工作位置说明：执行者在任务的 Worktree 里工作，任务目录和以前的报告在主检出，只读、不要改；同时给出 Worktree、主检出和任务目录的位置。这段不写进角色文件，也不改变资料的字节预算；相同输入得到逐字相同的输出。
- 内置规范从安装包读取。角色文件、项目规范和避坑分区从主检出读取。系统提示先给角色，再给内置和项目规范，各来源内按路径排序。
- Pi 主会话的规范放在桥接维护的系统提示里。Knit 派发的 Pi 执行者从环节交接取得规范，即使开放扩展发现，也会跳过 Knit 主会话桥接的初始化。Antigravity 从项目插件加载命令说明，在 `SessionStart` 和 `PreInvocation` 通过 `PATH` 上的 `knit hook agy <事件>` 读取上下文，内容变化时由 `injectSteps` 注入系统消息。`PreToolUse` 订阅 `run_command`，为 `knit context --use/--unuse` 绑定会话，为 `knit run start` 提供宿主默认执行者，并对照用户消息核对 `knit deliver --authorization`。插件直接使用钩子和 CLI，无需 MCP 服务。
- WorkBuddy 在受信任的工作区加载 `.workbuddy/settings.json`。`SessionStart` 与 `UserPromptSubmit` 通过 `hookSpecificOutput.additionalContext` 注入上下文，首轮另附桌面主会话指引。启动事件缺少 `cwd` 时依次取 `CODEBUDDY_PROJECT_DIR`、`CLAUDE_PROJECT_DIR` 和钩子进程工作目录。
- 两个钩子宿主按项目、宿主和原生会话标识分别保存任务选择，以及普通讨论规范、当前环节补充规范、适用避坑分区、任务状态和 WorkBuddy 指引的摘要。首轮注入全部适用内容；之后只发送变化的规范或指引块，并带上最新任务状态。任务状态单独变化时只发状态；内容未变或不在 Knit 项目时不注入。避坑分区变更不触发普通规范重发。
- WorkBuddy 的 `PreToolUse` 只订阅 `Bash`。`knit context --use` 和 `--unuse` 通过 `updatedInput.command` 取得 `KNIT_HOST=workbuddy` 和当前会话标识。交付时只读 `transcript_path`，排除宿主合成消息和 `<system-reminder>`。桌面端以 `<user_query>` 包裹正文时，提取其中的用户输入并去掉宿主附加的 `<query_source>` 来源标记。共用内核核对整条或完整一行原话。预览直接放行，原话核对失败时返回 `permissionDecision: deny` 及继续做法。
- 规范不写进角色文件：角色文件是 Knit 的模板，升级时会重新生成。

放系统提示的理由：Pi 压缩会话时保留系统提示，把旧消息压成摘要。本机记录里一次执行中位 13 分钟、最长 141 分钟，规范放在消息里可能被压掉。

另外两个工具的做法：

| | 执行者 | 主会话 |
| --- | --- | --- |
| Trellis | 拼进派给子 Agent 的那条任务消息：角色说明、规范正文、需求、任务 | 在 Pi 上放进系统提示；在走 hook 的客户端上只给精简状态 |
| OpenSpec | 不区分执行者 | 智能体调用 `openspec instructions`，规则作为命令输出回到对话里 |

两者都不把规范写进角色文件。

## 6. 流程与角色文件

### 6.1 流程

流程可以配置，文件是 `.knit/workflow.yaml`，格式：

```yaml
version: 1
model: provider/模型          # Pi 环节的流程缺省
thinking: high               # Pi 环节的流程缺省
maxRepairRounds: 5            # 返工上限，不写是 5
stages:
  - id: implement
    name: 实现
    prompt: .knit/agents/implement.md
    resume: true
    tools: [read, write, exec]
  - id: review
    name: 审查
    prompt: .knit/agents/review.md
    resume: true
    tools: [read, exec]
    executors:
      - id: pi-review
        agent: pi
      - id: agy-review
        agent: antigravity
        model: gemini-3.8-flash-low
    report:
      verdict: [pass, changes_requested, blocked]
    onVerdict:
      changes_requested: implement
      blocked: review
```

- 两头固定：讨论（需求确认之前）和收尾（交付），都在主会话里。中间有哪些环节、什么顺序，由这个文件决定。默认模板设有实现和审查两个环节，都显式开启 `resume: true`。审查角色先用改动摘要和实现报告的证据逐项核验，优先运行定向测试。需求或项目规范指定全量验证，或改动涉及跨模块行为、高风险路径时，运行全量测试。普通审查建议使用 `high`，高风险改动可用 `max`。
- 环节的 `agent` 接受 `pi` 和 `antigravity`。省略时取派发入口的客户端。Pi 桥接传入 `pi`，其他调用方可通过 `KNIT_SESSION_AGENT` 传入客户端。普通终端缺省为 `pi`。新执行记录写入实际 `agent`，历史记录省略该字段时按 `pi` 读取。`run status`、`run wait` 和 Pi 的续跑通知显示实际 Agent。
- Pi 模型写成 `provider/模型`，依次取本次 `--model`、环节、流程顶层、主会话。四处都没有模型时拒绝派发。思考等级按相同顺序取本次 `--thinking`、环节、流程顶层、主会话，允许 `off`、`minimal`、`low`、`medium`、`high`、`xhigh`、`max`。有值时传给 Pi 的 `--thinking`，Pi 按模型能力收窄。省略时由 Pi 取缺省。
- Antigravity 模型使用 `agy` 自己的 ID。模型和思考等级依次取本次命令行覆盖和环节值。思考等级允许 `low`、`medium`、`high`、`xhigh`、`max`，传给 `--effort`。缺省参数由 CLI 决定。`knit workflow validate` 给出显式配置的错误行号。省略 `agent` 时，模型格式和思考等级还要在派发时按实际客户端核对。
- Pi 桥接把 `ctx.model.provider`、`ctx.model.id` 和 `ctx.thinkingLevel` 放进子进程的 `PI_PROVIDER`、`PI_MODEL`、`PI_REASONING_LEVEL`，Pi 的 bash 工具也会注入这些变量。`knit workflow show` 显示环节的 Agent 和流程可确定的模型与思考等级。主会话和命令行覆盖值在派发时取用。
- 返工上限写在顶层的 `maxRepairRounds`，不写是 5。
- 每个环节可以写：`id`、`name`、`description`、`agent`、`model`、`thinking`、`prompt`（角色文件）、`resume`（允许返工时续聊，默认 `false`）、`tools`（能力：`read`、`write`、`exec`、`external`、`network`）、`report`（额外的报告字段）、`onVerdict`（按结论跳到哪个环节）、`maxVisits`（第一次之后最多再进入几次，`null` 是不设上限）。
- `executors` 是非空列表。使用列表时，把 `agent`、`model`、`thinking` 写在成员上。各成员的 `prompt` 缺省沿用环节角色文件。`id` 在环节内唯一，省略时按顺序取 `executor-1`、`executor-2` 等。命令行的模型或思考等级覆盖对每位成员生效。
- 有两位及以上执行器时，必须显式列出 `tools` 并排除 `write`。上例中的审查者分别验证同一份 Worktree，报告单独保存。单执行器可以继续使用原有环节字段。
- 报告里带 `verdict` 的环节算审查环节。
- 文件手工改，`knit workflow validate` 校验并给出行号。没有 `add`／`remove`／`move`／`set-*` 这些修改子命令，也没有 `knit_workflow` 工具。
- 文件有错时，拒绝派发新的执行并指出哪一行。
- 单执行器按最近一次正常结束的执行推导下一步。其结论命中 `onVerdict` 时转到指定环节，否则顺序前进。首次派发进入第一个适用环节，最后一个环节之后交回主会话 `task close`。单执行器失败可以原地重试。并行批次在全部成员结束后按第 7.1 节处理。
- `self`／`none` 的任务不进审查环节，其余环节做完后由主会话核对并 `task close`。
- 进入次数：任务从别的环节来到一个环节算进入一次；单执行器失败重派、`blocked` 后留在原环节均不增加进入次数。每个已结束的并行批次算一次进入。`maxVisits` 是第一次之后还能再进入几次，不写时用顶层的 `maxRepairRounds`；写 `null` 是不设上限。一个回退环上每个环节都写了 `null` 时返工停不下来，`knit workflow validate` 报错。

### 6.2 角色文件

- 角色文件是 Knit 的模板，随 Knit 发布。默认两份：`implement.md`（实现）和 `review.md`（审查）。内容是这个角色在 Knit 里怎么工作：职责、做事的顺序、报告怎么写、返工时怎么回应上一轮的问题（第 7.1 节）。
- 它和项目规范无关。项目自己的要求写在 `.knit/standards/`，不写进角色文件。Knit 升级后角色文件按模板重新生成，覆盖前备份。
- 项目在流程里加了自己的环节时，自己写那个环节的角色文件。
- 对所有环节都成立的硬规则由程序给，不写在角色文件里：不能提交、不能改受保护的路径、报告的格式。
- 位置：只有 `.knit/agents/` 这一份，由 `workflow.yaml` 的 `prompt` 指向。`knit init` 不往 `.pi/agents/` 或其它客户端的目录里生成：以后接入别的客户端时，各客户端共用这一份，由 Knit 拼进交接内容。
- Trellis 的做法相同：角色文件由初始化生成，规范目录初始化时只给待填写的骨架。

## 7. 执行

Knit 为 Pi 和 Antigravity 提供共用执行入口：

| Knit 共用流程 | 客户端适配器 |
| --- | --- |
| `startRun`／`prepareRun`：派发检查、Worktree、交接、准备命令、快照与后台进程登记 | 从主会话提供模型与思考等级的回退值，不覆盖流程和命令行设置 |
| `executeRun`／`runInPane`：在 Worktree 执行、开关 Rex 窗格、等待启动与后台回退、执行结算 | 提供交互客户端启动命令，或创建后台会话；映射启动参数、工具能力和权限 |
| `runAgentSession`：启动检查、保存报告、校验字段、原会话补报一次、停止客户端 | `AgentSession` 提供启动失败原因、每轮的报告或失败原因、原生会话文件，以及在原会话发消息和停止的操作 |
| `run-process`／`cancelRun`／`waitRun`：进程身份、窗格客户端登记、子进程停止、取消结算与等待记录（`waitRun` 轮询可按短退避或显式间隔参数化，兼顾生产低占用与测试快速响应；`stopProcesses` 生产默认 5 秒宽限期，测试可注入更短值） | 从 RPC 或交互事件采集结果；Pi 窗格暂停后保留原会话，继续输入才交回本轮结果 |

Pi 和 Antigravity 按 Agent 名在 `src/adapters/agents.ts` 登记。派发读取主会话客户端的缺省值，检查所选执行者的隔离条件。执行和结算按记录里的 Agent 找到适配器。接口在 `src/contracts/agent.ts`。Pi 和 Antigravity 的后台 worker 与窗格客户端都调用 `runAgentSession`，该函数保存与校验报告，必要时在原会话补报一次。窗格先发布 `outcome.json` 再停止客户端，后台 worker 收到后调用 `finishRun` 入账。原 Pi 主会话的等待链路在结算后投递结果，触发新一轮。

- 派发的执行者在任务自己的 Worktree 和 `knit/<任务目录名>` 分支里执行，主检出不变。同一任务一次派发一个环节。多执行器共用一份派发前快照和一个 `batchId`，每位成员有自己的执行 id、后台进程和报告目录。不同任务可以同时派发，各自结束时桥接各发一条通知。主会话直接做的任务不建 Worktree。
- 各任务只写自己的 `task.md` 和 `record.json`，写入时仍核对版本；运行资料在各自的 `.knit/.runtime/runs/<执行 id>/` 里。`knit run status`、`knit run wait` 和 `knit run cancel` 只针对指定任务，取消一个任务的执行不影响其它任务。含并行环节的流程按任务对派发和批次结算加短锁；会改同一批文件的任务用 `dependsOn` 排先后，合并冲突由交付处理。
- 第一次派发时，非交接的派发条件通过之后、读取交接资料之前，从主检出当时的 `HEAD` 建 Worktree；主检出没提交的改动和被忽略的目录（如 `node_modules`）不会带过去。返工、审查复用同一个 Worktree。目录不在而任务分支还在时，先 `git worktree prune`，再按原分支检出。这次派发新建了目录时才运行配置的准备命令，包括按原分支重建目录；复用时不再运行。不自动合并或清理。
- Knit 读取的流程、项目规范、配置、角色文件、任务目录和运行资料来自主检出。`knit run start`、`knit run status` 和每轮任务状态在 Worktree 存在时都显示它的位置和分支；任务状态不变时这一行逐字不变。
- 派发过的任务在任务 Worktree 里交付，提交留在任务分支上（第 8.2 节）；主会话要补代码改动时也在这个 Worktree 里改，不在主检出里改。
- 后台 Pi 使用 `--mode rpc`，后台 `agy` 使用双向 stream JSON。`knit run start` 在准备命令完成并派发执行者后返回。Rex 中优先使用原生交互窗格（第 7.2 节）。
- 执行者能用哪些工具，由环节的 `tools` 决定。Pi 后台 RPC 和 Rex 窗格都在启动 Pi 时设置 `KNIT_PI_EXECUTOR=1`。桥接入口读到该值就返回，跳过三个主会话工具及全部钩子的注册。`tools` 包含 `external`、写 `all` 或省略时，Pi 仍可发现其他扩展。
- 结束时：读取报告；对比派发前后在 Worktree 拍的工作区记录，得出相对 Worktree 的改动文件路径，写入主检出的 `record.json`；推进任务状态。改动文件以对比结果为准，不依赖执行者自报。主检出里其他人的改动不计入。
- 派发执行者要求项目在 Git 仓库里：改动文件是靠 Git 列出文件对比出来的，执行者有没有提交也靠它判断。不在 Git 仓库里的项目，任务由主会话直接做，照样可以确认、完成和交付。要让这类项目也能派发，得另外定怎么列出要对比的文件、跳过哪些目录；现在不做。
- 执行者不能提交：结束时 Worktree 的 `HEAD` 变了，本次执行记为失败。
- 执行者不能改 `.knit/standards/`、`.knit/workflow.yaml`、`.knit/config.json` 和流程用到的角色文件：只检查 Worktree 里的那一份，改了，本次执行记为失败。
- 派发前先检查：需求已确认、依赖的任务都已交付并合并、这个任务没有还没结束的执行、能按第 6.1 节的先后取到合法模型名和思考等级、仓库已有提交。这些条件不满足时不建 Worktree、不留下本次执行记录；仓库还没有提交时提示先提交一次。模型缺失时只对 Pi 拒绝派发，提示“不在 Pi 会话里时，在 .knit/workflow.yaml 里写 model，或加 --model provider/模型”。Antigravity 派发还检查可用的隔离环境（第 7.4 节）。
- 依赖检查包括已归档的任务，只在派发时做，主会话直接做任务不检查。依赖是 `done` 或更早的状态时拒绝，提示还没有交付，交付并合并之后再派发；被取消的依赖仍拒绝。主检出里找不到依赖时拒绝，提示可能已经在任务分支上交付但还没有合并，也可能确实不存在；按任务 ID 在任务分支的任务文档里找得到时，给出对应的 `knit/<任务目录名>` 分支和在主检出里运行的 `git merge <分支名>` 命令。主检出里是 `delivered` 时，任务分支不存在，或该分支已是主检出当前 `HEAD` 的祖先，才放行；分支还在但不是祖先时拒绝，提示还没有合并并给出合并命令。任务目录被 Git 忽略、归档留在主检出而代码还在任务分支上的项目也按此判断。主会话直接交付、没有任务分支的依赖可以放行；分支被手工删除但没有合并的情况无法判断，不处理。
- 然后准备 Worktree，再按第 5.2 节的来源拼交接。建不出来时拒绝派发，原样给出 Git 的错误。点名的资料读不出或角色文件不存在时也拒绝；仓库资料在主检出里有而 Worktree 里没有时，提示该路径，并说明它还没有提交，所以任务的 Worktree 里没有。这些拒绝条件都不运行准备命令。
- 交接拼好之后，在本次新建的 Worktree 里按顺序运行 `worktree.setup`。命令经系统的 shell 执行（Windows 上为 `cmd.exe`，以支持 `npm.cmd`），环境变量沿用 Knit 进程的；不设超时，不重试，命令是否正确、能否跨平台由项目负责。命令卡住时 `knit run start` 也一直等待，由用户中断。有一条退出码不是 0 时，后面的不再运行，拒绝派发，输出这条命令、退出码和它的标准输出／标准错误。全部成功后才登记执行、在 Worktree 拍 `before.json` 并启动执行者；准备命令生成的文件不算执行者的改动。
- 派发被拒绝时不留下这次执行记录，撤回这次派发新建的 Worktree 和分支，已有的 Worktree 和分支不动；为已有分支重建的 Worktree 只撤回新目录。交接被拒绝时不强制删除；运行过准备命令之后的撤回强制删除新目录，清掉准备过程中留下的未入库文件和被忽略的目录。撤回失败时一起报告 Git 的错误；撤回成功后，下次派发重新建目录、重新运行准备命令。
- 报告是执行者的最后一条消息，全文存成 `runs/<run-id>/report.md`。环节在 `report` 里声明了字段时，报告结尾要有一个 json 代码块给出这些字段；没有声明字段的环节不需要。没有固定字段。
- 报告读不出来时，要求执行者补报一次；仍然读不出就记为失败，保留原文。
- 模型请求出错、Pi 自己重试之后仍然失败时，记为失败 `执行者出错：<模型服务给的原因>`，不要求补报，不存报告。后台执行和窗格里执行记的一样。
- 模型、工具或报告失败后由主会话决定是否重新派发。会话选择见第 7.1 节。
- 执行进程意外退出时不自动恢复：`run status` 会指出，`run cancel` 把这次执行记为失败，之后才能再派发。
- 执行目录里的文件坏了时命令会报错退出，恢复办法见第 7.3 节。
- 看执行过程靠会话记录和 `knit run status`；主会话在 Rex 里时还可以直接看窗格（第 7.2 节）。

### 7.1 返工

单执行器审查按 `onVerdict` 决定去向。具备 `write` 时审查者直接修复范围内的小问题并重新验证；只读审查把每处问题的位置、对应场景和验收办法交给主会话。

| 结论 | 含义 | 默认单执行器流程中的去向 |
| --- | --- | --- |
| `pass` | 所有完成条件通过验证 | 交回主会话核对、收尾 |
| `changes_requested` | 有需交回处理的修改 | 回到实现环节 |
| `blocked` | 缺少验证条件 | 留在审查环节，主会话处理阻塞 |

并行审查按批次汇合（Join）。还有成员在跑时继续等待。全员正常结束且都给出 `pass` 时顺序推进；任一成员失败、受阻或要求修改时，整批交回主会话。主会话按通知中的执行器、报告路径和结论或失败原因核对分歧，汇总后用 `--instruction` 派发。默认去 `onVerdict.changes_requested` 指向的环节，未配置时回到当前环节。裁决时也可通过 CLI 的 `--stage` 指定环节，派发仍检查进入次数上限。

环节开启 `resume: true` 后，派发时在同一需求摘要、环节、执行器和 Agent 下查找最近一次已结束且有恢复标识的执行，正常结束或因模型错误、报告读不出来、中途退出等失败都可以续聊。最近的匹配执行若因提交改动、修改受保护文件或执行清理失败而失败，则使用新会话，不向更早的记录回找。失败重试仍由主会话显式派发，不改变执行计数、返工上限和状态推进规则。恢复失败执行时，增量交接说明上次失败原因，提醒执行者检查 Worktree 保留的改动、继续剩余工作和验证、按格式提交完整报告；附上主会话修改指令（如有），审查仍附上本轮 Worktree 改动摘要。正常返工和复审沿用原有增量交接。

Pi 用 `--session <路径>`，核对原生文件中的会话头、历史交接和助手回复，并在启动时恢复首轮的系统提示。Pi 将相同的系统提示沿用到下一轮，新增的用户消息仅含增量交接。Antigravity 用 `--conversation <ID>`，通过原生事件或钩子核对对话 ID。开启续聊的环节在执行目录保存 `standards.sha256`，涵盖该执行者收到的规范及避坑分区。规范摘要缺失或变化、没有匹配的恢复标识、原生记录失效或恢复启动失败时，Knit 使用本轮完整交接（含主会话修改指令）新开客户端。成功恢复并开始本轮工作后，模型、工具或报告错误按正常失败路径结算。`run status` 和 `worker.log` 显示续聊结果或回退原因。Pi 续聊期间，`run status` 给出正在追加的原生 JSONL 文件路径。重新确认变更的需求或指定 `knit run start <任务> --fresh` 时使用完整交接。

返工上限 5 轮，在 `workflow.yaml` 顶层的 `maxRepairRounds` 改。

审查者改过的文件记在 `record.json` 里这次审查的名下，交付预览里单独标出。这些修改没有第二个人再看；Trellis 的审查者也是直接修。

让返工少发生、发生了能收敛，靠下面三样，程序只做第一样：

- 使用全新会话再次进入一个环节时，执行者收到上一批各成员的报告，以及自己上一次进入该环节的报告。并行复审时，每位审查者收到实现者的新报告和自己上一轮的审查报告。
- 审查的角色文件要求：没修掉的问题逐个写清位置、哪里不对、对应哪条完成条件、怎样算修好；已经修掉的另写改了什么；再次审查时先逐条判定上一轮的问题有没有修好，再看有没有新问题。
- 实现的角色文件要求：返工报告逐条回应审查报告里的问题；上一轮没修好的问题，先写出上次的改法为什么不行，再动手。

程序不校验报告里问题的写法，不给问题编号，也不跨轮比对是不是同一个问题。

到上限时停下，交回主会话，不生成汇总。通知里列出各轮报告的路径和四条可以走的路，四条路是固定的文字：

1. 主会话直接修。
2. 拆成更小的任务。
3. 需求本身有问题就改需求。
4. 用户决定带理由接受，理由写进「结果」。

任务完成时如果返工过，主会话问用户要不要把原因记进避坑清单或规范。这一条写在交付规范里，随规范给主会话（第 5.1 节）；程序不检查。

### 7.2 Rex 窗格

主会话在 Rex 里时（环境变量里有 `REX_SESSION` 和 `REX_BLOCK`），Knit 通过浮动窗格启动选中的原生客户端。用户可以查看过程、继续输入和处理审批。窗格和后台复用会话执行与报告规则。

- 派发、等待、通知、状态、取消的命令和输出都不变。后台进程照旧启动，它开窗格、等窗格里的程序结束、记结果。
- 窗格开在主会话所在的窗口里，标签是 `knit <执行 id>`，开完就最小化，不抢焦点。执行者交报后退出客户端，窗格随之关闭。
- 窗格里的 Pi 扩展从 `agent_settled` 采集最后一条助手消息。`agy` 通过 `Stop` 和当轮转录区分等待、提交和权限阻塞，补报使用 `Stop` 的 `continue` 回执。等待输入或审批期间，执行保持进行中。窗格收到原生钩子的 `transcriptPath` 后，将路径原子写入执行目录的 `session-file.txt`，关窗或取消时据此记录原生转录。后台 `agy` 保存 stream 事件日志。
- `agy` 当轮执行出错时记录失败原因。正常返回时，首行 `KNIT_AGY_SUBMIT` 提交的报告按环节声明校验字段，即使同轮早前有工具被拒。首行 `KNIT_AGY_PERMISSION_BLOCKED` 表示权限阻塞。回复缺少提交和等待标记时，权限错误和本轮新增的 `denied_actions` 任一项都足以判定权限阻塞。结算时保留阻塞原因和被拒操作。后台收到 `KNIT_AGY_WAITING`，或漏标且没有权限拒绝证据时，在原 stream 会话中至多追问一次，要求以 `KNIT_AGY_SUBMIT` 提交完整报告。追问后仍未提交则记为失败。
- `rex` 命令运行不了或窗格开不了时，后台沿用本次选定的会话方式。窗格打开后 20 秒内执行者未登记 `pane.json`，Knit 先关窗。原生恢复在这里启动失败时，Knit 按第 7.1 节使用完整交接重开；新会话在窗格未能启动时改在后台执行。原因写入 `worker.log`。已开始执行本轮指令的窗格按本轮结果结算。
- 模型在 Pi 里找不到时不发消息，记为“执行者启动失败”，和后台执行一样。
- 用户在窗格里按 Esc 中止执行者：这次执行不结束，窗格留着，界面上提示可以接着输入；输入之后执行者接着做，最后照常交报告。代价是中止之后走开，这次执行会一直算正在跑，直到接着输入、关掉窗格或者运行 `knit run cancel`。
- 窗格在执行者交报告之前被关掉：先停止已登记的窗格进程及其子进程，再记为失败“执行者的窗格关掉了，没有交报告”。
- `run status` 显示执行者所在的窗格。后台进程意外退出而窗格还开着时，也会提示执行者可能仍在修改 Worktree。`run cancel` 通过 `pane.json` 找到 Rex 启动的执行者，并停止受管理的进程。
- 窗格客户端先登记自身进程，再确认后台进程仍在运行，然后发送第一条消息。取消会在后台进程退出之后再检查一次窗格登记。
- Rex 的接口和本机核实过的表现记在 `docs/research/REX-PANE.md`。

### 7.3 执行目录里的文件坏了

执行目录 `.knit/.runtime/runs/<执行 id>/` 里有三个 JSON 文件是命令要读的。它们只有在写到一半时进程崩溃或磁盘写满才会坏。坏了之后读它的命令报 `SyntaxError` 退出，不会自己修，要手工恢复。

| 文件 | 什么时候写 | 坏了之后 |
| --- | --- | --- |
| `worker.json` | 派发时，记后台进程的进程号和启动标识 | `knit run status`、`knit run wait`、`knit run cancel`、`knit context` 都报错退出；执行者还在跑，什么都没有停 |
| `before.json` | 派发时，记当时的工作区 | 执行者做完时记不了结果，错误在 `worker.log` 里，这次执行一直算正在跑；`knit run cancel` 先停掉进程，然后报错退出，这次执行还没有记为结束 |
| `after.json` | 审查以 `pass` 结束时，记当时的工作区 | `knit deliver --preview` 报错退出；`knit deliver` 不读它，照常交付 |

恢复 `worker.json`：

1. 停掉这次执行的进程：`pkill -f <执行 id>`。后台进程和它启动的 Pi，命令行里都带着执行 id。执行者在 Rex 的窗格里跑时，另外关掉那个窗格。
2. 删掉 `worker.json`。
3. 运行 `knit run cancel <任务>`。这次执行记为失败「执行进程意外退出」，改动文件照常记下，之后可以重新派发。

只删文件、不停进程的话，`knit run cancel` 照样把这次执行记为失败，但进程还在跑，还会接着改工作区。

恢复 `before.json`：

1. 删掉 `before.json`。
2. 运行 `knit run cancel <任务>`。这次执行记为失败「执行进程意外退出」，之后可以重新派发。

没有派发时的记录可比，这次执行改了哪些文件记不下来（改动文件是 0 个），这些文件不会进交付的提交。要留下的改动，在 `knit task close` 时用 `--paths` 登记。

恢复 `after.json`：删掉它。预览不再标出审查通过之后又改过的文件，别的不受影响。

### 7.4 Antigravity 工具隔离

首版的隔离环境是 macOS 和 `agy` 1.5.13。派发在创建 Worktree 和执行记录之前核对客户端、系统沙箱及欠缺的能力。`exec` 同时需要 `read` 和可用的 macOS 命令进程跟踪器。跟踪器由带 macOS 开发工具的构建生成并随包安装，派发前会在系统沙箱里验证它。Worktree 中已有 `.agents/hooks.json`，或配置链接会屏蔽 Knit 隔离钩子时，派发给出具体原因。准备命令完成后再次核对隔离条件，发现冲突就撤回本次新建的 Worktree，执行记录还未登记。

- `tools` 省略或写 `all` 时请求所有能力。显式数组为能力上限，`[]` 关闭项目工具。`PreToolUse` 对原生工具核对能力及文件的实际路径。具备 `read` 时，省略路径或传空串的读取工具使用 Worktree 根目录。第 5.2 节的主检出任务目录与历史运行目录通过 `read_file` 目录规则只读放行，当前执行目录除外。`allowNonWorkspaceAccess` 保持 `false`，`trustedWorkspaces` 只列 Worktree，启动时无需 `--add-dir`。`edit_file` 与其它原生写入工具共用 Worktree 的写入边界。
- 会话继承用户的许可与拒绝规则。后台和 Rex 窗格均清空询问规则，对允许的 Worktree 读写与命令统一返回 `auto_approve`（避免最小化的 Rex 窗格卡在审批卡），同时用 `permissionOverrides` 将原命令交给 `agy` 核对用户拒绝规则。命中拒绝规则或超出能力上限的调用仍直接拒绝；通过校验的命令直接在命令沙箱内执行。
- 环节没有 `external` 时，主目录的外部定制不影响派发。启动 `agy` 的系统沙箱屏蔽工作区和主目录的 MCP、插件、外部钩子以及 `skills`、`rules`、`workflows`、`agents` 文本定制，覆盖兼容目录、发现清单和对应的符号链接目标。
- `external` 需要同时声明 `network`。`agy` 可以读取上述定制文本和清单，包括 `~/.gemini/antigravity-cli/skills/`。外层沙箱保护这些只读输入及其符号链接目标，`PreToolUse` 继续核对工具调用。
- 声明 `external` 时，预检检查工作区和主目录的 `mcp_config.json`、工作区 `.mcp.json`、插件目录及 `plugins.json`。空的 `mcpServers`、空插件目录或空插件清单可以通过。工作区 `.agents/plugins/` 下仅有主会话插件目录 `knit/` 时也可以派发。同级有其它条目时报告冲突条目的路径。兼容目录和主目录中的同名插件仍按外部插件检查。已有 MCP 服务、其它非空插件来源、外部 `hooks.json` 或工作区 `.gemini/config.json` 会使派发报告冲突路径。新 Worktree 的预检读取将要检出的 Git 版本。在大小写不敏感的检出中，预检合并检查仅大小写不同的目录里的条目。已有 Worktree 的预检读取磁盘配置。外层沙箱始终屏蔽这些自动启动来源和 `~/.gemini/config/config.json`，并允许 `agy` 读取 Knit 安装的 `.agents/hooks.json`。模型连接由 `agy` 管理。
- 所有工具配置下，外层沙箱和 `run_command` 的命令沙箱都拒绝读写 `.agents/plugins/knit/` 及其符号链接解析后的目录，主会话插件的钩子和讨论规范只供主会话使用。插件路径指向 `.agents` 或其隔离钩子 `hooks.json` 时，预检拒绝派发。
- 外层系统沙箱允许 `agy` 在 Worktree 内写项目文件，另外给 CLI 自己的转录、数据库和临时文件留出所需写入路径。工具核对拒绝向这些 CLI 状态路径写入。Worktree 的 Git 元数据、Knit 控制文件、Pi 桥接和客户端配置由系统沙箱保护。Knit 在 Worktree 内创建普通钩子文件。`agy` 1.5.13 会忽略指向 Worktree 外的配置链接。结算时，Knit 依据本次执行保存的配置副本移除由它生成且内容未变的钩子文件。
- `run_command` 通过执行进程登记原命令与工作目录。通过钩子与拒绝规则核对后以单次请求交给独立命令进程，返回原命令的标准输出、标准错误和退出码。`agy` 1.5.13 的转发命令使用临时目录中的固定入口，通过仅对该次调用生效的环境变量传入请求标识。入口本身没有命令参数。会话为该入口添加放行规则，系统沙箱保护入口文件。具备 `exec` 时可查询命令状态，以及通过 `manage_task` 列出、查询或终止后台任务。终止任务会关闭转发客户端，执行进程在连接断开时停止对应的命令。命令继承宿主环境，移除 Pi 主会话私有变量，将 `PWD` 设为请求的工作目录，`TMPDIR` 指向本次执行临时目录中的 `tmp/`。即使环节只有 `read` 和 `exec`，命令也能在该目录创建临时文件。命令由 macOS 自带的 `/bin/ksh -c` 在请求的工作目录中执行。只读环节也能直接使用 here-doc，相对路径按该工作目录解析。使用 Bash 专有语法的脚本可显式指定 Bash，macOS 自带的 Bash 3.2 在只读目录中使用 here-doc 时仍受其临时文件机制限制。只有具备 `write` 时才能写 Worktree 中的项目文件。缺少 `network` 时关闭命令联网，并通过钩子拒绝原生联网工具。命令沙箱规则携带本次命令和执行的标识，子进程在父进程退出或另建进程组后仍带有标识。Knit 在命令返回时回收该命令的进程，并在取消或收尾时按执行标识回收剩余进程。跟踪器报错时仍清理临时目录和定位文件，在执行记录中保存结束时间和失败原因。

## 8. 完成与交付

任务完成之后，交付不再评判它做得规不规范。质量的门在「完成」，交付负责归档和提交；自动合并开着时，成功之后再合并和清理 Worktree。

### 8.1 完成

- `self`／`none` 任务：主会话 `task close` 并写「结果」。
- `independent` 任务：审查结论 `pass` 后完成。用户明确要求时可以带理由直接完成，理由写进「结果」。

### 8.2 交付

交付做两件事：把任务目录归档、状态改成 `delivered`；项目在 Git 仓库里时，再把这个任务的改动提交成一次提交。Git 不是必须的：项目不在 Git 仓库里时只归档，不提交。Knit 任何时候都不推送。

只有这几种情况不交付：

| 情况 | 处理 |
| --- | --- |
| 任务还不是 `done` | 提示先完成任务 |
| 没有用户授权 | 提示需要授权。归档和提交各自都要授权，所以不在 Git 仓库里时也要 |
| 在 Git 仓库里，没有给提交文案或文案是空的 | 提示给出文案 |
| 项目配置有误 | 指出 `.knit/config.json` 的字段问题，归档之前就拒绝 |
| 移动任务目录失败，或 Git 自己拒绝提交（例如 hook 失败） | 撤回：目录、状态、授权和本次暂存恢复到运行之前，原样报告错误 |

授权写成 `--authorization <引用>`，说明用户是在哪条消息里同意的，记进 `record.json`。命令行只要求有，不核对；桥接在调用之前核对它对得上本会话里的一条用户消息：`knit_deliver` 的 `authorization` 填用户同意交付的那条消息的原话，桥接在当前会话里找到这条用户消息才调用命令，记下的是消息的条目 ID 加原话。桥接只证明用户说过这句话，不判断这句话是不是针对这个任务说的。用户可以在任务开始的时候就给授权，交付时引用那一句。一次交付的授权同时覆盖任务分支的合并和清理，不另外要授权；不包含推送、发布和部署。

其它情况只在预览里提示，不拦：

- 记录里的路径现在没有改动（可能已经提交过，或者改回去了）。
- 工作区里有不属于本任务的改动（这些不会被提交）。
- 子任务还没结束。
- 有文件在审查通过之后又改过（标出来，不拦）。

哪些完成条件没有验证，程序判断不了：它们写在「结果」里，预览把「结果」全文列出来。

提交文案只要求非空，不做格式检查；格式写在交付规范里。

任务 Worktree 存在就算派发过，位置和分支使用第 2 节的算法，不按执行记录另存绑定：提交在这个 Worktree 的 `knit/<任务目录名>` 分支上；自动合并关着时，主检出的当前分支和 `HEAD` 不变。任务目录没有被 Git 忽略时，归档也移进这个 Worktree；被忽略时，归档留在主检出，任务分支只提交代码，避免删除 Worktree 时丢掉任务记录。是否忽略按交付所在检出的 Git 规则判断，与预览的文件筛选一致。Worktree 不存在的任务，仍在主检出的当前分支上归档和提交，不核对分支；不在 Git 仓库里的项目仍只在主检出归档。项目配置的 `worktree.autoMerge` 开着时，Knit 在交付成功后合并和清理；关着（缺省 `false`）时，主会话根据交付输出在主检出手工合并和清理（第 8.3 节）。

要提交的文件：各次执行记录的改动、主会话登记的改动，加上任务目录（原来的位置和归档之后的位置），取其中现在确实有改动的。被 Git 忽略的不在内。给出过结论的执行改过的文件算审查改过，预览里单独标出。派发过的任务，文件筛选、记录里现在没有改动的路径、不属于本任务的改动和审查之后的变化都看 Worktree，不看主检出。

审查通过之后又改过的文件也标出来：一次执行以 `pass` 结束时，把那时的工作区记录存成执行目录里的 `after.json`（格式和派发时的 `before.json` 一样）；预览拿算数的执行里最后一次给出结论的那一次来比，它是 `pass` 才比，要提交的文件里现在的样子和记录不一样的标 `审查通过之后又改过`。执行目录是本机的运行时资料，那份记录不在了（清掉了、换了机器）就不标。

步骤：

1. 预览（`--preview`，什么都不改）：列出任务目录要移到哪里、要提交的文件、上面的提示、「结果」和提交文案。派发过的任务另列出 Worktree 的位置和分支、实际归档检出里的绝对位置（被忽略时是主检出），写明提交在任务分支上；自动合并关着时写明不会合并，开着时写明交付之后会合并进主检出的哪个分支，再删除哪个 Worktree 和任务分支。
2. 状态改成 `delivered`，记下授权，把主检出的任务目录移到归档所在检出的 `.knit/tasks/archive/<YYYY-MM>/`。派发过且任务目录没有被忽略的任务，若任务分支带着建分支时已入库的旧任务目录，先临时放在 Worktree 内；这次提交删除它在原位置的那一份，归档里放主检出当前的内容，成功后删除临时副本。跨文件系统的移动先复制完整内容再删除源；复制失败保留源并清理半份副本，删除源失败时用完整副本补回源。
3. 在 Git 仓库里并且有要提交的文件时：在交付所在检出只暂存这些文件，提交一次。其它改动不动，原来已经暂存的别的文件也不进这次提交。不跳过 hook，不推送。提交说明的末尾由 Knit 加一行 `Knit-Task: <id>`。没有要提交的文件时（例如 `.knit/` 被 Git 忽略，任务又没有别的改动）不提交。第 2 步的任意目录移动失败，或 Git 拒绝提交时，都撤回：撤掉这次暂存，把任务目录移回主检出原位置，恢复原来的 `task.md` 和 `record.json`（状态 `done`、撤回授权）；任务分支原有的旧任务目录也原样恢复，不留下临时副本和本次新建的空归档目录，原样报告错误。
4. 核对提交里的文件与提交之前算出来的一致；不一致（hook 改过提交的内容）就报告差异，提交保留。
5. 成功输出归档位置、提交号和首行。派发过的任务还输出分支名和 Worktree 的位置。自动合并关着且生成提交时，输出「这个提交还没有合并进主检出的分支」，下一行给出在主检出运行的 `git merge --no-edit <分支> && git worktree remove <位置> && git branch -d <分支>`，其中分支名和 Worktree 路径都采用 shell 引用。交付此时保留任务分支和 Worktree。
6. 自动合并开着且任务 Worktree 存在时，交付成功后在主检出里合并任务分支，再清理 Worktree 和分支（第 8.3 节）。没有要提交的文件时也做这一步；交付撤回时不做。输出写明合并进了哪个分支、删除了什么；成功合并后的归档位置指向主检出，合并失败时仍指向实际归档所在的检出。合并失败或清理被 Git 拒绝时，任务仍然是 `delivered`，退出码仍为 0，Git 原始输出和后续处理说明都写在标准输出里，让桥接同时看得到交付成功和后续失败。
7. 实际交付成功后，按 `runtime.retainDays` 清理主检出 `.knit/.runtime/runs/` 下的直接子目录。运行 ID 必须唯一归属于主检出归档中状态为 `delivered` 或 `cancelled` 的任务，且 `endedAt` 距今已超过保留天数。本次交付任务、活跃任务引用的 ID、归属不明、尚未结束或 worker／pane 进程仍存活的运行目录都保留。预览、拒绝和撤回均跳过清理。扫描或删除出错时在标准输出写明原因，交付保持 `delivered`，退出码仍为 0。实际删除过目录时，输出末尾列出数量和保留天数。

不持久化交付的中间状态，也不提供进程被杀掉后的自动续跑或撤回。能捕获的移动错误和 Git 拒绝会按上面的步骤撤回；进程在归档完成、提交之前被杀掉时，需要在提交所在的检出手工提交，归档留在主检出且被忽略时只提交代码。进程在移动途中被杀掉时，先核对主检出的任务目录、目标归档和临时副本，再手工完成交付或恢复原目录、状态和授权，不能假定归档已经完成。主任务没有代码，交付只归档它的目录；在 Git 仓库里且目录没有被忽略时，提交的就是这次移动。

交付之后、合并之前，在主检出运行 `knit context <id>`、`knit task show <id>` 或 `knit run status <id>` 都能查看已交付任务。按 ID 先查主检出的进行中任务，再查主检出归档，最后读取该项目对应任务 Worktree 自己的 `delivered` 归档。`context` 和 `task show` 显示归档目录；归档在 Worktree 中时显示绝对路径。两条命令按提交说明末尾的 `Knit-Task: <id>` 字段查找交付提交，先查主检出 `HEAD`，再查任务分支，找到时显示提交号与首行。任务目录被忽略时，归档留在主检出。合并后优先读取主检出的归档。

新任务可用这份 Worktree 归档的 ID 指定 `--parent` 或 `--depends-on`。派发有依赖的新任务前，依赖的任务分支仍须合并进主检出当前分支。`knit task new` 分配目录名时一并检查主检出任务目录、当前项目的 Worktree 目录和本地 `knit/` 分支。候选名已被目录、分支或已有分支的路径前缀占用时，依次尝试 `-2`、`-3` 等后缀。目录和分支名都遵循所在文件系统的大小写规则。Git 仓库的分支读取失败时，`task new` 返回 Git 错误并停止创建。

### 8.3 合并和清理

派发过的任务交付之后，`worktree.autoMerge` 开着时由 `knit deliver` 接着做合并和清理，主会话不重复运行；关着（缺省 `false`）时由主会话接着做。一次交付的授权同时覆盖这些操作，不用再问用户；不包含推送、发布和部署。

在主检出运行 `git merge --no-edit knit/<任务目录名>`，合并进主检出当前所在的分支。普通合并能快进就快进，不能时生成合并提交，不打开编辑器；不要求快进，多个任务依次合并时主分支可能已经向前走了。不用 `--squash` 或 `--no-commit`，结果要落成提交，不留下没提交的合并结果。

合并成功后运行 `git worktree remove <位置>`，成功后再运行 `git branch -d knit/<任务目录名>`。位置和分支以交付输出为准。清理被 Git 拒绝时，未删除的 Worktree 或分支保留，输出 Git 的原话和位置；不用 `--force` 删除 Worktree，不用 `git branch -D`。任务目录被忽略时，归档留在主检出，清理不影响它。没有要提交的文件时也照样合并和清理。

合并失败时，进入了合并状态才运行 `git merge --abort`；主检出里没提交的改动挡住合并、没有进入合并状态时不放弃合并。任务归档已经移进 Worktree 时，放弃合并恢复出来的主检出旧任务目录会被删除，避免再次列出旧任务；当前记录仍在任务 Worktree 的归档里。Worktree 和分支都留着，任务仍然是 `delivered`，提交保留在任务分支上。输出写明交付已经成功、提交在哪个分支、合并没有成功和 Git 的原话。主会话把这些给用户看并问他怎么处理，不自己解决冲突，不强行合并。

自动合并失败或清理被拒绝时，`knit deliver` 的退出码仍为 0：已经交付，没做成的是之后的步骤。主会话必须看标准输出里的合并和清理结果，不能只看退出码。交付被撤回时不合并、不清理；没有任务 Worktree 或不在 Git 仓库里的项目不走这些步骤。

取消任务（`knit task cancel <任务> --reason <原因>`）先把状态改成 `cancelled`，理由写进「结果」，把任务目录归档到主检出；写入发生版本冲突时拒绝，不归档、不清理。有执行还没结束、任务已经交付或已经取消时不能取消，理由不能为空。取消由用户决定，主会话不自己取消；取消的任务不再继续，要做就新开任务。

取消并归档成功后，不合并，按第 2 节的 `taskWorktree` 算法计算位置和 `knit/<任务目录名>` 分支，只清理这个任务的 Worktree 和分支。目录存在时运行 `git worktree remove --force <位置>`；目录不在但任务分支还在时先运行 `git worktree prune`，再用 `git branch -D knit/<任务目录名>` 删除任务分支。取消清理是强制的，里面未提交的改动找不回来，不改变交付之后不强制清理的规则。

输出列出删除的 Worktree 和分支；目录已不在时说明位置和 prune，成功删除有未提交改动的 Worktree 时说明改动已经丢弃，并列出文件数（暂存、未暂存、删除和未跟踪的文件，重命名按旧、新两个路径计数，不计被忽略的文件）。Git 拒绝清理时，任务仍是 `cancelled` 并且已在主检出归档，退出码仍为 0；标准输出原样给出 Git 的错误和留下的 Worktree 或分支位置。没有 Worktree 也没有任务分支的任务，取消行为和输出不变。

## 9. 命令与工具

命令行：

```
knit init [--pi] [--agy] [--workbuddy] [--force]
knit task new | ready | close | cancel | list | show
knit task list [--archive]                查看活跃任务；--archive 平铺列出已归档任务
knit task cancel <任务> --reason <原因>       取消并归档；派发过的任务强制清理 Worktree 和分支
knit run start <任务> [--model <模型>] [--thinking <等级>] [--instruction <修改清单> | --instruction-file <文件>] [--stage <裁决目标环节>] [--fresh]
knit run status | wait | cancel 都按任务 id
knit context [任务]                      讨论规范；指定任务时追加任务信息和环节的补充规范
knit context --use <任务> | --unuse       选中或清除当前宿主会话的任务
knit hook agy <事件>                     Antigravity 插件钩子的入口
knit hook workbuddy <事件>               WorkBuddy 项目钩子的隐藏入口
knit deliver <任务> --authorization <引用> [--message-file <文件>]
knit deliver <任务> --preview [--message-file <文件>]
knit standards list
knit standards pitfalls <环节>
knit standards record --section <分区> --title <标题> --body <正文>
knit workflow show | validate
```

`knit init` 默认只生成 `.knit/`。首次初始化或以后补装时，`--pi`、`--agy`、`--workbuddy` 可以任意组合。

`knit task list` 保留优先级、ID、状态和标题，将活跃子任务缩进在父任务下，每层两个空格。顶层和同级子任务各按优先级、创建时间排序。父任务已归档或缺失时，子任务在顶层显示 `父:<ID>`。`阻塞:<ID 列表>` 列出尚未归档交付、已取消或任务分支尚未合并进当前 `HEAD` 的依赖。

执行期间，任务行显示 `正在启动`、`运行中 3m`（不足一分钟为 `运行中 <1m`）或 `进程已退出`。并行批次需要主会话裁决时显示 `待裁决`。流程文件缺失或无效时仍可查看层级、依赖和进程状态。在 Git 仓库中，列表末尾列出不属于活跃任务且尚未合并进 `HEAD` 的本地 `knit/*` 分支及合并命令。

`knit context [任务]` 始终输出完整内容，Pi 用它每轮替换系统提示。Antigravity 和 WorkBuddy 则由钩子按第 5 节做增量注入。`knit context --use <任务>` 和 `--unuse` 在钩子宿主中只刷新动态状态摘要，不清除已发送的规范或指引摘要。选中任务无法读取时，钩子保留选择，只报告错误，必要时附未发送的普通讨论规范；错误未变时不再注入。旧的 `.knit/.runtime/host-sessions/` 文件保留任务选择，下一次注入时按当前内容重建分块摘要。

WorkBuddy GUI 的 `PATH` 可能优先使用内置 Node 22。钩子脚本将 Homebrew 和用户级工具目录前置，找不到 `knit` 或 Node 低于 24 时再启动登录 shell。自定义安装可通过登录配置或 shims 提供 Node 24 以上和 `knit`。这些路径调整只作用于钩子进程。

WorkBuddy 作为桌面 GUI 主会话宿主，默认使用自身工具与原生子 Agent 完成实现和检查，通过 Bash 调用 `knit task`、`knit context --use <任务>`、`knit task close` 与 `knit deliver` 管理任务与交付，不默认派发外部 CLI。仅在用户明确要求或 `.knit/workflow.yaml` 显式指定外部执行者（`pi` / `antigravity`）时，才在沙箱外（`dangerouslyDisableSandbox: true`）运行 `knit run start <任务>`，派发后立即返回。支持后台等待时用 `run_in_background: true` 运行 `knit run wait <任务>` 并等待完成通知；沙箱拒绝后台等待或无法唤醒时，可用 `knit run wait <任务> --timeout 60` 短等，也可报告已派发，等用户下一轮发言自动刷新选中任务的状态。

Antigravity 主会话通过 `run_command` 调用 Knit CLI。`knit run start <任务>` 成功后，主会话立即用后台 `run_command` 运行 `knit run wait <任务>`，由后台命令完成通知唤醒会话并读取整批结果。

Pi 桥接有 3 个工具：

| 工具 | 动作 |
| --- | --- |
| `knit_task` | new、use、ready、close、list |
| `knit_run` | start（派发任务下一个环节，可选 `model`、`thinking`、`instruction`、`stage` 和 `fresh`。并行审查裁决时，`instruction` 给出修改清单，`stage` 对应 CLI 的 `--stage`，指定裁决目标环节）、status、cancel |
| `knit_deliver` | 预览、交付 |

- 工具的声明不随流程配置变化。
- 桥接只做转交：每个动作对应一条 `knit` 命令，工具的结果就是命令的输出。桥接运行的是 `PATH` 上的 `knit`，不记录安装位置。
- 工具的每个动作都要写明任务 id，不从“当前任务”里取。Pi 的 `use` 把选中的任务写在 Pi 会话记录里，只决定每轮注入显示哪个任务。用 `new` 建的任务不自动选中，选中哪个只由 `use` 决定：一次建一批任务时，选中的不会被新建的换掉。
- 执行结束的通知：`knit_run` 派发成功之后，桥接运行 `knit run wait <任务>`，将返回的状态作为一条 `knit.run-ended` 消息发给发起派发的会话，使用 `deliverAs: "followUp"` 和 `triggerTurn: true`。空闲时触发新一轮，正在执行时由 Pi 排到当前执行结束后投递。并行审查只为整次派发启动一次等待，全部成员入账后，消息列出每位执行器的报告路径和结论或失败原因。若剩余 worker 都已意外退出，`wait` 返回异常状态和 `run cancel` 提示，主会话据此结算。主会话通过工具主动取消时，取消结果随工具返回，桥接停止这次等待，不再另发结束通知。会话重新加载或重开之后不接着等，下一轮的注入里能看到结果。
- `task.md` 正文、`plan.md`、`design.md`、项目规范和 `workflow.yaml` 都是普通文本，主会话用普通的读写工具直接改；格式在 `task ready`、`standards list` 和 `workflow validate` 时校验。
- 用户可以全程在会话里讨论。什么时候问用户要不要建任务、建了之后怎么确认和开始实施，只写在内置讨论规范里；工具说明和注入的结尾提示不重复这些规则。`knit_task` 的说明只写每个动作做什么、要什么参数、返回什么：`new` 建一份草稿，返回标题、编号、`task.md` 路径、`draft` 状态及当前会话是否选中，不改变当前任务选择，失败时返回原因。主会话随后用普通读写工具把已讨论清楚的需求写入 `task.md`。Knit 不解析用户消息来自动建任务。
- 每次成功调用 `task new` 都创建一份独立的草稿，包括同一轮中分别创建的多份草稿。Pi、Antigravity 和 WorkBuddy 的建草稿入口向 CLI 传入宿主与会话标识，CLI 逐份返回标题、编号、`task.md` 链接、`draft` 状态及选择情况。
- 通过 Pi 的 `knit_run` 工具派发时，`start` 动作传递宿主与模型环境。通过 `knit_deliver` 或 `bash` 执行实际交付时，桥接在当前会话分支中核对用户原话。预览可直接执行。
- 每轮注入：没有选中任务时读取 `knit context` 的全部讨论规范，结尾只提示没有选中任务和怎么查看、选中；选中任务时读取 `knit context <任务>`，先给讨论规范，再给任务标题、状态、下一步、目录和第 5 节说的补充规范。选中的任务读不出来时显示错误，仍通过不带任务的 `knit context` 提供讨论规范，不改变选择；讨论规范读取失败时也显示原因，不使用旧缓存。当前任务的选择写在 Pi 会话记录里。

## 10. 用 Knit 开发 Knit

1. 管理本仓库的是安装版（`npm run pack:install` 装到全局），桥接调用安装版。工作区的 `dist` 可以随意重建。
2. 升级安装版是显式的一步，在一个任务交付之后做。
3. 核心文件和宿主桥接的模板在 `assets/templates/`。执行者修改模板。升级安装版后，在主检出运行 `knit init --force` 更新副本，首次启用宿主时加上 `--pi`、`--agy` 或 `--workbuddy`。四份内置规范在 `assets/standards/`，安装版升级后，下次读取规范就使用新版本。
4. 测试只在临时目录里建夹具，不读本仓库的 `.knit/`、`.pi/` 和 `AGENTS.md`。测试夹具优先通过应用层入口和只读模板仓库复制构造，减少重复启动 CLI 与 `git init` 子进程。
5. 交付不依赖 `AGENTS.md` 或任何规范文件的摘要。
6. 普通初始化只补齐核心和本次显式指定的宿主模板。`--force` 还纳入项目中已有任一 Knit 桥接文件的宿主，并补齐该宿主缺少的文件。对 `workflow.yaml`、角色文件和这些宿主的桥接，先将与模板不同的副本按项目相对路径备份到 `.knit/.runtime/backups/<时间>/`，再恢复模板内容。已有的 `config.json`、`.gitignore`、项目规范和任务保留原样。旧版内置规范副本按第 4 节提示迁移。
7. WorkBuddy 以 `.workbuddy/knit-hook.sh` 或三个项目钩子中任一命令对该脚本的引用识别已启用的桥接。项目已有自定义 `.workbuddy/settings.json` 时，普通安装保留该文件，可从模板合入三个钩子。`--force --workbuddy` 备份后恢复整份模板。Antigravity 执行者可以读取项目的 `.workbuddy/`，该目录受写保护。
