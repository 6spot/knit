# Knit：轻量项目辅助层设计

初始记录日期：2026-10-31  
状态：首版设计已实现至 Linux 候选（001–026）；macOS 后续验证。

Knit 是独立 CLI 与项目辅助系统，负责项目初始化、任务记录、规范演进、配置驱动的阶段编排、模型选择、提交归档和恢复。内部按可插拔模块组织，已接入 Pi、local 与 REX；Worktree 和其他客户端具体实现后续增加。

日常主入口是用户在 Pi 中对话，由主 Agent 调 Knit；CLI 同时供本人直接操作。个人开发按单人设计，多会话、多分支和换机器只要求身份、资料和恢复不出错，不建设多人协作、共享调度或团队任务库。

阅读入口：[首版范围](#151-首版闭环) · [架构](ARCHITECTURE.md) · [状态契约](STATES.md) · [技术选型](TECHNOLOGY.md) · [用户命令](#41-命令面) · [运行细则](OPERATIONS.md) · [术语](GLOSSARY.md)。后续 [Worktree](../research/WORKTREE.md)、[研究](../research/RESEARCH.md) 与 [开发约定](../../AGENTS.md) 分开维护。

## 1. 定位与原则

Knit 通过自身 CLI 和项目资料提供核心能力，Pi 是首个客户端／执行后端。Markdown 与 Git 保存长期事实，本机运行资料和原生 Session 保存执行关联。需求讨论、代码编写、代码检查、提交归档围绕同一任务推进，内部模块隔离客户端与宿主差异。

- 模型负责理解需求、判断范围、选择规范与解释结果。
- 程序负责身份、路径、引用、Git 操作、运行状态和结果校验。
- 任务资料保存当前结论和关键经过，执行 Session 保存对话与工具记录。
- 创建任务以用户授权为前提；明确要求创建即视为授权。子任务使用相同规则。
- 普通讨论和小修改可以直接完成，用户按需要选择是否建立正式任务。

### 1.1 依赖边界

| 组件 | 职责 |
| --- | --- |
| Pi 本机 CLI／宿主公开 API | 首版阶段执行与主会话薄桥接；不引入 Pi SDK 依赖 |
| Git | 首版用于状态核对与提交；合入、分支及 Worktree 管理用于后续能力 |
| Knit 核心 | 独立 CLI、初始化、任务、规范演进、阶段、运行协议与恢复 |
| ClientAdapter／AgentRuntime | 系统内部的客户端资料、原生会话与阶段执行适配 |
| SoL-Pi 等 Extensions | 可选的上下文、计划或其他会话辅助 |
| REX 终端适配 | 已实现的进程启动、窗口定位与展示；自动识别 Rex 环境，不可用时回退 local |

初始化、资料与诊断由 Knit 自身运行；Pi 执行需要相应运行时和可用模型。SoL-Pi、计划工具等客户端扩展均为独立可选项。终端宿主只改变执行展示，任务身份、模型策略、检查结论和 Git 操作由核心管理。

## 2. 总体结构与权威信息

内部按 CLI／桥接入口、核心用例、纯领域规则、内部端口／适配、基础设施分层，职责和数据写入方见 [ARCHITECTURE.md](ARCHITECTURE.md)。状态枚举与转移统一在 STATES.md，技术决定在 TECHNOLOGY.md；核心不依赖 Pi SDK 类型或 UI。

首版以独立 CLI 安装，init 自动生成项目资料、受管入口和 Pi 薄桥接，用户无需另装全局 Pi Extension。桥接接原生能力，核心执行业务，内部 Pi/local 实现阶段运行。项目目录如下：

```text
AGENTS.md                         # 保留原规则，添加 Knit 受管入口
.pi/extensions/knit.ts            # init 生成的 Pi 薄桥接，可入库
.knit/
  config.json                     # 项目配置
  workflow.yaml                   # 阶段顺序、提示词、工具、报告字段与回退边
  agents/
    implement.md                  # 实施阶段提示词（默认模板示例）
    check.md                      # 检查阶段提示词（默认模板示例）
    runtimes/<runtime-id>.md       # 按需增加的平台补充，如 pi.md、codex.md
  standards/
    index.md                      # 规范路径、简述与适用范围
    candidates.md                 # 项目级未生效候选（不进入正式规范摘要）
    ...                           # 规范正文
  tasks/
    MM-DD-<slug>/
      task.md                     # 任务入口与业务状态唯一权威
      plan.md                     # 可选：复杂任务实施计划（按需创建）
      design.md                   # 可选：重要技术取舍与方案依据（按需创建）
      research/                   # 可选：调查材料（按需创建）
    archive/YYYY-MM/
      MM-DD-<slug>/
        task.md
        ...
  .runtime/                       # 本机运行、绑定与恢复资料，Git 忽略
    installation.json              # 本机 Knit 安装位置与版本
    init-manifest.json             # 初始化模板与受管文件指纹
    metadata.db                    # Session/binding/operation 元数据（SQLite，WAL）
    runs/<run-id>/                 # 请求、状态、快照与回执
    tasks/<task-id>/scope.json     # 按 Task 累积的成果范围，接收时写入
    checks/<run-id>.json           # 检查凭据，结果接收时写入
    pi-sessions/                  # Pi 自己保存的阶段原生记录，跨 run 保留
```

任务目录直接位于 tasks/ 下，归档按月份组织。sessions/bindings/operations 的元数据存于单一 SQLite 库（M0 实证选定，见 [ARCHITECTURE.md](ARCHITECTURE.md) 第 6 节与任务004）；runs 的请求／证据、快照和诊断仍作文件产物，不镜像重复权威。项目配置、阶段提示词与规范由项目维护，辅助资料按实际内容增加。

| 信息 | 权威位置 |
| --- | --- |
| 任务目标、完成条件、进展、关键结论与下一步 | 当前承载任务的目录中的 `task.md` |
| 复杂任务实施计划与未完成步骤 | 任务目录中的 `plan.md`（按需创建；需求仍以 task.md 为权威） |
| 重要技术取舍与方案依据 | 任务目录中的 `design.md`（按需创建） |
| 调查材料与入口摘要 | 任务目录中的 `research/`（按需创建） |
| 项目规范与适用范围 | 规范正文和 `standards/index.md` |
| 主／子 Session 的身份、关系与原生定位 | 本机 Session 元数据仓储，原生历史仍由客户端保存 |
| 会话原始对话与工具记录 | 对应客户端的原生 Session 记录 |
| 当前主 Session 选择的任务 | 原生有效路径上的关联事件；索引 `selectedTaskId` 为已核实快照 |
| 任务的本机执行位置与阶段 Session 引用 | 本机 binding 仓储（SQLite 元数据库） |
| 阶段请求、状态与结果回执 | 执行目录 `.knit/.runtime/runs/<run-id>/` |
| 代码、分支与提交状态 | 文件系统与 Git |
| 任务列表与归档列表 | 从当前项目的任务目录派生；默认只列未归档任务（进行中／待归档／已取消），归档用 `task list --archive` 按月查看；后续增加 Worktree 列表 |

Session 索引保存身份和关系，任务绑定保存执行位置，运行回执保存每次执行结果。正文中的业务事实以任务资料为准，执行结果以实际产物和验证为准。主 Session 与子 Session 均可从索引查询，历史原文由对应客户端读取。

## 3. 任务主文档与身份

### 3.1 最小元信息

`task.md` 使用简短 frontmatter 和可读正文。

| 字段 | 含义 |
| --- | --- |
| `id` | 带 `k-` 前缀的随机稳定身份，创建时检查冲突 |
| `status` | `open` 或 `closed`，表示业务工作是否结束；不单独证明提交或归档完成 |
| `stage` | 下一步所需阶段：内置锚点 `start`／`deliver`，或当前 `.knit/workflow.yaml` 声明的阶段 id；新任务为 `start`。旧字段 `phase` 的 `discuss` 只读映射为 `start`，其余旧值原样展示，写操作要求当前配置内 |
| `branch` | 本任务当前绑定的完整本地分支引用，例如 `refs/heads/feature/login` |
| `verification` | 完成验证要求：`none`、`self`（默认）或 `independent`；旧记录缺省按 `independent` 兼容 |
| `outcome` | 结束时填写：`completed`、`cancelled` 或 `superseded` |
| `parent` | 父任务稳定 ID；顶层任务为 `null` 或缺省。关系只存子任务一侧，见 3.10 |
| `priority` | 任务自身优先级 `P0`–`P3`；缺省 `P2`，与父子层级无关，见 3.11 |
| `dependsOn` | 前置依赖的稳定任务 ID 列表；缺省为空，执行前必须全部完成，见 3.11 |
| `order` | 人工调整后的业务顺序编号；缺省 `null` 表示沿用真实创建先后，见 3.11 |

标题保存在 Markdown 一级标题。任务类型、负责人、日期等信息按实际需要增加。

`id` 在改名、迁移和归档后保持不变。关联保存身份与路径线索，路径失效时按身份核对。一个工作目录中出现多个同 ID 文件时报告歧义。后续 Worktree 支持按执行绑定区分同 ID 的当前资料和历史副本。

### 3.2 目录命名与归档

任务目录使用 `MM-DD-<slug>`，日期取创建时的本地月日。

```text
任务资料：.knit/tasks/11-01-fix-login/task.md
归档资料：.knit/tasks/archive/2026-11/11-01-fix-login/task.md
```

归档保留整个任务目录的名称和内容。外层 `YYYY-MM` 是归档月份，内层 `MM-DD` 是创建月日；跨月完成时两者分别保留各自含义。

创建时核对当前分支可见的任务目录。名称被其他任务占用时，为 slug 添加短序号，例如 `11-01-fix-login-2`。后续 Worktree 与工作分支命名见 [WORKTREE.md](../research/WORKTREE.md#62-创建与连接)。

任务后来改名时按稳定 ID 更新资料路径线索与绑定。归档目标已存在时按 ID 和操作回执区分断点恢复与其他任务占用；其他任务占用时停止归档并报告。

### 3.3 正文内容

`task.md` 将有效输入与运行记录分开，初始化模板固定放置记录区标记。

| 板块 | 区域与用途 |
| --- | --- |
| 目标与边界 | 输入区：目的、范围、约束与必要设计 |
| 完成条件 | 输入区：可验证结果与必需验收 |
| 待澄清 | 输入区：未决项列表；顶格 `- [blocking] ` 为需用户取舍且影响实施的决定，`- [assumed] ` 为 Agent 假定；解决后折入目标与完成条件并删除，存在 `blocking` 时 `task ready` 拒绝 |
| 输入引用 | 输入区：适用规范、设计材料、代码范围与验证入口 |
| 当前位置 | 记录区：当前 stage 的可读摘要、进展和下一步 |
| 关键经过 | 记录区：决定经过、发现和理由；影响要求的结论须同步输入区 |
| 结果与验证 | 记录区：执行证据、检查摘要、未执行事项和交付结果 |
| 运行引用 | 记录区：Session、run、检查凭据、工作 Commit 和归档回执 |

记录区位于 `<!-- knit:progress:start -->` 与 `<!-- knit:progress:end -->` 之间，所有收尾追加的验证、Commit 与运行引用均写在此区。记录可变化，不参与业务输入摘要；记录中提出新要求或新阻塞时，仍须通过核心更新有效输入或检查状态，不能用记录代替。「待澄清」区段固定使用二级标题「## 待澄清」，行前缀区分大小写且必须顶格；无区段或空区段视为没有未决项，仅 `assumed` 不阻挡 ready；`blocking` 是 task.md 输入内的标记，不是独立任务状态。 需求摘要取确认的输入区及其适用引用版本；status／stage／branch、Session／run ID、记录、本机路径线索、自动解析的运行模型／用量和诊断不纳入。分支、成果内容、正式规则／提示词及必需验证的版本另作检查证据核对；用户明确把特定模型列为验收条件时，按该输入要求处理，而非因主会话后来换模型自动判旧检查 stale。

创建时保存标题、目标、stage 和初始记录，实施前补足完成条件与输入引用。其他区外正文和明确引用的辅助资料视为输入；项目级规范候选保存在 `.knit/standards/candidates.md`，旧任务 `standards.md` 只读兼容，均不自动成为有效规则。详细工具输出保存在原生 Session。

### 3.4 任务规划资料

任务资料以 `task.md` 为固定入口与唯一业务状态权威；`id`、`status`、`stage`、`branch`、`outcome` 与绑定只保存在 task.md frontmatter 和元数据仓储，不因文件拆分建立第二套状态表。复杂任务按需增加规划资料，简单任务始终只用 task.md。

| 文件 | 职责 | 创建时机 | 更新方式 |
| --- | --- | --- | --- |
| `task.md` | 输入区（目标与边界、完成条件、输入引用）与记录区（当前位置、关键经过、结果与验证、运行引用）；业务状态唯一权威 | 创建任务时 | 输入区经 clarify/change 或创建；记录区经 task record 与收尾写回 |
| `plan.md` | 实施计划：步骤产出、真实依赖、受影响结构／接口、验证方式与风险处理；含未完成步骤标记 | 讨论确认任务复杂（多模块、迁移、协议、跨会话）时由主 Agent 创建；简单任务不创建 | 讨论中随方案确认更新；实施中勾选步骤、追加证据为进度更新；步骤产出改变需求时走 clarify/change |
| `design.md` | 重要技术取舍与方案依据：备选对比、取舍理由、与工程结构的对应 | 存在影响后续维护或跨会话理解的取舍时 | 随方案确认更新；不承担进度记录 |
| `research/<主题>.md` | 调查材料：代码事实、外部约定、实验记录 | 讨论中调查产物需要跨会话保留时 | 追加式；task.md 输入引用只链接入口摘要 |

规划资料按需创建：创建任务不堆空 design／plan／研究文件；已有单文件任务直接读取与继续，不强制拆分。规划资料属于任务目录内资料，随任务一起改名、复制交接、恢复与归档；路径变化按稳定 ID 重新定位，引用失效时报告具体缺口（任务045实现生命周期，046实现加载）。

各类事实只有一个权威来源：需求在 task.md 输入区及其引用，方案取舍在 design.md，实施顺序在 plan.md，调查在 research/，执行输出在原生 Session，进度与运行证据在 task.md 记录区。plan.md 不复制需求正文，design.md 不充当计划；同一内容出现在多处时以本表归属为准。

### 3.5 规划资料变更语义

区分需求输入、执行方案、上下文引用与观察记录，修改影响如下：

| 修改 | 需求摘要 | 检查身份 | 入口 |
| --- | --- | --- | --- |
| task.md 输入区 | 变 | 随需求 | clarify/change 或创建 |
| 被输入引用的 design／plan 中的目标、条件、范围或验收 | 变 | 随需求 | 必须 clarify/change，不能藏在计划记录中 |
| plan.md 步骤勾选、证据追加、未完成步骤更新 | 不变 | 不变 | 主会话直接编辑或 task record；阶段执行器报告后由主会话写回，不产生草案 |
| research/ 追加调查 | 不变（除非被输入引用且影响需求，同上） | 不变 | 直接编辑 |
| task.md 记录区 | 不变 | 不变 | task record |

方案文件中被冻结的需求引用按引用时版本核对；实施中修改方案的要求性内容与修改 task.md 输入同语义，活动 run 期间保存为草案，待终态后应用。进度勾选与证据追加不是需求变化，不使检查失效；改变目标或验收不能只改 plan.md。

### 3.6 规模控制

复杂任务的判定由主 Agent 结合上下文判断：多模块、迁移、协议、跨会话接续、多轮澄清通常需要持久 plan；有重要技术取舍时保留 design。调查材料较多时按阅读需要拆为 research/ 文档并保留入口摘要。子目标具备独立实施、验收和结束边界时，Agent 提出拆分并按任务创建规则取得授权。

### 3.7 当前目录执行与绑定

首版以初始化确认的当前项目根为执行目录，实施、检查、工作提交与归档均在该目录进行，使用当前分支。Knit 按阶段核实 cwd、仓库及任务身份；执行位置变化时停止并报告。

本机 binding 保存任务／仓库、相对路径、分支、lastRunIds、lastCheckRunId、阶段 Session 引用，以及 repairCycleId、repairRounds、stopReason；至多一份待应用输入草案保存 kind、理由、内容、基线摘要和草案摘要。binding 等元数据存于 M0 选定的单一 SQLite 库，不双写文件权威；主会话选择独立于绑定。

任务随当前绑定 Git 分支保存，adopt 只接管用户已经切到的分支，不创建或切换 Git 分支。无存活／未知 run、无未核实交付操作，且仓库、任务 ID、文件与 Git 状态匹配时，主 Agent 可按“在当前分支继续”的明确意图代调 adopt，无需用户手工敲命令。任务已绑定旧分支时，只允许改绑到当前检出分支；start 与配置阶段保持当前阶段，deliver 失去交付资格后按 verification 回到最近工作阶段或检查阶段，清除 completed，且旧检查失去交付资格但历史文件保留。adopt 不附带提交授权。

仅分支改变且有效需求未变时，start 与配置阶段保持原 stage；已有检查引用失去交付资格并保留历史，检查阶段保持待检查，deliver 恢复为 status=open、stage=最近工作阶段或检查阶段，并清除 completed outcome。主 Agent 将输入更新声明为 change 时才回到 start。原阶段 Session 可保留，恢复核实客户端、阶段、cwd 并使用当前分支输入；旧报告不证明新分支完成。已取消／替代只接管收尾，不自动重开；已完整归档不自动接管。

文件在新分支不可见时暂停关联，不凭本机记录重建。多机缺少原检查凭据时重查；跨分支同名目录按 Git 冲突和稳定 ID 核对，首版不做全分支任务库或协作同步。

换 Session 继续时核实当前分支可见任务、绑定与旧 run；状态未知时保留占用。绑定缺失时从本项目任务与回执核对重建；指向其他目录或身份不明时阻塞。跨目录关联见 [后续设计](../research/WORKTREE.md)。

### 3.8 阶段权威与推导

frontmatter 的 stage 表示下一项业务工作，取值是内置锚点或当前生效流程中的阶段 id。`task ready` 保存讨论确认后从 `start` 进入配置的第一个阶段；阶段报告被接收后按 `onVerdict` 或顺序流转，最后一个阶段完成进入 `deliver`。`independent` 任务在实施后保留正式检查阶段，`self`／`none` 可直接进入收尾；声明回退的阶段受 `maxVisits` 限制，超限停止并报告 `repair_round_limit`。每次获准实施即刻使旧检查失去交付资格，失败不借旧报告收尾。

业务完成由 `task close --outcome completed` 按当前目标、成果和任务验证要求核对后记录；不要求已有 Git 提交、交付回执或归档。完成凭据写入 `.knit/.runtime/completions/<task-id>.json`，只冻结完成时的输入、scope、验证方式与来源，不新增业务 stage。`self` 依据最近获准实施及其输入／scope，或主会话实施记录（`task implement` 记录的输入摘要、成果路径指纹与实际验证），`independent` 依据当前有效的正式检查；`none` 只在用户明确选择时使用，并记录未验证项。没有可用证据而用户明确要求时，可用 `task close --force --reason` 强制完成：凭据记 `forced`、原因与未验证项，交付提交带 `forced` 标记；`independent` 不能借 force 跳过正式检查。完成后的输入或成果变化使凭据失效，不能继续沿用旧完成交付。

task update 直接写入／保存输入时须声明 --kind clarify/change 及说明；apply/withdraw-pending 使用第3.8节的独立模式，应用时复用草案保存的 kind。clarify 保持当前阶段，摘要变化使检查 stale；当前为 deliver 且 stale 时 independent 回到最近检查阶段、self／none 回到最近工作阶段并清 completed。change 改变目标、条件、范围或业务约束，回 open/start。核心只验摘要、版本与结构，主 Agent 判断类型；新引用带来新要求不能标 clarify，摘要未变不迁移，clarify 不重置修复次数。

上述输入变更迁移仅用于未归档且 outcome 不是 cancelled/superseded 的任务。取消／替代与完整归档不通过输入更新隐式重开；新业务目标按任务创建授权另建，原档案仍可补记和维护资料。

运行中保存 kind、理由和拟修改，旧 run 继续冻结范围；后续代码／交付先应用或撤回。选定目标的检查因 clarify、adopt、restore、生效规范等变 stale，原为 deliver 时按 verification 回到最近检查阶段或工作阶段，不保留不可交付的 deliver；只读发现外部改动仅报告待同步，下一写动作先收敛。run check --task 是复查入口，从 deliver 或检查阶段发起；当前工作阶段调用返回 `phase_mismatch`，不跳过 ready／实施。

草案复用保存的 kind／理由／内容，不建队列或独立状态机。草案摘要包含生成它的更新操作 ID，同内容重建也获得新版本，不能只按正文哈希撤回后来草案。`task update --apply-pending --expect-pending <digest>` 在旧执行结束、结果事实已收敛后应用该版本，并核对草案保存时的基线输入摘要；基线已变则重新确认／合并，不覆盖后来输入；`task update --withdraw-pending --expect-pending <digest> --reason <说明>` 只撤回并留记录，不改冻结输入或阶段。摘要不匹配返回 stale_input，不作用于后来草案；apply/withdraw 与 --kind 更新互斥，也不再接收新的 --file／stdin 正文。取消／替代关闭时核心先撤回未应用草案并留原因，不使草案生效；迟到旧执行结果不得重开任务。

### 3.9 状态转移与展示

完整对象清单、转移表、守卫、写入方和恢复路径以 [STATES.md](STATES.md) 为准。本文件保留产品行为概览；代码按同一状态契约实现，不从自由正文或进程退出码猜测业务阶段。

业务 status/stage/outcome、run 生命周期、检查资格、规范审阅、操作与归档展示分别建模。未知实例、无效输入和未核实副作用优先阻止相关后续动作；纯记录与诊断不因代码阶段排他而全部被锁住。

人读输出以标题与阶段显示名为先、稳定 ID 为后：任务称「标题」加短 ID（类型前缀与前 6 位，如 `k-8ed2d4`），标题超过 20 字截断加省略号；阶段显示生效流程的 `name`，内置锚点固定为准备／收尾，与阶段 id 并列（如 `检查 check`）。`knit status`、`knit run status`、桥接通知与回合上下文共用这一口径；JSON 保留完整任务 ID、run ID、标题与阶段 id，展示缩写不进入协议。

### 3.10 父子任务结构

父子任务以稳定任务身份关联：子任务在 frontmatter 写 `parent`，父任务不保存重复的子任务清单，子任务集合由扫描 `parent` 派生。因此目录改名、归档移动和路径线索变化都不改变关联，也不按目录名称推断层级。

- 创建：`task new --parent <taskId>` 在创建时挂接；也可用 `task parent <taskId> <parentTaskId>` 事后挂接，`task parent <taskId> --detach` 解除。一个任务至多一个父任务，父子层级与执行依赖是两件事——父子关系不构成开始前置。创建子任务仍由用户决定是否登记，挂接 `--parent` 只是结构关系，不等于实施授权。
- 内容分工：父任务自身 `task.md` 保存总体需求、拆分映射与跨子任务完成条件；子任务各自保存范围、产出与验证要求，不复制父任务总需求。父子关系只影响展示与父任务完成核验，不合并输入、scope 或运行状态。
- 结构核对：父任务必须存在、未归档且 status 为 `open`；子任务必须未归档且未结束；拒绝自我挂接与成环（沿 parent 链向上核查）。归档任务的关系冻结：已归档任务不能再挂接或解除父任务，归档父任务不再接收新子任务；归档子任务仍计入父任务结束情况。
- 摘要与资格：`parent` 属于结构身份，与 `id`／`status`／`stage`／`branch` 一样不参与需求摘要，挂接或解除既不改写输入，也不使既有检查 stale。
- 展示：`task list` 默认只列未归档任务，行内只给优先级、稳定 ID、阶段显示名与标题，父子层级不改变执行顺序，也不占用列表行内字段；父任务与直接子任务的结束情况由 `knit status <taskId>` 给出，归档条目用 `task list --archive` 按月分组查看。
- 总体验收：子任务完成只表示分项结束，不自动使父任务可完成。父任务 `task close --outcome completed` 要求所有直接子任务都已结束（归档任务视为已结束），并要求主会话给出 `--reason` 作为总体验收依据；该依据写入完成凭据。子任务全部结束后父任务仍按自身目标、成果与验证要求评估完成资格，不能仅凭子任务状态收尾。
- 取消／替代父任务不自动结束子任务：子任务保持各自状态与资料，仍可独立继续或分别取消。

### 3.11 优先级、前置依赖与执行顺序

调度事实只存于 `task.md` frontmatter，独立于父子层级、阶段状态与目录命名：

| 字段 | 含义与规则 |
| --- | --- |
| `priority` | `P0` 最高，依次到 `P3`；未指定为 `P2`。"紧急"对应 P0，"可后置"对应 P3；未说紧急不等于可后置。`P1` 的具体业务判定由用户在讨论时明确，不从措辞推断 |
| `dependsOn` | 前置依赖的稳定任务 ID 列表；启动前必须全部 `closed` 且 `completed` |
| `order` | 同一优先级内人工调整后的业务顺序编号，只由 `task order` 写入；`null` 表示沿用真实创建先后 |

- 稳定顺序：先按 `P0`→`P3`；同优先级内已调整顺序的按 `order`，未调整的排在其后按 `createdAt`（ISO 毫秒）；`createdAt` 相同才用稳定 ID 兜底，不伪造先后。排序不读目录名、文件系统枚举顺序或创建时间之外的线索。
- 业务顺序调整：`task order` 在目标任务所在优先级分组内移动，`--before`／`--after` 的参照任务必须与目标同优先级，`--top`／`--bottom` 是该分组的两端；跨优先级参照拒绝为 `order_reference_priority_mismatch`。调整只写入该分组的 `order`，不改变其它优先级或同级未涉及任务的先后。
- 原始创建事实：`createdAt` 在创建时写入，调整优先级、依赖、业务顺序与目录改名都不改写它。`order` 保存新的业务顺序，两者分别可追溯；缺少历史时间的旧资料不被填成猜测值。
- 依赖铁律：`task ready` 与实施 `run prepare` 在推进／启动前核对直接前置依赖，未满足时分别返回 `dependency_unmet` 并列出未满足项；优先级和用户明确指定任务都不能绕过。只核对直接依赖；传递依赖由各前置任务在自身启动时按同一规则处理，守卫不重算已发生的历史。检查、交付、记录与只读查询仍可用于已实施任务。
- 结构核对：依赖必须引用已存在的任务，拒绝自依赖与成环；已取消／替代或已归档但未完成的前置保留为可诊断阻塞（`dependency_not_completed`／`dependency_archived`），由用户显式调整依赖，不静默移除。
- 摘要与资格：`priority`／`dependsOn`／`order` 是调度事实，不改变工作内容与验收条件，因此不参与需求摘要；调整它们不改写输入，也不使既有检查 stale。
- 一致性：`task list` 与 `task next` 共用同一排序与阻塞判定；`task list` 默认视图按该顺序分段展示，行内给优先级、稳定 ID、阶段显示名与标题，阻塞只在汇总行计数，逐项原因与下一项由 `task next` 给出；主会话按同一视图选择任务，不各自排序。`task next` 只读，不推进阶段、不派发运行。

## 4. 阶段编排（配置驱动）

任务流程由 `.knit/workflow.yaml` 声明，`stages` 的数组顺序即流转顺序；`start`（准备／讨论）与 `deliver`（收尾）是内置锚点，不可配置、没有提示词。默认模板为 `start → implement → check → deliver`，但环节不是产品固定枚举：项目可增删阶段、改名、调序、限定工具或声明回退边。

| 默认阶段 | 职责 | 阶段结果 |
| --- | --- | --- |
| 实现 `implement` | 按 task.md 目标与完成条件产出代码、测试、配置、文档或研究报告 | 变更范围、验证结果与未验证项 |
| 检查 `check` | 独立核对完成条件、冻结输入、实际成果与验证 | `pass`、`changes_requested` 或 `blocked`，附证据与位置 |

关键字段：

| 字段 | 语义 |
| --- | --- |
| `version` | 当前为 `1`；未知版本整份配置降级 |
| `stages` | 有序阶段列表，至少一个；顺序即流转顺序 |
| `id` | `^[a-z][a-z0-9-]{0,31}$`，写入 task.md 的 `stage`，全文件唯一且不能用锚点名 |
| `name` / `description` | 显示名与本步说明；只用于顶部提示和展示，不参与机器判定 |
| `prompt` | 项目相对提示词路径；缺省或文件缺失时用核心默认 agent 指令 |
| `tools` | 能力白名单：`read`／`write`／`exec`／`task`／`external`／`network`；不写 = 全部放开 |
| `report` | 额外报告字段：`string`／`string[]`／`paths`／`bool`／非空枚举数组；固定字段 `summary`／`validation`／`blockers` 始终校验 |
| `onVerdict` | 报告值 → 阶段 id 或 `deliver`；未命中走顺序下一阶段，目标必须存在 |
| `maxVisits` | 阶段访问上限；回退环上缺省取 `workflow.maxRepairRounds`，无有限上限的环拒绝 |

流转规则：

- `task ready` 从 `start` 进入第一个阶段；阶段报告被接收后按 `onVerdict` 命中值跳转，否则顺序进入下一阶段；最后一个阶段完成进入 `deliver`。
- `onVerdict` 的回退目标可以是已声明阶段；回退环必须有有限上限，超限停止并报告 `repair_round_limit`，不自动续跑。
- 自动流转只推进业务阶段，不代表提交、推送或发布授权；交付仍由主会话按授权协调。
- `independent` 任务在实施后保留正式检查；`self`／`none` 可按配置直接进入收尾。change 回讨论，clarify 保持当前阶段，deliver 的检查 stale 时按 verification 回到最近工作阶段或检查阶段。
- 配置非法时整份降级为 `start → deliver`，不套提示词，使用默认 agent 行为；`workflowMode`、`knit workflow show`、每轮顶部提示与 `knit doctor` 均显示降级原因。在途 run 继续跑完，降级只对新 run 生效。
- 配置与注释不进入 `inputsDigest`：流程重排不使已有输入或检查凭据过期；已删除的 `.knit/workflow.md`（历史文件）不再有单独的 workflow 摘要分节。

默认阶段之外的内容仍由项目维护：主会话规则在 `AGENTS.md` 受管块，阶段职责与停止条件在 `workflow.yaml` 引用的 `.knit/agents/<stage>.md`，规范在 `.knit/standards/`。

### 4.2 主会话工作流

主 Agent 处理每轮用户需求前获得当前任务、阶段、资料入口与下一步规则（每轮注入由宿主桥接实现，见第 9.6 节）；按上下文把请求归入下列路径之一，不建立关键词自动建任务规则：

| 请求类型 | 处理 |
| --- | --- |
| 普通讨论、问答、只读调查 | 直接回答或读取／评估，不建任务，不写业务资料；即使临时委派也只派宿主通用只读能力 |
| 非正式小修改 | 当前会话澄清、修改、自检、汇报；不建任务不提交；用户可要求更广验证或改走正式任务 |
| 新正式需求 | 是否建任务由用户决定；新事项先问任务选择再展开需求（不按类型或预估大小跳过）；提出创建提议（目标、拟建任务、完成验证要求）；未授权不创建，明确要求或已有持续授权直接创建并进入讨论 |
| 正式研究报告／需要跟踪的调研 | 仅用户要求正式跟踪、独立复核或把报告作为任务成果时建任务；报告写项目路径，按 verification 完成；否则直接交付结论，不因落盘强制升级 |
| 继续已有任务 | 选择或确认当前任务，读任务资料与记录接续，不重复询问已授权事项 |
| 已有任务补充／范围变化 | 按 clarify/change 更新任务，尊重活动 run 草案边界，不默认另建新任务绕过旧状态 |

任务创建／选择授权来自用户明确指令或既有持续授权；已有授权持续有效，不逐轮重复询问。新事项先问用户是否建任务再展开需求；暂不创建时继续讨论，转到实施前再确认；明确不创建时同一事项持续有效，不重复追问；实施前仍无有效选择时先补问，不能用“你做吧”代替。创建任务不等于需求确认或实施授权；用户明确“按这个做”等可同时确认范围与实施授权，仅认可思路且实施意愿不明时补问。授权只覆盖任务创建与选择，不解释为提交、推送、发布或迁移授权。用户拒绝创建时不创建，仅在当前会话直接执行；不因代码修改、调研、委派或报告落盘强制建任务。Knit 的 `run` 只派发正式任务 worker；无任务委派使用宿主通用工具／子 Agent，宿主不提供时直接执行并说明限制，不暗建任务。

实施验证按目标、改动范围、影响与风险选择：小范围只检查相关范围；共享基础设施按实际影响扩大并说明理由；用户明确要求的更广／更窄范围优先，未执行项如实记录。不能把建立任务自动解释为全项目全量复核。

讨论阶段先取证再提问：查代码、测试、配置、文档、既有规范与任务历史（含归档任务、run 记录与提交说明），引用 `path:line`、任务 ID、`run:<id>` 或 `commit:<sha>`；仓库证据只证明现状与约束，产品意图、范围边界、验收偏好与风险取舍不能由仓库证据单独回答。按目标与成功判据、范围与非目标、验收与证据、约束与依赖、冲突与合规、数据与副作用、失败与回滚、优先级与时序逐项扫描缺口；证据已解决的不问，不硬造问题。需要用户决定时，每问给出要定的决定、为什么重要、推荐项与选另一项的代价，一轮最多 3 个且一问只承载一个决定；推荐项不是默认选择，用户不答时按推荐推进须落 `[assumed]` 并标注“（Agent 建议，待确认）”。与既有规范、决定或架构冲突时先指出冲突、影响与替代方案，再等用户选择；用户已明确决定的不重复建议。未决项写入 task.md 的「待澄清」区段（`- [blocking] `／`- [assumed] `），解决后折入目标与完成条件并删除；存在 `blocking` 项时 `task ready` 拒绝。收敛时给出最终摘要（目标、范围内外、验收、关键决定、风险与延期、资料状态）并等用户明确批准，不能以“完整方案＋是否正确”作为唯一确认。取证后缺口清单为空或用户已裁决，才视为需求明确并写入 task.md 输入区；复杂任务持久保存 plan.md（步骤产出、真实依赖、受影响结构／接口、验证、风险），重要取舍写 design.md，调查保留 research/。讨论完成与 ready 的结构核对：必需目标／条件／规划齐备、「待澄清」无 `blocking` 项才可 ready；可选文件缺失不阻挡简单任务，不新增独立规划状态机，沿用既有 stage 与 ready 入口（`blocking` 标记与 plan 结构由核心机械核对，其余语义判断属主 Agent）。

每轮主会话需要的上下文：当前选定任务的稳定身份、stage 与业务摘要、待决项（「待澄清」的 `blocking`／`assumed` 计数与内容）、待应用草案与活动运行摘要、下一步规则及阶段提示词入口；无任务时给出相应入口规则，不虚构任务状态。实际写动作仍经核心重新核对授权、阶段、锁和版本；注入是行为引导，不是副作用安全边界。

### 4.3 命令面

Knit 独立安装，项目 Pi 桥接的 /knit 和工具转交同一核心处理器。默认输出摘要，--json 为单响应，--events 为观察流；日志走 stderr，不混入机器响应。

| 子命令 | 行为 |
| --- | --- |
| init [--pi] [--force] | 初始化项目资料与客户端入口；默认沿用已有项目文件，--force 按模板覆盖并备份 |
| start [--pi] | 启动原生客户端，不另建聊天 UI |
| session attach / context | 核实原生上下文，提供讨论输入与下一步，不创建 worker |
| task new [--verification none/self/independent] [--parent <id>] [--priority P0-P3] [--depends-on <ids>] | 按用户授权创建；完成验证要求默认 self，优先级默认 P2；可同时挂接父任务与登记前置依赖 |
| task parent <id> <parentTaskId> / --detach | 挂接或解除父子关系；只改结构身份，不使输入摘要与检查失效 |
| task priority <id> <P0-P3> | 设置任务自身优先级；只改调度事实，不使输入摘要与检查失效 |
| task depends <id> --add/--remove/--set <ids> / --clear | 维护前置依赖；拒绝缺失、自依赖与成环，未完成的前置显示为阻塞 |
| task order <id> --before/--after <id> / --top / --bottom | 在同一优先级分组内调整业务执行顺序；参照任务须同优先级，不改写原始创建时间 |
| task next | 按稳定执行顺序列出活跃任务与不能启动的原因；只读，不派发运行 |
| task search <query...> [--scope task/archive/run/git] [--limit n] | 按用户查询意愿只读检索任务、归档、run 与 Git，返回 path:line／run／commit 来源；默认 20 条、上限 100；无匹配返回空数组 |
| task verification <id> --mode <值> | 仅在讨论阶段调整完成验证要求，作为输入变化 |
| task list [--archive] [--month YYYY-MM] | 默认按进行中／待归档／已取消分段列出未归档任务，行内给优先级、稳定 ID、阶段显示名与标题，末尾汇总条数；--archive 按月列出归档（--month 过滤月份）；JSON 带 scope，默认不返回归档数组 |
| task rename / use / clear | 按授权管理身份、位置与当前原生路径选择 |
| task ready [id] [--session <id>] | 保存讨论确认，不自动实施；省略 id 时用主会话已落盘的选择，否则拒绝为 `task_id_required`；「待澄清」存在 `[blocking]` 项时拒绝为 `clarify_blocking` |
| task update [id] --kind clarify/change | 明确变更类型，可用 --file 或 stdin；活动 run 中只保存当前草案 |
| task update [id] --apply-pending / --withdraw-pending --expect-pending <digest> | 按摘要应用／撤回草案；撤回另带 --reason，不与 --kind 同用 |
| task record [id] | 短锁写纯记录；封存中明确返回未保存 |
| task implement <id> --path <p> --validation <text> | 记录主会话／用户实施事实：输入摘要、成果路径指纹与实际验证；没有 worker run 时作为 self 完成依据 |
| task adopt <id> --branch current | 接管当前可见分支，不切分支，不附带提交授权 |
| workflow init/show/validate/add/remove/move/set-prompt/set-tools/set-report/set-next | 生成、查看、校验与修改 `.knit/workflow.yaml`；写入先全量校验，失败带 YAML 行号拒绝 |
| run prepare/start --stage <id> --task <id> [--rex/--local] | 按生效流程派发阶段 worker；配置外的阶段拒绝并返回合法清单；缺省按 execution.host 自动选择宿主 |
| run check --scope <路径...> | 非正式检查，不建 Task 绑定，不赋正式交付资格 |
| context --task <id> [--stage <id>] | 生成阶段分层输入与顶部提示；阶段目标由生效流程派生 |
| resume [id] [--run <id> 或 --operation <id>] | 新 run 恢复或核实效果后继续同一操作 |
| cancel --run <id> / --operation <id> | 指定对象和执行 token 取消，核实实际停止，不改变业务 outcome |
| deliver [id...] --branch <ref> [--authorization-ref <ref>] [--plan] | 逐任务收尾；业务产物与任务资料分开提交，--plan 只读预检；完整目标 ref 明示，桥接声明授权来源，不默认启动 worker |
| archive [id] --branch <ref> [--authorization-ref <ref>] | 归档资料／继续步骤；提交同样核实目标及授权，不绕正常交付条件 |
| task close <id> --outcome <值> [--reason <说明>] [--force] | 业务结束并核对完成资格（`self` 接受 run 或主会话实施记录）；父任务完成还要求子任务全部结束并给出总体验收说明；`--force` 仅限用户明确要求且 `independent` 除外，凭据记 `forced` 与原因；不要求 Git 提交，不等于已归档 |
| status [id] [--run <id>] | 耗时、最近模型／工具活动、心跳，任务视图含「待澄清」`blocking`／`assumed` 计数；--events 仅观察 |
| session list/history | 查询身份和关系，由所属客户端读原生历史 |
| standards list/propose/review/apply/pending/migrate | 项目级候选、审阅决定与采纳；旧任务候选只读兼容并幂等迁移 |
| doctor / storage | 只读诊断，容量及 Knit 基线引用统计 |
| snapshot show / restore / unlock | 对照、明确恢复与解除，细则见 OPERATIONS |

`task list` 的输出契约：默认视图只有进行中／待归档／已取消三段，按优先级、ID、阶段、标题四列按显示宽度对齐，只打表头与汇总行；不打印资料路径、验证方式、父子进度与逐项阻塞原因。归档视图按月分组，行内给日期、稳定 ID、结论与标题，跨机历史与档案异常只在末尾汇总。`--json` 附 `scope` 与 `archivedCount`，归档数组只在 `--archive` 时返回。

run 返回 run ID，context 返回输入，deliver 返回操作 ID，不设同名 run 别名。prepare 先持久化目标 ID；持有本次调用的桥接或直接 CLI 入口取得并保存 ID 后确认 start，之前无模型或项目业务副作用。确认是入口内部协议，不是新增的人类许可，也不要求用户手敲两条命令。start 响应丢失按原 ID／status 核实，不创建替代运行。新 run ID／操作执行 token 隔离旧取消，不引请求级取消协议。CLI --wait 退出只结束观察，Pi 桥接执行工具取消须另向核心请求。

M1 的 --dev 仅增加本次及其 worker 的结构化 stderr，桥接分离诊断与业务结果；不自动存文件。Pi 会话开关与私有 JSONL 归 M3A，见 [开发者模式](OPERATIONS.md#7-开发者模式)。机械收尾和资料维护不需选模型，诊断不得自动增加模型回合。

## 5. 阶段执行、检查与模型选择

### 5.1 主 Agent 与阶段执行器

主 Agent 负责用户沟通、任务意图、阶段协调、结果汇总和收尾。需求讨论默认在主会话完成。

正式任务的阶段由 Knit worker 通过选定 AgentRuntime 创建或恢复独立 Session，首版直接调用本机 Pi CLI，cwd 指向任务执行目录。主 Session 与阶段 Session 均登记到统一索引；各阶段按阶段 id 保存引用，后续修复与重查优先恢复对应阶段的会话，原记录无法恢复时按第 9.4 节自动新建会话读取任务资料续做。恢复与兜底沿记录所属客户端。

阶段提示词由 `.knit/workflow.yaml` 的 `prompt` 指定；缺省或文件缺失时使用核心默认 agent 指令，不阻断执行。`tools` 不写表示全部放开，写了就是能力白名单：`read` 只读，`write` 改文件，`exec` 执行命令，`task` 使用任务工具，`external` 放开项目扩展／MCP／技能，`network` 放开网络。外部能力是显式 opt-in，声明后工具不存在要报错，不静默降级。

检查阶段可在既定需求内直接修复明确缺陷；其余发现和证据交回主会话或实施阶段。worker 的职责限于受委派阶段；任务创建、递归委派、提交、合并、推送与环境清理由主 Agent 和确定性工具协调。这些职责与工具策略不是操作系统沙箱；首版不宣称能阻止任意 shell 的所有越权副作用。阶段边界核对 HEAD／分支、index 与实际成果，发现未授权 Git 变化或无法确认的副作用时保留事实并报告 needs_attention，不借正常报告自动归档。

检查上下文包含目标、完成条件、适用规范、变更范围、实际文件和验证入口。实施报告作为待核对证据传入，检查以实际内容为依据。

检查阶段提供读取、写工具和必要验证能力，但写权限只覆盖任务范围内、问题与修复方向明确的缺陷；涉及需求解释、取舍、验收变化或扩大范围时以 `blocked` 交回，不自行决定。检查者修改后必须在报告列出实际 `changedPaths`，由核心与实际 diff 核对；接收通过后改动并入 scope。对自身修改的验证属于自检，不表述为已由另一独立执行者复核，也不默认追加一轮独立检查。shell 的可用性仍可能产生未声明写入，执行前后需比对相关代码与 Git 事实；无法确认的改动保留事实并报告。

### 5.2 模型选择

每次阶段启动按以下优先级确定最终模型：

1. 本次调用明确指定的模型。
2. 项目对该阶段配置的模型（`phases.<stage>.model`；配置键名沿用 phases）。
3. 阶段启动时主 Agent 当前实际使用的模型。

模型以 provider 和 model 标识传递，启动前由选定 AgentRuntime 检查可用性。跨平台使用模型标识时采用显式配置的映射；缺少映射、模型或鉴权时报告阻塞，保留用户选择。阶段请求与结果记录实际模型；创建和恢复 Session 均使用本次解析结果，后续阶段重新按上述规则解析。

指定讨论模型时，由独立上下文协助分析，主会话承担沟通与结论确认。收尾模型协助整理和复核，Git 操作由工具执行。凭据通过对应 AgentRuntime 支持的公开鉴权机制取得。

### 5.3 检查结论与有效范围

检查阶段结论为 pass、changes_requested 或 blocked，附覆盖、证据与未执行项。检查只在任务要求 `independent` 或用户明确要求时执行；`self` 任务的实施自检不自动升级为独立检查。用户明确要求的人工验收由主 Agent 核对并记录实际确认，首版不设专用门槛命令／字段；技术 pass 不能冒充人工完成。

检查记录由核心在结果接收时写入 `.knit/.runtime/checks/<run-id>.json`（不在 run 目录内）：任务／分支／run 身份、报告、结论、检查前后输入摘要和范围。指纹按版本化 SHA-256 规则保存路径、类型、模式和内容，删除项记为不存在。检查者直接修复的路径随接收并入 scope，凭据绑定并入后的 scope 摘要与实际 `changedPaths`／`selfVerified`。正式任务以 `lastCheckRunId` 为唯一候选，在检查获占用且正式接纳时更新；未获准的忙请求不算开始，已接纳后的失败不能回退更早 pass。输入缺失、版本未知、结果失败或摘要不符时重查。无正式任务的报告仅对该 run 的显式范围有效。

`self` 任务不要求 `lastCheckRunId`，以最近获准实施及当前输入／scope 作为完成依据；`none` 由用户明确选择并记录未验证。任务主文档与辅助资料按稳定任务 ID、任务内相对路径识别；已登记改名／归档操作可更新物理定位并核对相同内容，不因单纯搬动任务目录反复失效。其他路径变化、引用内容改写或业务输入变化仍需核对；不改写旧 run 凭据，以操作记录关联新位置。

成果 scope 按 Task 累积，恢复的新快照不清空旧成果。纯报告／结论的正式成果以显式文档纳入 scope，进度摘要不代替被验正文；小讨论仍可不建任务。需求、所选指令、授权输出、纯记录分别处理；规范本身为明确输出时以冻结旧版本为输入、新内容为成果，不机械退回讨论，新规则是否追用于本任务由主 Agent 确认。范围与数据权威见 [ARCHITECTURE.md](ARCHITECTURE.md)。

输入覆盖成果变更、相关未跟踪文件、验证依赖、已采纳提示词／规范和第 3.3 节输入区。stage/status/outcome、运行记录、运行引用、未生效的项目候选／旧任务候选／处理记录不计需求摘要；任务 ID 和分支另作身份校验。保存纯记录不会反复使通过结果失效，正式规则或业务要求改变仍需核对。

需求摘要与绑定分支分别校验，分支改变使旧检查失去交付资格，但不等于需求要重新讨论。HEAD／index 用于定位和诊断，纯提交或暂存变化不能替代内容判断。检查者声明的修复随接收并入 scope；未声明改动、有效输入变化或恢复源文件时重新核对。

阻塞发现和一般建议分别列出。默认独立性来自分离的阶段、Session 和实际复核，实施与检查可使用同一模型；不同模型是按用户选择配置的补充，不能替代验证。

### 5.4 核心 worker 与执行宿主

```text
用户／Agent → knit CLI → 核心：阶段、上下文、AgentRuntime、最终模型、cwd
                              ↓ 选择 ExecutionHost
                   内置 local             内置 REX
                   后台子进程             可见终端中的阶段 Pi
                              ↓
                 同一个 Knit worker → AgentRuntime → 原生 Session
                              ↓
                    核心校验结构化结果并推进阶段
```

worker 随 Knit 安装，负责运行协议、事件输出、结果回执、取消与资源释放。worker 始终由本机启动；`presentation` 决定阶段 Pi 在后台还是 REX 浮层执行，ExecutionHost 负责启动、定位和呈现。缺省 `execution.host: auto`：REX 环境与能力探测通过时使用浮层，否则回退 local。AgentRuntime 负责指令适配、模型与工具策略、原生 Session 和阶段执行。

Pi runtime 启动本机 `pi --mode rpc`，直接通过 stdin/stdout JSONL 发送请求并接收响应／事件；不导入 SDK 或其 RpcClient。用 CLI 参数指定模型、cwd、工具集合与系统附加约束；恢复只向存在且归属已核实的记录传 `--session`。默认关闭扩展、MCP、技能和上下文文件的自动加载，按输入计划显式提供阶段提示词、规范与上下文；模型配置和鉴权复用本机客户端，不另建运行时。启动后通过可用清单或 `set_model` 校验所选模型，再核对实际选择。当前 CLI 无法落实的必需资源／策略显式报告，不用 SDK 补齐。编排逻辑在 Knit 核心，本机模块启动同一 worker。

核心解析最终模型，worker 经 AgentRuntime 再核对。凭据留在对应公开鉴权渠道。默认 local 后台执行；REX 呈现时在浮层中输出模型文本、工具进度和结果摘要。需要用户决策时返回主会话处理。

### 5.5 内部可插拔模块

Knit 在源码内以可替换模块划分职责，模块随系统构建、安装和升级。核心按已知 ID 的装配表创建实现，新增客户端或宿主时增加实现并登记；项目配置只选择内置能力，不提供代码路径、模块名或可执行入口。

| 内部边界 | 职责与首版实现 |
| --- | --- |
| ClientAdapter | 生成项目桥接与入口、启动客户端、核实原生会话上下文；首版 Pi |
| AgentRuntime | 阶段指令、模型和工具策略、原生会话、运行与取消；首版本机 Pi CLI 协议 |
| ExecutionHost | 启动与定位统一 worker；local 与 REX（自动探测） |

同一客户端的 ClientAdapter 与 AgentRuntime 共享稳定客户端 ID；宿主 ID 独立。实例按主会话或 run 构造，失败清理本次已取得资源，结束后按依赖顺序释放。运行中使用的实现保持到工具终态，切换选择影响后续运行。

这些是内部代码契约，不是对外插件 SDK。首版无需第三方 Manifest、安装器、授信存储、公开注册 API 或动态热加载；配置不能导入任意仓库代码。worker 仅装配所选 runtime，原生客户端 API 留在对应模块。确定性测试通过测试装配表注入 fake 实现。

### 5.6 运行协议

每次 worker 执行使用新 run-id。CLI 发布请求与启动意图，worker 以自身身份取得占用、重新核实身份及预期需求、冻结 inputs 并完成实施快照，之后才允许调用阶段模型／写代码，不做执行锁跨进程交接。资料位于 `.knit/.runtime/runs/<run-id>/`。

| 文件 | 写入方 | 内容 |
| --- | --- | --- |
| `request.json` | 核心 | 发布后不改的身份／阶段、发起方、版本、purpose、预期需求／基线、模型、工具与恢复引用、acceptanceOperationId；diagnostics.enabled 仅技术标志，不进业务摘要 |
| `inputs.json` | worker 内的核心 ContextPlanner | 取得占用后冻结输入、规范／阶段提示词、基线引用与指纹，发布后不改 |
| `launch.json` | 核心 | planned/starting/confirmed/failed 启动意图、句柄与实例证据 |
| `instructions.json` | worker | 已落实的注入清单：来源 ID、作用域、指纹、注入途径、版本和原生产物位置 |
| `state.json` | worker | 实例身份、运行状态、Knit／原生 Session 引用和已知子进程定位 |
| `result.json` | worker | 不可变终态、结构化报告、原生引用与本 run 增量用量，不证明 Git 收尾 |
| `diagnostics.json` | worker | runtime 启动失败时的一次性 stderr 尾部与失败码；只作辅助证据，不作权威回执、不参与状态机 |
| `acceptance.json` | RunAcceptanceService | 接收检查点：来源目标、binding before／after、scope 与 check 凭据、输入／规范摘要 |
| `snapshot/` | 核心 | preparing/ready/failed 恢复对照及覆盖说明 |
| `events.jsonl` | worker | 只作脱敏进度观察，半行／重复不作为完成证据 |
| `cancel.json` | 核心 | 取消意图：目标 run、operation 与 owner token，按需建立 |

成果 scope 与检查凭据不在 run 目录：接收时由核心分别写 `.knit/.runtime/tasks/<task-id>/scope.json` 与 `.knit/.runtime/checks/<run-id>.json`，发布后不改，资格由当前目标版本推导。

未建正式任务的执行使用空任务 ID。临时启动／指令资源放在本 run 的 `native/` 下，原始对话与工具记录引用客户端自己的原生 Session，不另存完整转录。取得原生引用时只在本次 state 登记 opening 候选；模型可在参数与指令就绪后启动，无需先让空会话落盘。核实原生 ID、归属和持久化后才置 available、更新可恢复阶段引用；失败候选不覆盖旧引用，父会话失联时可从原 run 补确认。 执行与报告均有效时，原生引用暂不可恢复只记引用原因，不单独触发模型重跑；本 run 的结果证据仍须持久化，后续必要续做按第9.4节处理。

代码阶段、Git 收尾、初始化和有效输入修改共用项目执行占用；主会话记录与项目级规范候选可并行使用短锁／元数据占用，不等待长阶段结束。记录写入只能改记录区，读改写核对当前版本并原子替换，避免覆盖其他变更。原生事件登记不推进阶段，具体顺序见 [占用细则](OPERATIONS.md#2-占用与解除)。 本机共享执行锁根为 `~/.knit/locks/`，项目键按规范化根、阶段 Session 键按客户端原生身份生成；它不提供用户级配置或跨机协调。具体获取顺序和新会话换锁见 OPERATIONS 第2节。

终态为 `completed`、`failed`、`cancelled`。正常 completed 要求合法报告，缺失或无效记 failed；已确认中止的 cancelled 可只保存原因、部分结果与工具终态，不因缺完整业务报告改判失败。worker 完成不代表任务或交付完成；建议类输出不能推进业务。核心复核协议、身份、请求和实际证据。 运行状态和结果另记录本次原生起止 entry／leaf 引用及增量用量，无法取得则如实 unknown；同一原生文件后续追加不成为旧 run 的内容，不能只用当前整个 Session 统计冒充本 run。

| 报告 | 最小字段与判定 |
| --- | --- |
| 固定字段 | `summary` 为文本，`validation`、`blockers` 为数组，可为空。每条验证记录方法、结果和证据，结果为 `pass`、`fail` 或 `not_run` |
| 阶段声明字段 | 按 `workflow.yaml` 的 `report` 校验；`paths` 类型（通常为 `changedPaths`）必须与实际 Git 可见差异一致，`bool` 与枚举按声明核对 |
| `onVerdict` | 报告值命中时跳转声明目标；未命中的普通完成走顺序下一阶段 |
| 收尾 | 锚点 `deliver` 不产生 worker 报告；交付由主会话协调，commits、archivePath、pending 来自核心操作结果 |

主会话的讨论确认与收尾事实写核心操作和任务记录，不伪造 worker run/result。正常执行结果由核心按 request 中固定 acceptanceOperationId 复核并接收。进程在接收中断时先恢复操作，不再执行一次模型阶段；worker 崩溃后的核实结论另记 run.reconcile，不能冒充正常报告。

启动响应丢失时，按 run 和 handle 查找原运行。父会话退出、窗口关闭或心跳停止后，核对回执、实例和存活证据。状态未知时保留占用并调查，确认原运行终止后才允许重试。旧 PID 和旧状态标记需结合实例身份核实。

取消基于已持久化并确认的 run／operation ID 和执行 token；ID 前无执行。worker 等待工具终态，取消与完成用同一短临界区裁定；超时仅待确认，保留占用。确定性操作核实当前效果后暂停，不回滚 Git 或文件。恢复新 ID／token，单独观察退出不发送执行取消。

同一项目不并行运行两个代码阶段或 Git 收尾。主 Agent 可持续讨论并保存纯记录；新要求先记待应用，真正修改有效输入在旧工具结束后进行。Knit 占用不约束外部编辑器或用户直接 Git 操作，阶段边界仍核实实际文件与身份。

首版保留 Session 索引、绑定与运行资料，归档不自动删除。`storage` 统计体积并在超阈值时提示，`doctor` 检查引用、占用和孤儿 run；不自动 gc。原生 Session、快照与 request 按私有权限保存，恢复链和版本约定见 [运行细则](OPERATIONS.md)。

请求只保存必要环境变量的名称与凭据引用，不序列化环境值、token 或 API key。凭据经受信运行时通道提供。Knit 写入任务、规范或配置前，以及限定路径提交前，扫描待写内容与本次实际差异中的常见 token／私钥模式；命中时暂停并只报告类型和位置。外部工具不受 Knit 事前写入控制，提交前仍执行扫描；扫描不构成无泄露证明。

### 5.7 REX 执行适配

阶段呈现（presentation）在 prepare 时一次解析并落盘，start／resume 不再探测或换宿主：

1. 调用级 `--rex`／`--local` 优先；二者同时出现报 `invalid_request`。
2. 否则按 `.knit/config.json` 的 `execution.host`：`auto`（缺省）在派发前探测，`local` 始终本地，`rex` 强制使用 REX。
3. `auto` 同时满足 `REX_SESSION` 与 `REX_BLOCK`、`rex` CLI 可执行（`REX_BIN_DIR` 或 PATH）、`rex api list --json` 含 7 个必需方法时才使用 REX；否则回退 local 并记录原因。探测复用 `RexApi.check()` 与 `REX_REQUIRED_METHODS`，不新写协议。
4. `--rex` 或 `host: "rex"` 不可用时报 `rex_unavailable` 并保留具体原因（环境缺失、CLI 缺失、连接失败或缺方法），不静默回退。

选择 REX 后，local worker 仍在项目内完成认领、输入冻结和快照；StageRunner 在 REX session 内用 `session.new_layer` 新建可见终端，运行 Pi TUI + worker 扩展，标签为 `knit <run-id>`，通过 bridge 观察状态、steer 与 stop。Rex 子进程沿用用户当前主题、不传 `--no-themes`，主题发现与主会话一致。已有 `rex.json` 时按标签与身份恢复发现，不重复建浮层。REX window 对应 session 内的窗口／标签页。浮层创建后即最小化；run 到达终态（completed／aborted／error，含恢复发现）时，宿主按 `rex.json` 的 `layerId`（缺失时按 `blockId` 反查）调用 `session.close_layer`，取消／失败走同一路径，关闭失败只忽略、不改变已落盘结果；`closeOnSettle=false` 仅用于测试／调试时保留浮层。

`presentation`、`presentationSource`（explicit/config/auto）与 `presentationFallbackReason` 写入不可变 request；活动 run 的呈现不可变，`run resume` 沿用旧值。浮层创建或阶段 Pi 启动后的失败不切换宿主，沿用 `rex_start_failed:*` 与既有失败语义；用户重新派发时按当时检测结果重新解析。`run list`／`run status`／`knit status --run` 显示实际宿主、来源与回退原因。`run check --scope` 为非正式检查，仍不支持 REX。桥接 `knit_run` 不传 `--rex` 时继承扩展进程环境，按同一规则自动生效。

### 5.8 客户端适配与原生会话

Knit 的初始化、任务、阶段、Git、记录与恢复由独立 CLI／核心完成。Pi 是首个客户端与执行后端；后续 Codex、Claude Code 增加对应内部模块，核心流程继续复用。

Pi ClientAdapter 自动生成 `.pi/extensions/knit.ts`，并在 `AGENTS.md` 受管块链接流程配置与索引。桥接使用公开 API 提供 Session、模型、事件、命令／工具和上下文入口，业务调用 Knit CLI。共享桥接由自身文件位置定位项目，再读取本机安装映射，不能按临时 cwd 或项目配置导入其他核心代码。AgentRuntime 单独封装本机 Pi CLI 的启动与公开 JSON 协议。

Pi 桥接执行工具被取消时，向核心发送当前调用已关联的 run/operation ID 与执行 token，观察真实终态，不能只结束等待便宣称取消；直接 CLI 观察退出不等于停止执行。

项目桥接在加载与会话变化时登记主 Session，每次调用重新提供当前身份、有效会话分支和模型。`start`／`session attach` 可核实登记；`selectedTaskId` 是当前路径选择的已核实快照，来源见第 9.1 节。CLI 人工直接执行可无原生主会话，发起方记为 CLI、主 Session 引用为空。

无法可靠取得实际上下文时显式参数或阻塞，不猜旧模型。M0 前置验证必须实际加载／reload 桥接，读取 Session／模型，验证轮外完成消息投递及是否触发真实模型回合、忙时队列与上下文变化、agent_settled、受控工具取消和新进程恢复，详见 [M0 门槛](TECHNOLOGY.md#61-m0-前置验证)。

原生引用由所属客户端模块解释，主会话和阶段 Agent 可用不同客户端。恢复与兜底按已记录客户端选择 runtime；客户端实现缺失或当前运行能力不满足时阻塞，仅旧原生记录不可用则按第 9.4 节自动新建会话续做。切换客户端须明确建立新 Session 并关联历史，不能用 Pi 解释 Codex 或 Claude Code 格式。ExecutionHost 变化只改变 worker 启动与展示。

### 5.9 用量记录与停止条件

首版记录各 run 的 token、费用和耗时，不设置累计 token、费用或固定总时长的自动停止阈值。大任务可分步推进、压缩上下文或恢复原生 Session，不能因累计消耗较大就判断任务不值得继续。

停止来自用户取消、真实执行错误／阻塞、未解决检查达到修复轮次上限，或原生工具明确的执行条件；心跳可疑阈值只触发核实。用量缺失标为 unknown，不按零计，也不因无法计费而阻塞正常执行。

统计按本 run 新发生的调用增量计，不重算恢复会话中的历史消费。归一化为总输入 `inputTokens`（含缓存）和输出 `outputTokens`，`totalTokens = inputTokens + outputTokens`；缓存读写是输入的子集，单列展示但不重复相加。供应商原始字段保留，无法无歧义映射时不伪造总数。费用按供应商规则另计，缓存用量不等于同价消费。完整约定见 [运行细则](OPERATIONS.md#5-用量存储与诊断)。

## 6. Worktree（后续设计）

首版不实现任何 Worktree 创建、连接、枚举、交接、迁移或清理。完整规则独立保存在 [WORKTREE.md](../research/WORKTREE.md)，当前目录执行按第 3.7 节处理。后续 Worktree 实现同样以各执行目录自己的 `.knit/workflow.yaml` 决定阶段、提示词与工具；流程配置不跨执行目录合并。

## 7. 记录更新与防漏

- 讨论结论及时写入任务记录；有效目标、条件和约束分别维护在输入区。
- `task record` 通过短时任务文件占用读改写记录区，并校验未覆盖输入；不等待正在运行的阶段释放执行占用。
- 记录操作不能修改 branch、stage、status 或 outcome，也不推进阶段；worker 以请求冻结的输入为准，后来记录不能偷偷变成当前指令。
- 收尾短锁封存记录；封存中补记明确未保存，不自动转存或留修改，结束后按原 Task ID 重试为新档案资料修改，不冒充原提交。
- 运行中的新要求先记录为待应用，主 Agent 可选择等本轮结束或请求取消；工具终态明确后再更新有效输入与 stage。
- 实施、检查、失败和暂停后保存结果、证据与下一步；已生效输入变化会使旧检查失效。
- 核心负责机械校验与状态写回，桥接负责原生入口；语义遗漏由主 Agent 结合需求复核。

## 8. 规范、冲突与例外

规范由三层组成：项目入口、语义索引、按需正文。入口提供工作流与规范位置，索引说明每份规则的范围和用途，Agent 按任务加载实际相关内容。

实施和检查前确认适用规范。规范引用包含路径与适用理由，任务例外记录范围、理由及授权依据。通用规则变更作为项目级变更处理。

规则冲突时结合宿主指令层级、项目要求和任务授权说明取舍；无法判断时报告具体冲突。相关规范实质变化后，重新判断方案与检查覆盖范围。引用失效由程序提示，内容是否充分读取与采用由 Agent 核实。

### 8.1 阶段提示词与平台注入

阶段输入由核心提供的职责与操作约束、核心生成的顶部提示行、`.knit/workflow.yaml` 中该阶段的 `prompt`、可选平台补充、当前任务与规范引用组成。锚点 `start`／`deliver` 没有阶段提示词；默认模板的 `.knit/agents/implement.md` 与 `check.md` 只是示例，阶段可复用同一提示词文件，也可不声明 `prompt`。

提示词文件缺失或未声明时使用核心默认 agent 指令，不阻断执行，也不把整份流程降级；配置本身非法时按第 9 节降级为 `start → deliver`，不套阶段提示词。阶段 × 报告字段／工具能力／停止条件的对照见 [ROLE-CONTRACT.md](ROLE-CONTRACT.md)，实际行为由完整装配后的提示与核心校验共同决定，不以单个文件长度或措辞代替。

`.knit/agents/runtimes/<runtime-id>.md` 保存平台特有的工具用法、输出约定等补充。每个上下文只选择自己的阶段提示词、所属客户端补充和相关任务／规范；辅助资料按需读取。任务、流程配置和 Git 规则来自核心与项目资料。输入冲突按宿主指令层级与任务授权处理，额外载入资料遵守本次工具和资源策略。

核心生成统一注入计划，每项包含稳定来源 ID、内容指纹、作用域、优先级与更新版本。阶段提示词、流程配置、规范选择和任务上下文由核心确定；客户端适配只处理原生接口、参数、文件格式与加载方式。

阶段由 AgentRuntime 落实上下文计划，主会话由项目桥接转交计划并通过原生能力落实；自动加载、显式注入与受控资源去重。资料引用不等于已读证明，记录计划与可确认的生效清单。桥接只落实核心选择，子 worker 默认不加载该扩展。

主会话的生效清单随 Session 索引登记，子会话的 `instructions.json` 保存实际途径、指纹与版本并由索引引用。Pi 使用受控系统提示与资源加载；后续平台使用其公开指令入口。本 run 的 `native/` 只放临时启动／指令资源；新建阶段会话由 Pi CLI 在 `.knit/.runtime/pi-sessions/` 自行保存，跨 run 沿原记录追加，不放进某次 run 的临时目录，也不复制成第二份聊天库。主会话继续使用 Pi 原有位置。已有 `AGENTS.md` 与平台配置按项目资料维护，适配层核对当前项目与适用用户规则已按计划生效。

恢复时比较上次已生效清单与当前计划。仍被原生会话保留且未变化的项保持一次；变化项使用客户端支持的更新方式明确生效。历史消息与报告标为背景资料，当前职责、模型与工具策略由本次计划确定。仅旧记录导致必要更新无法落实时按第 9.4 节新建会话；新会话也无法落实必需策略或确认所需指令生效时仍阻塞。

### 8.2 规范持续演进

规范索引按适用范围链接设计、开发、测试规则，正文按需增加；既有权威文档优先引用。任务先查索引再读相关正文。

规范是项目事实，不依附任务。讨论、无任务交流、实施发现的重复问题、检查缺口和收尾复盘都可形成规范；保存候选或采纳不要求 taskId、任务存在、阶段或任务收尾，也不为保存规范暗建任务。

- 用户明确长期规则且含义清楚时，直接整理采纳并说明替换内容，不重复询问同一决定。
- Agent 判断足够明确时可自行采纳；依据来自讨论决定、已验证实践或多次一致处理，适用范围清楚。区分长期约定与本次例外，不替用户填补未决目标或偏好。
- 推导规则与已有规范冲突时，先提出冲突、影响和建议，取得用户决定；未决定不改正式规范。
- 未明确的可复用内容用 `standards propose` 保存为项目级候选 `.knit/standards/candidates.md`，记录来源、问题、证据、适用范围、建议规则与验证／示例；一次性要求只保留本次范围，不提议为通用规则。
- 采纳用 `standards review --decision applied` 记录理由与目标，再由 `standards apply` 机械写入正式规范并补索引；自行采纳同样记录依据。延期／拒绝有理由即可，不强制新规则生效。

项目候选与审阅回执不进入正式规范摘要或任务需求摘要；回执按候选集合摘要匹配，不要求分支一致。旧任务目录的 `standards.md` 保持只读兼容：`standards list --task <id>` 仍可查看，`standards migrate` 幂等迁入项目候选文件且不改写原文件。交付不因候选未审阅而阻塞，也不把规范处理重新绑定任务。旧回执仍可读取，历史事实不撤销。

正式规则写清约定、正反例、失败边界和验证入口，后续任务从索引读取；只收录通用且有证据的规则，不要求每任务都增加内容。采纳更新正文和索引，正式规则变化按第 5.3 节影响相关检查。Agent 在正常回复末尾简短说明本次沉淀的内容、适用范围和位置；需用户决定的问题当场提出。

## 9. 主会话、Session 与上下文集成

### 9.1 主会话任务关联

主会话任务选择随原生会话有效分支保存，核心统一解释选择／清除事件；Pi 桥接把这些事件写入当前路径的专用自定义条目。`selectedTaskId` 是索引中经核实的当前选择快照，附原生分支与关联条目引用，独立于执行绑定。清除操作追加空选择事件，不能让更早选择再次生效。

树切换后，桥接提供当前有效路径，核心从关联事件恢复并校验选择。选择／清除带操作 ID，桥接写条目前再次核对原生上下文仍匹配，再按持久化回执更新索引；中断重试核实已有条目，不能重复应用或并发改写活跃原生文件。无可用桥接上下文时 CLI 用显式 `--task`，不设置全局选择。 空主会话若条目尚只存在内存，返回待持久化而不宣称已保存选择；自然落盘后由桥接补确认，不伪造消息或额外调用模型来强制保存。

CLI 只使用与本次调用匹配的上下文。无上下文的正式任务调用须显式 `--task`，非正式检查按第 4.3 节使用 `--scope`。任务改名按 ID 更新；归档操作完整成功后结束该任务关联，不能清除后来选择的其他任务。旧路径中的已归档选择仅供历史查询，状态校验不会将其重新激活。

### 9.2 会话与 Git 分支

| 变化 | 行为 |
| --- | --- |
| 新主会话／Fork | 新会话默认无选择；Fork 核实来源并从有效路径恢复候选，当前任务仍需校验 |
| 原生会话或对话树切换 | 重新核实当前上下文与任务，原生历史按有效分支读取 |
| Git 分支变化 | 按第 3.5 节核对可见性和绑定，暂停不匹配任务 |
| 清除任务或归档 | 清除活动选择，磁盘与历史记录保持实际状态 |

原生会话分支与 Git 分支分别处理。没有可靠事件或上下文证明时，不根据最近文件、最近 PID 或其他 Session 的模型自动推断当前状态。

### 9.3 运行状态与持久化

输入变更先保存意图；活动 run 尚未终止时不改有效输入，后续代码阶段与交付需先应用或明确撤回该变更。输入与记录、启动／worker、取消、检查、选择、规范、操作和封存的完整规则见 [STATES.md](STATES.md)。各文件唯一写入方与意图／效果顺序见 [ARCHITECTURE.md](ARCHITECTURE.md)。

提交、阶段写回与归档的断点记录由本机 operation 元数据仓储保存，实现为 M0 选定的 SQLite 元数据库。原生工具记录仍由客户端保存，run 产物与元数据按版本核验，见 [版本约定](OPERATIONS.md#5-数据版本与升级)。

桥接在当前宿主内用一个可销毁的轻量定时器，默认每 5 秒调用 `knit status --run <run-id> --json` 查询自己发起的未结束 run，不建立常驻服务或新状态库。结束、会话／树切换或宿主关闭即停止相应观察；reload 后只从当前有效路径与绑定核实可观察引用。发消息前再次核对原生 Session、发起条目仍在有效路径及任务关联，按 run ID／终态版本检查已有原生通知去重；持久化未知不自动重发，未匹配只保留核心结果供查询。通知按是否需要处理分流：失败、取消或结果待接收时用 follow-up 队列并唤醒主 Agent，不抢新输入；完成且结果已被接收的通知以 nextTurn 进入下一轮上下文，只展示、不启动模型轮次。结果尚未接收时只通知待同步和下一步，status 不偷偷接收或重派。投递不作执行回执，也不保证模型轮次恰好一次；业务副作用仍按核心幂等检查点核实。完整轮询链路已由 015 真实桥接验收；定时回调实验不代替该验收。

### 9.4 阶段 Session 恢复

默认 `agent.resume: "prefer"`，含义是优先恢复原生会话，原记录无法恢复时自动新建会话从任务文件续做，无需再次确认。同一任务和阶段已有 Session 引用时，恢复与兜底均沿其所属 AgentRuntime；首次进入阶段才按调用与项目配置选择客户端。进程退出后两条路径都启动新进程，区别是加载旧记录还是创建新会话。每次执行使用新 run ID，旧 run 的终态与回执保持原样。

1. 按绑定和 Session 索引找到原执行目录、旧 run 与原生记录，核实当前仓库、任务、会话种类和阶段。旧 run 仍存活时观察，状态未知或工具终态不明时调查并保留占用，不同时另开写入执行。
2. 确认旧 worker 及其工具已终止后，按第 5.6 节取得占用并再次核实状态。校验所属客户端、当前 cwd、模型与必需输入；客户端缺失、模型不可用或当前任务／目录归属不明仍阻塞。已登记 adopt 可保留原阶段 Session；本次请求使用当前分支和有效输入。
3. 记录存在、可读且兼容时，由所属 AgentRuntime 加载指定原生 Session，并核对实际 ID 与历史；不能因 CLI 返回成功就认定恢复成功。重新解析本次模型和工具策略，落实最新任务、文件与注入清单。
4. 原记录缺失、损坏、不兼容，或加载后身份不符／原生恢复失败时，保留旧引用和原因，在同一客户端创建新 Session。新会话读取当前任务要求、适用正式规范、进度记录、已有 run 事实／检查发现及实际代码和差异，核实已完成与待完成工作后继续。进度记录不代替需求，旧检查结论不自动当作当前通过。
5. 新建成功并核实可用后更新阶段引用，保存旧 Session 来源与兜底原因并向主 Agent 报告。无法启动新客户端／落实本次输入时按执行失败处理，不循环重建；已有效完成执行而仅原生引用不可恢复时按第5.6节保留执行事实，不重复模型。新会话不重置 Task ID、stage、修复次数或累计 scope，不因会话更换本身使检查失效；实际输入／代码变化仍按原失效规则处理。明确切换客户端按第 5.8 节处理，兜底不自动换客户端。

实施修复复用实施 Session，独立重查复用检查 Session；检查请求带入当前内容指纹与待核对范围。任务目录改名只更新资料定位。后续更换执行目录或终端展示方式时，仍需核实原生引用、cwd 与资源边界。

### 9.5 统一 Session 索引

主／子会话在本机 Session 元数据仓储登记，实现为 M0 选定的 SQLite 元数据库；按所属客户端、原生 ID 与必要实例定位匹配，首次分配稳定 Knit Session ID。记录包含：

| 字段组 | 内容 |
| --- | --- |
| 身份 | 协议版本、Knit Session ID、所属客户端、适配版本、原生 ID 与定位 |
| 职责与关系 | 主／子会话种类、阶段、父 Session ID，以及 Fork／明确切换／恢复兜底产生的来源引用；兜底原因记录于本次准备结果 |
| 工作关联 | 参与任务、绑定分支、run、原 cwd、会话检查点；主会话另存选择快照及其有效分支／关联条目引用 |
| 可用性 | 最近核实时间、原生记录是否可读取、关联运行的已知状态与缺失原因 |

主会话由 `start`、`session attach` 或已核实的调用上下文登记；CLI 直接执行时可没有原生主 Session。新子会话启动前分配 Knit Session ID，worker 取得原生引用后写状态，核心核实并补齐索引。记录原子更新，失联后可按回执补齐；父 Session 记录真实创建来源，每次 run 另记发起方。索引保存定位、选择、关系和可确认的指令信息，原始历史仍在所属客户端。

Session 查询可按任务、客户端、主／子类型和父子关系定位，再读取对应阶段报告或指定历史片段。原生文件缺失、客户端卸载或项目迁移后保留索引并显示待核实原因。索引缺失时，通过当前客户端身份、任务引用和原 run 回执核实重建。

### 9.6 主会话每轮上下文注入

主会话每轮处理用户需求前，桥接使用宿主公开的模型调用前事件或等效能力（不假定存在专用对话拦截 API）注入当前工作上下文。注入内容：当前选定任务的稳定 ID 与 stage、任务业务摘要、待决项、待应用草案与活动运行必要摘要、下一步规则和阶段提示词入口（当前 plan／design／research 入口，按第 3.4 节）；无选定任务时注入无任务入口规则，不虚构任务状态。

注入是每轮刷新的当前快照，不无限堆叠历史正文；任务切换、换 Session、资料更新或取消后，下一轮取最新适用信息，不串用旧任务或旧阶段。活动 run 期间注入展示草案与冻结事实，但不改写活动 run 输入；注入内容只作主 Agent 行为引导，所有写动作仍经核心按授权、阶段、锁和版本重新核对。注入失败或宿主能力缺失时按既有准入报告具体原因，不降级为静默无注入；正常闲聊、查询与轻量修改在无任务上下文下保持可用。实现与真实宿主验收见任务047。

## 10. 提交、交付与归档

### 10.1 策略与授权

deliver 是唯一正常交付处理器，由主会话协调确定性工具，不启动交付辅助 worker。所有会提交的 deliver/archive 必须显式 --branch <完整本地ref>，与实际及绑定分支一致；桥接 Agent 声明 authorizationRef，终端代调可 --authorization-ref，operation 记录来源引用／版本，不把分支参数当人类授权证明。直接 CLI 只记录调用声明，Agent 代调仍需已有授权。

认可的项目策略写在项目规则文件（如 AGENTS.md 的交付约定或显式授权来源），模板不默认授予主分支提交许可。候选默认分支依次来自 delivery.defaultBranch、本地 origin/HEAD 或 unknown，不按 main/master 名猜、不联网探测。检测用于展示和审计，不授予权限；unknown 不阻明确授权。主 Agent 核对来源语义，核心验证引用／版本和目标，已有授权覆盖不重复询问，adopt 不附提交许可。详见 [授权细则](OPERATIONS.md#51-提交目标与授权来源)。

deliver 由核心 CLI 同步执行；单独观察断开不等于取消，实际执行程序中断则按操作记录核实工具和 Git 效果后恢复，不承诺关闭界面后自动跑完整个交付。不额外建设后台操作调度器。

交付／归档不检查规范候选；候选未审阅、延期或仅在旧任务文件中保留都不阻塞。规范处理不重新绑定任务；本任务明确采纳并写入正式规范的路径仍按实际改动进入资料提交。

后续增加项目可配置的 `merge` 交付，使用 `delivery.target` 或本次指定的本地目标，缺少目标时报告阻塞。合入遵守已有授权及明确约束；推送、PR、发布和部署分别取得对应授权。完成条件要求首版尚不支持的交付操作时，明确报告待人工完成，不将其标为已交付。

### 10.2 产物与资料提交

完成资格有效后整理收尾提交。任务资料与实际开发产生的业务产物分开提交：业务产物先形成工作提交，任务记录、交付记录和必要共享元数据形成独立任务资料提交，归档移动再形成归档提交。多个已完成任务可逐项处理，每个任务保留自己的提交记录，不合并成整批大提交。只有文档／研究报告等实际成果进入产物提交；任务目录本身不进入产物提交。

1. 列出候选任务路径，结合任务开始时已有改动确认归属。
2. 核对同文件混合修改，范围无法可靠区分时先整理或明确归属。
3. 使用限定路径提交，程序检查实际 Commit 范围，并保持其他路径的暂存与工作区状态。
4. Hook 失败或其他进程改变内容时保存现状，核对检查有效性后继续。

自动提交使用明确路径集合。暂存整理保留用户现场；stash、reset、amend、rebase 或历史改写需要对应的明确操作意图。

产物提交说明由主会话起草，经 `deliver --message-file` 传入；核心只校验、拼装并持久化，不调用模型。文案为 UTF-8 纯文本：首行 1–72 个字符，空行分隔正文，正文非空且不超过 4000 个字符，整个文件不超过 8 KB；首行不得以旧机器前缀 `knit: ` 开头、不得只含任务／操作 ID，正文行不得以保留键 `Knit-` 开头。非法或空文案在创建操作、`git add` 与修改 Task 之前拒绝。未提供文案时使用事实型模板正文并记录 `message_source: template`；交付结果与 `--plan` 都显示来源。三类提交末尾统一附 `Knit-Task`／`Knit-Operation`／`Knit-Stage`／`Knit-Verification` trailer；恢复与合入按 trailer 识别，无 trailer 时回退旧 `knit: <stage>` 单行格式。文案按阶段持久化，重试复用已保存文本，新文件被忽略并记录 `message_ignored_on_retry`；已提交说明不做 amend。

### 10.3 交付顺序与冲突

`local`：业务产物提交 → 整理最终结果 → 任务资料提交 → 在当前项目封存并归档 → 归档提交 → 报告当前分支与目录。

后续 `merge`：产物提交 → 资料提交 → 核对源与目标目录、取得目录占用 → 核对目标 index 清洁并执行已授权合入 → 验证整合结果 → 转交任务资料与绑定 → 在目标目录归档 → 归档提交。

以下为后续合入的冲突处理规则。

目标目录存在运行中的阶段或状态未明的占用时，先核实其终态。目标 index 已有暂存内容时，保留该内容并报告待处理，处理后再合入。

只交接本任务资料、持续维护一个任务正文位置，可以减少记录分叉。合入前核对以下情况：

- 同路径未跟踪草稿可能阻挡 Git 覆盖。核对交接回执后，原稿可转存恢复备份；含新增内容时先保存并判断归属。
- 已跟踪文件或 index 存在其他修改时，保留现场并明确范围。双方分别提交同文件的不同内容时按实际冲突处理。
- 代码、规范、配置和忽略规则的分支变化按双方差异及任务要求核对。解决冲突后重新判断检查覆盖；语义取舍不明确时保存现场并请求必要决策。

全局选择 ours／theirs、删除挡路文件或还原用户修改不能代替冲突判断。合入失败保留源 Worktree 和提交；已经成功的合入由操作结果识别，后续从归档等剩余步骤继续。

### 10.4 归档提交

移动前核对目标与引用。输入按 clarify/change 应用，完成资格不适用先复查；纯路径与记录由确定性操作核验。补齐结果、验证、遗留、产物提交、资料提交和结束结果，整体移到 archive/YYYY-MM/<原目录>/。封存中补记明确未保存，不自动转存或留修改；结束后按原意重试，作为档案新资料修改，说明不含于原提交，是否提交按已有授权，不重开业务。

首次归档记录任务 ID、源路径、目标路径和归档月份。跨月重试沿用该操作目标。移动与归档提交分别记录结果；后续环境清理另记独立结果。移动后提交失败时显示“已移动、待提交”，按 ID 和回执继续。归档提交只含任务资料移动；业务产物已在独立产物提交中处理，不重复纳入。

归档提交范围为本任务源／目标路径及实际相关引用。归档文档保存工作 Commit，归档 Commit 哈希由 Session 操作结果和最终报告提供。归档提交使用确定性模板 `chore(task): archive <目录名> (<taskId>)`，正文记录 `tasks/<目录名> → tasks/archive/<YYYY-MM>/<目录名>`、产物提交与资料提交短哈希；资料提交使用 `chore(task): <任务标题> (<taskId>)`，正文记录结束结果、验证依据、产物提交与资料。模板首行按 72 个码点截断，trailer 规则同 10.2。

任务可按完成、取消或被替代归档。取消／替代只归档资料，不要求把未完成源码检查成 pass，也不默认提交部分代码；已有提交如实引用，没有就记录无工作提交，不制造空 commit。暂停保留活动任务和绑定。

## 11. 失败与中断恢复

每次正式实施前先建立可核对的本机快照；失败、取消或部分写入后保留现场，展示对照，不自动整仓还原。`snapshot show`、逐路径 `restore`、索引保护与未跟踪文件范围见 [恢复细则](OPERATIONS.md#3-实施快照与显式恢复)。

| 情况 | 处理 |
| --- | --- |
| 讨论尚未形成方案 | 读取已保存结论和待决项继续 |
| 换 Session 继续任务 | 按 ID 查绑定，核实当前项目、执行目录与旧 run |
| 绑定缺失或路径异常 | 用本项目任务身份与运行记录核对；涉及其他目录时保留记录并阻塞 |
| 原主会话继续讨论 | 更新当前项目的任务记录；输入显式分类并核实旧执行／检查适用性 |
| 阶段中断或取消 | 核对回执、实例、文件变化与遗留进程，终态确认后优先恢复阶段 Session |
| 原 worker 已退出，原生 Session 有效 | 由记录所属的 AgentRuntime 加载指定会话，校验当前模型、注入清单、cwd 与工具策略 |
| 恢复时当前客户端或项目默认变化 | 按旧 Session 的客户端归属恢复；客户端不可用时报告阻塞 |
| 原生 Session 明确不可恢复 | 保留旧引用与原因，确认旧执行结束后沿原客户端自动新建会话，读任务文件与当前现场续做 |
| REX 断连或启动响应丢失 | 查找原 run 与 handle，核实后重连或结束处理 |
| 所需客户端模块不可用 | 保留原生引用与回执，报告版本或能力原因；不切到其他客户端恢复 |
| 实施完成、检查未完成 | 从检查继续 |
| 检查后代码变化 | 判断并补充检查范围 |
| 产物／资料提交失败 | 保留修改、暂存与已生效提交，处理原因后按操作重试 |
| 已提交、记录落后 | 核对基线、Commit 和文件后补记录 |
| 后续合入成功、归档未完成 | 连接目标位置，继续归档 |
| 归档已移动、提交失败 | 按回执定位并完成归档提交 |
| 后续归档成功、清理失败 | 报告成果与保留环境，单独处理清理 |

收尾记录 operation ID、本次执行 token、预期状态与效果。取消停止后续步骤，核实在途进程，保留已发生 commit/move，不自动回滚或改业务 outcome。新尝试使用新 ID／token，跳过已验证效果，不另建请求级取消路由。

## 12. 列表与资料维护

调用入口见第 4.3 节；`doctor` 只读检查状态与引用，`storage` 显示容量及告警。首版保留恢复资料，不实现自动 gc。

首版列表采集当前项目活动区及 archive/YYYY-MM；默认视图只列未归档任务（进行中／待归档／已取消），归档条目由 `task list --archive` 按月查看。结合业务状态、操作和 Git 事实显示待收尾、已移动待提交、完整归档或异常。归档条目带 history 分类：身份有效（id 符合 k- 模式，title／createdAt／branch 非空）、结束有效（status=closed；outcome=completed 时 stage=deliver，cancelled／superseded 保留停止时的非空 stage）且 task.md 已被 Git 索引跟踪（`git ls-files -- <路径>` 批量一次查询）时为 git-history；字段有效但未被跟踪为 local-only；身份或结束字段无效为 invalid 并列出问题明细；Git 查询失败时按未验证处理并记录「Git 跟踪状态不可判定」，不冒充已入库。归档视图末尾只按条数汇总跨机历史与档案异常，逐条明细只列档案问题；默认视图不逐行标注这些分类。跨机克隆缺本机回执时，git-history 档案只读展示，不自动重开，不创建绑定、不产生检查资格，也不能作为新执行或交付的检查证明；完成资格链路不变，归档任务本就不能 adopt／close。归档 task.md 解析失败只写入列表 problems（路径与原因），不中断其余条目；活动区解析失败仍按业务权威报错。同一 taskId 同时出现在活动区与归档或多个归档位置时记录重复来源诊断，操作定位仍以活动区优先，列表不改变任何业务状态。列表缓存按分区记账（任务 k-3d730c8907b3）：活跃分区取 `tasks/` 下每个活跃 task.md 的 dev／inode／size／mtimeNs；归档分区只取 `tasks/archive` 与各 `tasks/archive/<YYYY-MM>` 目录的 dev／inode／size／mtimeNs（O(月份)，不逐条 stat 归档 task.md）。归档条目、problems、父子关系与依赖归档状态随归档索引缓存，命中即复用，指纹变化只重扫该分区。Knit 自身归档／还原／改档操作写 `.knit/.runtime/task-list/archive.invalidation` 显式失效标记，与分区指纹一起参与比较，不依赖目录 mtime；`task list`、`task next` 与 `knit status` 项目概览共用同一分区缓存。绕过 Knit 原地改写或删除已归档 task.md（不改变月份目录的直接子项）不会自动失效，正常流程归档后不再改内容；纯外部 git add／commit 只改索引、不改文件时也不会触发失效。缓存仅在进程内复用，不落盘，新进程首次读取仍按当前目录事实重建。

历史检索同样只读。需求澄清期间为核对既有决定、约束或冲突，可主动检索任务历史并须引用来源；普通对话仅在用户以自然语言明确表达查历史、查上次决定／处理／修改或追溯问题的意愿时使用，不按固定关键词或任务编号判定，不因话题与旧任务相关就主动检索，也不建立持续索引／缓存或第二套历史权威。检索范围为当前任务资料（task.md、plan.md、design.md、research/）、归档任务、实际 run 记录（`.knit/.runtime/runs/<run-id>/`，兼容 `.knit/runs/`）与 Git 提交；查询词按 AND 语义匹配文件或提交，命中返回 `path:line`、`run:<id>` 或 `commit:<sha>` 来源。无匹配返回空结果并说明未找到；找到相关记录只证明内容或时间相关，不能包装为某次修改导致问题的根因结论，缺少复现、对照或验证证据时必须说明因果缺口。

后续 Worktree 列表按 Git 登记与绑定采集各执行目录，区分同 ID 的当前资料和历史副本；不可达绑定保留条目并标明待修复。

Session 列表从第 9.5 节统一索引查询主／子会话、客户端、任务、父子关系和 run，历史片段经所属适配只读取得；不可读取的原生记录保留条目和原因。元数据从 M0 选定的 SQLite 单一仓储读取，不双写 JSON 镜像；run 证据仍按第 5.6 节保留。实现（任务023）：history 按唯一助手条目统计原生用量，input 含 cacheRead／cacheWrite，未知量／费用为 null；status 显示用量，storage 单列原生会话与诊断字节，Git 基线只报引用数量、不与共享对象重复相加。活跃主会话历史由桥接公开 API 读取；离线记录可按已文档化版本只读解析，未知格式只报告引用，不为查询打开可写会话、设置模型或触发轮次。规范索引包含语义描述，按规范变化维护。

任务内容增长时整理当前状态、合并过期描述，并按阅读需要拆出辅助材料。

首版没有 `limits.maxTokens`、`limits.maxCostUsd` 或 `limits.workerTimeoutMs` 配置；用量只观测。主动预算停止作为后续可选能力，不由项目配置暗中启用。

首版依赖与版本按 [TECHNOLOGY.md](TECHNOLOGY.md) 选取，模块与文件写入方按 ARCHITECTURE.md，所有状态按 STATES.md；实现时同步命令、配置和验收，不在本地模块另写不同枚举。

首版不提供 ~/.knit/config.json 行为覆盖；用户本机目录只放跨项目 Session 锁等必要资料，不增加全局模型优先级。--dev 或当前 Pi 会话开关不写项目配置，不纳业务摘要。

### 13.1 开发者模式

默认关闭。M1 只提供本次 --dev 的结构化 stderr 与 M0 对比字段：对象／步骤、reasonCode、摘要、状态决定、耗时、模块／仓储版本及可观察写入／事务计数。业务 stdout／JSON 不混日志，不改变规则／模型／权限，不自动增加回合；不采集正文、凭据、提示词或工具原文。保留一个最小等价冒烟即可。

私有 .runtime/diagnostics/<对象ID>/<写入者ID>.jsonl、Pi /knit dev on/off 会话开关及完整通道验证归 M3A，不是 M1 门槛。桥接分离 stderr，普通终端工具合并输出的限制见 [细则](OPERATIONS.md#7-开发者模式)。

## 14. 初始化与客户端接入

`knit init [--pi] [--force] [--dir <项目>]` 是独立入口。客户端开关由注册表生成，当前只有 `--pi`；不带任何客户端开关时默认 `--pi`，未注册的开关由 commander 直接报未知选项。默认在 Git 项目根执行，monorepo 子目录归一到已确认仓库根；非 Git 目录按指定目录准备资料，并提示正式执行的 Git 条件。初始化不要求启动 Pi，不调用模型、安装依赖、创建正式任务或执行 Git 提交。

初始化分别处理两类文件：项目维护配置、流程配置、阶段提示词与规范，Knit 默认只补缺，已有内容沿用；Knit 管理桥接代码与 `AGENTS.md` 中的标记块，按模板基线核对和更新。生成模板来自 Knit 安装包，不复制开发 Knit 仓库的 `AGENTS.md`。默认不会因版本升级改写已有项目文件；显式 `--force` 时，项目模板文件只要与当前模板不同就按模板覆盖，覆盖前把原文件备份到 `.knit/.runtime/init-backup/<时间戳>/<相对路径>`（目录 0700），内容已一致则不重写；受管桥接在旧基线匹配时更新，人工改动或未知来源报告冲突；AGENTS 受管块内容变化报告差异，`--force` 才显式更新。

1. 确认项目根，检查版本、现有规则与逐文件计划；存在冲突先报告。
2. 准备运行目录忽略规则和私有权限，写 `preparing` 初始化清单及本机安装映射。
3. 补缺项目配置、`.knit/workflow.yaml`、阶段提示词和规范索引，准备受管入口与桥接候选文件。
4. 核对文件与模板指纹、CLI 映射和客户端兼容信息后，原子发布桥接并把清单置为 `ready`。失败记录逐项结果，桥接仅在本机清单 ready 且匹配时处理操作。
5. 输出已创建、沿用、更新、冲突与下一步；Pi 按原生项目信任规则加载，可信项目中新会话可自动加载，已有会话 `/reload` 或重启。换机器 init 补齐本机映射，无需另装全局扩展。

安装 ready 只证明文件和映射一致，不授予 Pi 项目信任。未受信时说明桥接未加载的原因，不默认通过 `--approve` 绕过；子 worker 使用明确的资源策略，与主桥接自动发现分开。

`init --check` 只展示计划；`init --check --force` 只预览将覆盖的项目模板项，不写文件、不建备份。实际初始化与其他项目写操作共用项目占用，不能在阶段或收尾运行中更新桥接和公共输入。重复执行保留项目维护的正文；默认不覆盖项目文件，`--force` 覆盖与当前模板不同的项目模板文件并先备份原文，内容已一致不重写。受管内容与旧基线一致时才更新；上次清单的受管基线可升级，人工改动或未知来源报告冲突，`--force` 才覆盖。上次清单记录、当前模板不再生成但项目里仍存在的文件作为“模板已移除文件”报告，默认只报不删，是否清理由主会话核对内容与来源后决定；孤儿报告不阻断 ready，覆盖也不删除用户自建的非模板文件。中断按逐项清单继续，未知版本不降级；项目由更新版本初始化时拒绝降级。安装映射每次 init 按本机入口重写，桥接不嵌项目／机器绝对路径。实现（任务022）：桥接全局 observer guard 在 reload／重复加载时停止旧轮询和定时器，避免重复通知；ready 仍不等于 Pi 项目信任。

已有设计／开发规范优先建立索引引用，保留原权威位置；缺少规范时先给简短索引和提炼指引，不由 CLI 猜测通用规则。后续按第 8.2 节从真实讨论、实施与检查持续完善，不依赖任务是否存在。

### 14.1 Git 与项目边界

正式任务创建、写入型 worker 和提交归档要求本地 Git 仓库、有可读 HEAD、处于本地分支、身份匹配且无进行中的 merge、rebase、cherry-pick、revert、bisect 或冲突。运行目录必须忽略且未跟踪，否则阻塞这些操作。非 Git、空仓库或 detached HEAD 可初始化资料和只读诊断；非正式辅助检查需显式范围，无法核实 Git 状态时仅做只读分析，不执行 shell 验证。不会自动 init Git 或创建提交。

monorepo 子目录统一使用已确认仓库根和相对路径，验证命令可指定包 cwd。子模块可明确选为独立项目；父子仓库跨界修改或 gitlink 提交不自动处理。已有脏文件本身不阻塞，先保存对照并区分归属。占用仅协调 Knit，外部并发和网络盘边界见运行细则。

保留现有 Git hooks，限定路径提交不得混入无关 index；不使用 `--no-verify`。hook 失败保留现场，hook 修改已检查内容时使检查失效。提交后核对实际 commit、index 与工作区；无法在现有 hook 行为下保持范围时报告阻塞。

## 15. 交付范围

### 15.1 首版闭环

首版以独立 CLI 初始化和运行，使用内部 Pi 与 local 模块，在当前项目和绑定分支完成闭环。

1. 按授权创建任务，维护单主文档、稳定身份、当前状态与结束结果。
2. init 建立项目入口、资料与规范索引；从最小闭环开始包含候选扫描、主 Agent 核对和正式规范更新，是首版核心能力。
3. 内部 Pi runtime 与 local 适配器从第一条闭环走正式装配路径：application 层首版为固定装配（直接组合内部适配器），保留显式注入点（StageRunner／非正式检查的 runtimeFactory 与 piExecutable、SessionService 的 checkFile）；通用接口抽象待第二实现出现时再提升为端口，不在首版预建。
4. 通过 CLI 协调讨论、配置阶段、按任务要求的检查与提交归档；默认模板保留 implement／check，项目可增删阶段；按既定优先级选模型，修复次数有界。
5. 通过内部 Pi runtime 记录阶段、主／子 Session、检查与快照；支持取消和恢复，实际消耗只观测，不以累计 token 中止任务。
6. 在当前绑定分支按任务做限定路径产物／资料提交与归档提交，保护既有改动与 index，写断点记录并扫描本次入库内容。
7. 提供命令／工具入口与当前项目查询，`doctor` 和 `storage` 只读诊断；归档保留恢复引用，首版不自动 gc。
8. 主会话每轮注入当前任务、阶段与资料入口；是否创建任务由用户决定，复杂任务按需持久 plan／design／research 资料并跨会话接续（第 3.4–3.6 节、第 4.2 节、第 9.6 节）。

按第 16.4 节依次推进：先 M0／M1 得到可观察闭环，真实项目使用前完成 M2，首版发布完成 M3A／M3B。里程碑不削弱授权、范围、凭据和实际交付证据要求，也不扩展多人协作。
